## 0. 一页结论与当前进度

**问题不在「功能不够」，而在「模式」是个输入变量**（用户手切）→ 每个功能各自判一次模式 → 12 处分叉、6 个横幅分支、若干「点了必然失败」的入口。

**解法**：把「模式」从**输入**改为**输出**（连接探测的投影）。代码里于是只剩一条路径 ＋ 一张**能力表**：

- **功能不冲突** —— 不可用能力**统一门控**（能力表驱动），不再各写一套 `if`。

- **UI 一致** —— 前端**不再认识** **`auto / analyzer / local`**，只认能力；同一功能只有一套 DOM。

- **⭐ 额外收益** —— 两种形态**共存于同一份代码**，**不需要「拆中继」**（关掉 Analyzer 即自动独立，开回来即自动组合）：切换从「一次性决策」变成「**运行时事实**」。

| 目标变更量   | **≈ 净 +180 行**（分叉点 **12 → 3**）                            |
| 剩余阶段    | **阶段 5** 收敛（退役旧端点 / 三入口合一）· **阶段 6** 可选（置灰 → 隐藏）　**〔阶段 0/1/1.5/2/3/4 已落地 2026-10-03〕** |

## 1. 问题诊断：判据有两套，而且在打架

### 1.1 两套判据

| 判据            | 载体                                                 | 变更方式              | 分叉点 |
| ------------- | -------------------------------------------------- | ----------------- | --- |
| **A · 数据源模式** | `store.SOURCE["mode"]` ＋ `data/source_config.json` | **用户手切**（设置面板三选一） | 6 处 |
| **B · 连接健康**  | `/api/fetcher-health` → `reachable` ＋ `sessdata`   | **自动轮询**（5 分钟）    | 6 处 |

A 与 B **语义交叉**：`mode=analyzer` 但 Analyzer 不可达时，到底算哪个模式？现状靠 `auto` 的隐式降级 ＋ 一堆诊断码「圆场」，于是出现 `src-diag-path_missing`、`auto-degraded`、`mode-local` 这些**只有开发者能分辨**的状态。

### 1.2 分叉点普查（12 处，归类）

| 类             | 分叉点                                                                                                    | 问题                     |
| ------------- | ------------------------------------------------------------------------------------------------------ | ---------------------- |
| **判据定义**      | `store.SOURCE_MODES` 三态 ＋ 模块级 `SOURCE`；`_pick_sources` 三分支（**`analyzer`** **与「`auto`** **且有数据」完全等价**）  | 冗余分支；用户需理解内部概念         |
| **判据派生物**     | `analyzer_db_diagnosis` 5 分支诊断；`_health_payload` 一个 payload 塞三种信息                                      | 都是「判据重复」的产物            |
| **手切端点**      | 手切端点 ＋ 写配置                                                                                             | 与 B 判据并存               |
| **功能冲突** ⚠️   | `/api/fetcher-trigger`（`local` 下也走 Analyzer）· `/api/fetcher-check` · `/api/export/*` · `/api/images/*` | **`local`** **下点了必失败** |
| **UI 不一致** ⚠️ | 横幅 **6 个** **`if`** **分支**；设置面板暴露 `auto/analyzer/local` 三选一；⑧⑨⑩⑪ 测试入口**无门控**                           | 认知负担 ＋ 点了必报错           |

> **根因：模式是「可变的输入」。** 其余 10 处都是它的派生。

### 1.3 抓取入口现状：三个按钮、三套判据（阶段 2 的靶子）

| 前端按钮   | 打到哪                        | 内部判据                                |
| ------ | -------------------------- | ----------------------------------- |
| 「同步数据」 | `POST /api/sync`           | 读 `store.get_source_mode()` → 分派    |
| 「全量重建」 | `POST /api/sync?full=1`    | 同上 ＋ `full` 来自**前端传参**              |
| 「实时更新」 | `GET /api/fetcher-trigger` | **绕过 mode**，只走 Analyzer；自带「增量→全量」回退 |

**同一个「抓取」有三条路、三套判据、两个入口。** 目标：合成**一个**入口，策略由后端自定。

## 2. 目标架构：连接 → 能力/策略 → 呈现（三层，单向）

```
┌─ L1 探测层（后端，唯一真相源，唯一做 IO 的地方）───────────────┐
│  probe_connection()                                          │
│    analyzer: {reachable, db_ok, db_count, diagnosis{level,code}}│
│    finder:   {sessdata, db_count, last_success_at}            │
└───────────────────────────┬──────────────────────────────────┘
                    │ 纯函数，无 IO（两个并行的消费者）
        ┌───────────┴────────────┐
┌─ L2a 能力层 ──────────────┐ ┌─ L2b 策略层 ───────────────────┐
│ derive_capabilities(probe)│ │ decide_sync_plan(probe,policy,state)│
│  → 每项{available,owner,  │ │  → {mode: full|inc|skip|blocked,  │
│         reason}            │ │     reason, owner}                │
│  回答「**能不能**」            │ │  回答「**怎么做**」               │
└───────────┬───────────────┘ └───────────┬───────────────────┘
            └──────────┬──────────────────┘
                       │ GET /api/capabilities（含 plan 预览）
┌─ L3 呈现层（前端，唯一渲染的地方）────────────────────────────┐
│  按 capabilities 渲染；**前端不出现 auto/analyzer/local 字样** │
└──────────────────────────────────────────────────────────────┘
```

**为什么拆 L2a / L2b**：Q1（`local` 要留且日后加策略）与 Q3（同步策略后端自定）其实是**同一件事的两面** —— 一个统一的「策略层」。L2a 答「能不能」、L2b 答「怎么做」，**两者吃同一个 probe**，拆开不增加 IO，只多一处纯函数。

**落点分工（直接决定可测性）**：`probe_connection()` 落 `server.py`（只有它持 `_forward_fetcher` / `_sessdata_status` 等网络能力）；`derive_capabilities()` 与 `decide_sync_plan()` 落 `store.py` —— 都是**纯函数**，可脱离 HTTP 单测（喂一个假 probe 即可）。

**三条铁律（UI 一致的判据）**

1. **同一功能只有一套 DOM** —— 不存在「模式 A 的导出按钮」与「模式 B 的导出按钮」。
2. **不可用 = 置灰 ＋ 统一 tooltip**（策略：内部先灰、日后可一键转隐，见 D7）。
3. **前端零模式词汇** —— 用户只看得到「当前形态：组合 / 独立」这一句人话。

## 3. 关键设计决定（D1–D7）

### D1 · 模式三态 → 二态，且由「输入」降级为「输出」

- **删除手切值** **`analyzer`**（与「`auto` 且有数据」完全等价，是冗余分支）。

- **`auto`** **成为唯一默认** = 「能连上 Analyzer 就用它，否则用本地」。

- `local` **保留**（**不是隐藏**）—— 但**当前无 UI 入口**（`adr/0005` 保留；仅配置文件 / `POST /api/data-source` 可设），设置面板只**只读展示**「当前形态（`#srcModeBox`）」。⚠️ **原设计未落地**：D1 初稿设想以「策略」名义给出「跟随连接（默认）」／「始终用本地库」两张卡，**实现时只做了只读形态卡、没有 `local` 的策略 UI 入口** → 与 §4「设置面板改只读形态卡」一致，但与本条初稿不符，属**未决边界**（见 §6.1 `O13`）。纯调试用的 `?force=local` 仍保留。

### D2 · 一个端点取代两个：`GET /api/capabilities`

响应含 `mode`（`combined | standalone`，只读结论）· `connection`（analyzer / finder 两段）· `data`（条数）· `plan`（本次同步计划 ＋ 一句话理由）· `capabilities`（逐项 `{available, owner, reason}`）。

- 不可用时形如 `{"available": false, "owner": null, "reason": "需要 Analyzer 连接（当前不可达）"}` —— 而不是「点了然后失败」。

- **能力项数与键名以** **`现状.md`** **为准**（`CAPABILITY_KEYS` / `CAPABILITY_DOC`），本文件不复述。

- `/api/fetcher-health` 与 `GET /api/data-source` **由它取代**；旧端点是「兼容别名」还是「直接删」见 §6 **O9**。

### D3 · 抓取单入口：`/api/sync` 内部按能力 ＋ 策略分派 ⭐

| <br />  | 现状                                                                      | 设计后                                                 |
| ------- | ----------------------------------------------------------------------- | --------------------------------------------------- |
| 前端按钮    | 「同步数据」＋「全量重建」＋「实时更新」三选一                                                 | **只有「同步数据」一个**                                      |
| 后端行为    | `POST /api/sync` 按 `mode` 分派；`/api/fetcher-trigger` 绕过 mode 只走 Analyzer | `/api/sync` **既读状态也触发**：Analyzer 可达 → 中继抓；不可达 → 本地抓 |
| 增量 / 全量 | **前端传** **`?full=1`**                                                   | **后端策略决定**，`?full=1` 降为隐藏 override                  |
| 前端需要知道的 | 谁在抓、走哪条路、增量还是全量                                                         | **什么都不需要知道**（响应带 `plan.reason` 一句话）                 |

> **实测更正（重要）**：原本把「单入口分派」列为**中高风险、需新造**。实读发现 —— `POST /api/sync` **已有一层按模式分派的骨架**，而 `/api/fetcher-trigger` **已把「增量失败→自动升级全量」的回退策略写好**。
> **所以 D3 不是「新造策略引擎」，而是「把已散在三处的判据换成一处」** → 风险由**中高降到低-中**。

### D4 · 能力门控取代模式分支

所有 Analyzer-only 入口（图片批量下载 / Excel / 完整性自检 / 备注 / 测试入口）统一挂 `applyCapabilities()`：**不可用 → 置灰 ＋ 统一提示**。后端对应端点加前置检查，不可用时返 `409 {"ok":false,"error":"not_supported","reason":...}`（**不再 502 / 转发失败**，语义清晰）。

### D5 · 凭证归属显性化

`capabilities` 带凭证归属（`owner` ＋ 状态），前端一句话即可说清「凭证由谁持有、是否有效」：

| 形态 | owner                   | 前端一句话                 |
| -- | ----------------------- | --------------------- |
| 组合 | Analyzer（`config.yaml`） | 「凭证由 Analyzer 持有（有效）」 |
| 独立 | Finder（`config.json`）   | 「凭证由本机持有（需更新 / 有效）」   |

用户不再需要理解「为什么有两个配置文件、哪个生效」。

### D6 · ⭐ 策略层：`decide_sync_plan(probe, policy, state)`

**一个纯函数，一张规则表，一个可扩展的配置结构。**

| 规则（自上而下，命中即止）      | 触发条件                                                                           | 产出                         |
| ------------------ | ------------------------------------------------------------------------------ | -------------------------- |
| **R5 凭证闸门**        | `owner=finder` 且 Finder 凭证**非** **`present`** ·（**提到规则表之前执行**，不可被 override 绕过） | `blocked` ·「需要有效 SESSDATA」 |
| R1 首次建基线           | 本地 `last_success_at` 缺失 / 库为空                                                  | `full` ·「首次建基线」            |
| R2 缺基线自动升级（现有逻辑搬入） | 上次增量返回「未找到本地历史记录」**且不在全量冷却内**                                              | `full` ·「缺基线，自动升级为全量」      |
| R3 长尾缺口修复          | 本地跨度比**历史峰值**少 > `gap_threshold_days` **且** 距上次全量 > `full_interval_days`       | `full` ·「修复长尾缺口」           |
| R4 防连点             | 距上次全量 < cooldown                                                               | `skip` ·「刚刚跑过，冷却中」         |
| R6 默认              | —                                                                              | `incremental` ·「常规增量」      |

> **R2 与 R4 共用冷却判据**（阶段 2 落地时补）：缺基线标记一旦粘住，若 R2 不看冷却，每次点击都会跑一次全量、冷却形同不存在 → R2 命中但仍在冷却内时输出 `skip`（「缺基线，但 N 秒前刚跑过全量，冷却中」）。配套：**全量成功即清 `no_baseline`**（`server._note_full_success()`），并单独记 `last_full_at` —— Analyzer 侧全量不写本地库 meta，不记这一笔 R4 对 Analyzer 形态永不生效。

**配置结构升级**（`data/source_config.json`，**必须兼容旧文件**）：

```json
{
  "policy": { "prefer": "auto", "sync": "auto", "rules": { "full_cooldown_min": 10, "full_interval_days": 7, "gap_threshold_days": 30 } },
  "analyzer_db": "<Analyzer 主库路径>"
}
```

- `prefer`: `auto | local`（**`analyzer`** **删除**；两项**都在界面上可见**，以「策略」名义呈现）。

- `sync`: `auto | full | incremental`（后两项即原 `?full=1` 的隐藏 override）。

- `rules`: **预留扩展位** → 「后续增加具体策略」 = 往这里加字段 ＋ 往 R 表加一行。

**两条纪律**：① **可解释** —— 每次同步响应都带 `plan: {mode, reason}`，前端原样显示成一句话；② **可覆盖** —— 隐藏 override 永远存在，只是不进 UI。

> **⚠️ 落地更正（实测，以实现为准）**
>
> 1. **R3 原判据是错的**：原写「增量缺口 > M 条」，且把「缺口」理解为「主源 − 本地」。**实测**该差是 **B站接口只保留近三个月** 造成的**结构性差异**，不是缺口 → 拿它当判据会让 R3 **在任何状态下命中**、每 `full_interval_days` 白跑一次全量（而全量同样补不回长尾）。→ 已改为 **「本地跨度 vs 历史峰值」**（`state.span_peak_days`）；结构差异降级为 **`advisory`**（说明性字段，**不参与决策**），文案直接指向 **P2 一次性迁移**。
> 2. **R5 的位置与判据都收紧**：① **提到规则表之前**（它是安全闸门，override 与 R1–R4 都不应绕过）；② 判据由「`prefer=local` 且凭证无效」改为 **「`owner=finder`** **且凭证非** **`present`」** —— 这样「独立形态下没有凭证」也被挡住，且与 `derive_capabilities()` 的 `fetch` 项**共用同一判据**（否则会出现「能力说不能抓、策略说可以增量」）。

### D7 · 「置灰 → 隐藏」做成「单点常量」

#### ⚠️ 为什么拆成两维（`fetch` 语义裁定的落点，2026-10-03）

**问题**（第四轮审查 §七.1）：`fetch` 能力与 `CAP_DOM.fetch` **语义不等价** → 独立形态 ＋ Finder 凭证有效时，能力表说「可以抓」，但 `#anRealtimeBtn` 打的 `/api/fetcher-trigger` 是 Analyzer 中继、由门控拦 → **必 409** → 「按钮亮着、点了必失败一次才置灰」，与阶段 4 完成标志冲突。

**裁定（用户）**：**「Finder 自己能抓」** —— 即 `fetch.available=true, owner="finder"` 这个结论**是对的**，错的是把它挂到 Analyzer 的中继按钮上。

**修法**：把「能力」与「端点归属」拆成两维，各用各的判据：

| 维度 | 表 | 判据 | 回答的问题 |
| --- | --- | --- | --- |
| 能力 | `CAP_DOM`（7 键） | `caps[cap].available` | **这件事**能不能做 |
| 端点归属 | `ANALYZER_ONLY_DOM` | `connection.analyzer.ok`（**业务级**） | **这个按钮的端点**在不在 Analyzer 上 |

## 7. 并行 / 暂缓的分支

### 7.1 Finder 轻量化（`archive/方案-Finder轻量化.md`）——**已改判：不切形态**

原方案是「5 步切到单 Finder ＋ 拆中继」，**收益是「形态」而非「代码量」**。本方案（连接即模式）**替代了它的切换路径**：

| 维度   | 拆中继方案           | 连接即模式（本方案）                     |
| ---- | --------------- | ------------------------------ |
| 中继代码 | **删除**（≈500 行）  | **保留**，`available=false` 时不被调用 |
| 模式切换 | 手工拆/装 → **不可逆** | 关掉 Analyzer 即自动独立 → **可逆、零成本** |
| 实施顺序 | 5 步，第 5 步无退路    | 每步可独立回退                        |
| 数据深度 | 需先做一次性迁移（P2）    | **同**（P2 仍需要，与形态无关）            |
| 风险   | 中高（拆完无退路）       | **低**（纯增为主）                    |

**结论**：先做本方案；**保留中继**（决策见 `adr/0006`）。轻量化核算证明「收益是形态而非代码量」，故「保留中继」不构成损失。其 §6 的取舍点 **A–D 里 B / C / D 已由取舍自动回答，只剩 A → 即 O1（**已定：保留**）**。

> **唯一不变的硬约束仍是 P2**（一次性把 Analyzer 主库导入本地库）—— 那是**数据问题，与架构无关**。
