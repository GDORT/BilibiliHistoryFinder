## 1. 现有前端架构与已落地能力

### 1.1 文件与规模（实测）
| 文件 | 行数 | 职责 |
|---|---|---|
| `src/web/index.html` | 210 | 页面骨架、抽屉/弹层容器 |
| `src/web/app.js` | 1643 | 全部交互逻辑（加载/渲染/筛选/规则/批量/同步） |
| `src/web/style.css` | 397 | 样式 |

### 1.2 功能分区（app.js 实测）
- **数据加载与渲染**：`load()` / `render()` / `cardHtml()` / `skipBadgeHtml()` —— 调 `/api/query` 取记录，渲染卡片（封面/标题/UP主/进度条/跳过角标）。
- **视图切换**：`setView(v)` —— finished / auto_skip / stale / needs / all，对应三视图+全部。
- **基础筛选**：类型（archive/live/article/pgc）、时间范围、时长范围 —— `timeRangeToTs` / `durToSec` / `buildQueryBody`。
- **高级筛选器（超集）**：`renderAdvGroups()` / `advCondHtml()` / `renderAdvHaving()` / `renderAdvSort()` / `renderAdvViews()` / `renderAdvLists()` —— 组合布尔 AND/OR/NOR+NOT、相对时间、空值、正则、聚合 HAVING、排序、保存视图、黑白名单。
- **规则抽屉**：`openRuleDrawer()` / `renderRuleList()` / `attachRuleListEvents()` / `pollRuleStatus()` —— 单活跃规则管理、冲突提示、dry-run 状态轮询。
- **批量操作**：`batchEligible()` / `syncBatchButtons()` / `updateBatchEligibility()` —— 多选 + 批量归档/跳过/取消。
- **同步状态**：`pollSync()` / `applySyncStatus()` —— 轮询 `/api/sync` 状态，展示进度。
- **视图/名单持久化**：`loadViews()` / `saveViewCall()` / `loadLists()` / `saveListCall()` —— 走 `/api/views` + `/api/lists`。

### 1.3 验证状态
- 已通过 HTTP 端到端验证：各视图 counts 正确、批量/规则持久化于侧库、首页/封面 200。
- 三视图不变式精确：`finished 1473 + auto_skip 1226 + stale 0 + needs 579 = 3278`。

## 3. 历史展示页设计要点（已落地，供参考）

- **卡片单元**：封面图（`/cover/` 代理防跨域）+ 标题 + UP主名/头像 + 进度条（`progress_pct`）+ 跳过角标（manual/auto_exempt/auto_skip 理由）+ 相对时间（`relTime`）。
- **三视图 Tab**：待续看 / 已跳过 / 久未动 / 全部，顶部展示各视图计数（来自 `/api/query` 返回的 `counts`）。
- **分页**：`PAGE=60`，滚动或翻页加载。
- **设计原则**：信息密度优先、操作就近（卡片内直接跳过/归档）、分类状态可解释（角标显式理由）。

### 3.5 高级筛选器（超集，已落地，吸收自 `记录筛选规则分析.md` §11）
> 原 `doc/记录筛选规则分析.md` 已归档，其 §11「高级筛选器演进」核心吸收于此；规则引擎底层（三视图/冲突/优先级）归后端轴（见 `方案-后端与数据源.md` §3.8）。

**设计约束**：高级筛选器必须是**当前引擎规则的超集**——保留三视图、跳过优先级、冲突校验、单 active 规则语义，不得丢失；在此之上扩展通用筛选能力。

**已落地全部能力（2026-08-24 完成，作为当前引擎超集）**：
| 能力 | 算子/说明 |
|---|---|
| 组合布尔 | AND / OR / NOR + 组内 NOT（条件组嵌套） |
| 相对时间 | `relative_after` / `relative_before`（如"近30天"） |
| 空值判断 | `exists` / `empty` |
| 文本增强 | `regex` / `not_contains`（原有 `contains`） |
| 集合匹配 | `in_list` / `not_in_list`（黑白名单） |
| 范围反向 | `not_between`（原有 `between`） |
| 聚合 HAVING | 同 UP主/分区等分组计数阈值（如"同UP主>5条"） |
| 排序 | 多字段 `apply_sort`（view_at/progress/duration/author 等） |
| 保存视图 | `saved_views`（落侧库 `data/canonical_state.db`） |
| 批量操作 | 多选 + 批量归档/跳过/取消（批量写侧库） |

**实测验证**（3278 条合并集）：OR 筛选 1551、近30天 1556、有备注 389、同UP主>5条 789，三视图不变式仍精确成立（1473+1226+0+579=3278）。

**与官方前端对比**：官方仅基础筛选（类型/日期/分区）+ 海量分析页；本高级筛选器是其**超集**，且叠加续看三视图规则引擎——这是替代谈判中"我们更强"的部分。

## 4. 控制 Analyzer 前端变更量（Phase 1.5）

> 配套后端见 `方案-后端与数据源.md` §5（路径 A 转发层）。

### 4.1 需要新增/修改的增量（前端侧）
| 项 | 文件 | 性质 | 估量 | 说明 |
|---|---|---|---|---|
| ③ 实时更新按钮 | `app.js`+`index.html`+`style.css` | 新增按钮 + 触发 + 刷新 | ~70 行 | 调 `POST /api/trigger-realtime`，成功后重 `load()`；加"同步中"态（复用 `pollSync` 模式） |
| ④ 设置项（可选） | `app.js`+`index.html` | Fetcher 地址/Key 配置 UI | ~40 行 | 存 localStorage；若 Key 经 server 代理则不必暴露前端 |

**前端合计 ≈ 110 行。**

### 4.2 交互流程
1. 用户点「实时更新」→ `app.js` `POST /api/trigger-realtime`。
2. `server.py` 转发 `GET localhost:8899/fetch/bili-history-realtime`（SESSDATA 服务端读取，前端不碰凭证）。
3. 后端返回进度/完成 → 前端置"同步中"态，轮询或等待。
4. 完成后前端重 `load()` 刷新三视图（ Analyzer 库已被 Fetcher 更新，只读重读即得新数据）。

### 4.3 风险
- 本机 Fetcher 后端未运行 / SESSDATA 过期 → 触发失败，前端须有错误 toast（复用现有 `toast()`）。
- 按钮仅在"本机 Analyzer 后台可达"时有意义；不可达时禁用或提示。

## 5. 独立前端全量设计评估（不含历史记录展示页，仅评估）

> 问题：官方 Frontend 是"全家桶"（历史/年度/收藏/评论/下载/动态/计划任务/设置）。若作为**独立前端**全量实现（**排除历史展示页**——那块我们已有且更强），网页应如何设计？

### 5.1 设计前提
- 纯前端 / 轻前端：控制与数据来自 Fetcher 后端（`:8899`），前端只消费 API + 触发 `/fetch/*`。
- 排除历史展示页：续看分类/历史列表归我们现有工程，不重复造。
- 对齐官方能力面：年度分析、收藏夹、评论、动态、视频/图片下载、计划任务、登录态管理、设置。

### 5.2 推荐页面拓扑
```
App Shell（左侧导航 + 顶栏）
├─ 仪表盘 / 概览（Dashboard）         聚合各域关键指标
├─ 年度分析（Annual Analytics）       官方 20+ 分析页收敛为单页 + 内部 Tab
│   └─ 时长分布/分区偏好/UP主完成率/重看率/热门命中率…（走 /analysis /viewing /title /daily /popular）
├─ 收藏夹（Favorites）                /favorite
├─ 互动动态（Interactions & Dynamic） /interactions + /dynamic 合并
├─ 评论（Comments）                   /comment
├─ 下载中心（Downloads）              /download + /collection + /video_details + /images
│   └─ 任务列表 / 进度 / 历史记录（仅 UI，实际下载交后端）
├─ 同步与计划（Sync & Scheduler）     /fetch + /scheduler
│   └─ 实时更新按钮 / 全量补拉 / 每日计划任务开关
├─ 账号（Account / Login）            /login/qrcode 扫码登录态管理
└─ 设置（Settings）                   服务器地址 / X-API-Key / 本地图片开关（存 localStorage）
```

### 5.3 与官方差异的取舍
| 维度 | 官方 | 本设计建议 |
|---|---|---|
| 分析页数量 | 20+ 独立路由 | 收敛为"年度分析"单页 + 内部 Tab，前端只做图表渲染（ECharts/Chart.js） |
| 下载 | 内嵌 yutto 调用 | 仅任务提交 + 状态轮询 UI，实际下载交后端 `/download` |
| 登录 | 二维码弹窗 | 独立"账号"页：登录态有效期 + 扫码刷新 |
| 设置 | 散落 | 统一"设置"页，建议经我们 server 代理转发以隐藏 Key |
| 技术栈 | Vue3+Tauri 重壳 | 原生 HTML/JS 或轻框架 + 单 Python 代理（消除 Tauri 打包负担；CORS 全开可直连 8899，但须经代理隐藏 Key） |

### 5.4 必须依赖的后端接口契约
- 读：`/history/all`、`/history/search`、`/analysis/*`、`/viewing/*`、`/favorite/*`、`/interactions/*`、`/dynamic/*`、`/comment/*`、`/download/*`、`/video_details/*`
- 写/触发：`/fetch/bili-history[-realtime]`、`/importSqlite/import_data_sqlite`、`/scheduler/*`、`/login/*`
- 鉴权：`X-API-Key`（设置页配置，建议经 server 代理转发以不暴露 Key 于浏览器）

### 5.5 工作量评估（纯前端，不含已有历史页）
- **低（复用契约，纯渲染）**：仪表盘、年度分析图表、收藏/互动/评论列表、账号页、设置页 —— 约 1200–1800 行 JS + 对应 HTML/CSS。
- **中（状态机/轮询）**：下载中心（任务提交+进度轮询）、同步与计划（触发+刷新+调度开关） —— 约 600–900 行。
- **关键风险**：① 官方 20+ 分析页具体图表定义需对 `:8899/docs` 逐接口实测字段；② 下载/计划任务涉及写操作，须确认后端鉴权与并发；③ 若前端直连 8899，X-API-Key 暴露在前端代码——**安全上必须经代理**。
