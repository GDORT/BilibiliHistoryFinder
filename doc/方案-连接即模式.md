## 0. 一句话结论

**现状的问题不是"功能不够"，而是"模式"是个**输入变&#x91CF;**（用户手切），于是每个功能都得自己判一次模式 → 12 处分叉、6 个横幅分支、一堆点了必然失败的入口。**

**你的思路是对的，而且比"拆中继"更优**：把「模式」从**输入**改为**输出**（连接探测的投影），代码里就只剩一条路径 + 一张**能力表**。这样：

- **功能不冲突** —— 不可用的能力**统一门控**（由能力表驱动），而不是各写一套 if。
- **UI 一致** —— 前端**不再认识 `auto/analyzer/local`**，只认能力；同一功能只有一套 DOM。
- **⭐ 额外收益**：做完之后，两种模式**共存于同一份代码**，**不需要 §7 那个不可逆的"拆中继"** —— 关掉 Analyzer 就自动是单 Finder，开回来就自动是组合，**切换从"一次性决策"变成"运行时事实"**。

**变更评估：≈ 净 +180 行**（新增能力层 ≈130 · **新增策略层 ≈65**，删冗余分叉 ≈60，前端重写 ≈70 与删减相抵），分叉点由 **12 处收敛到 3 处**。

> **⭐ 实读更正（本轮最重要的一条）**：原估把"`/api/sync` 单入口分派"列为**中高风险、需新造**。实读发现 —— `POST /api/sync`（`server.py` 1655–1700）**已经有一层按模式分派的分派骨架**：`auto`/`analyzer` → `_forward_fetcher("/fetch/bili-history")` 中继全量；`local` → `run_sync_background(full)` 本地抓取。而 `GET /api/fetcher-trigger`（1428–1452）**已经把"增量失败→自动升级全量"的回退策略写好了**（命中「未找到本地历史记录」即升级，对齐开源 Frontend）。
>
> **所以 D3 不是"新造策略引擎"，而是"把已散在三处的判据换成一处"** —— 风险由**中高降到低-中**，工作量由 ≈+25 变为 ≈+30（换判据 + 合并回退分支）。

## 2. 架构设计：连接 → 能力/策略 → 呈现（三层，单向）

```
┌─ L1 探测层（后端，唯一真相源，唯一做 IO 的地方）───────────────┐
│  probe_connection()                                          │
│    analyzer: {reachable, db_ok, db_count, diagnosis{level,code}}│
│    finder:   {sessdata_state, db_count, last_success_at}      │
└───────────────────────────┬──────────────────────────────────┘
                    │ 纯函数，无 IO（两个并行的消费者）
        ┌───────────┴────────────┐
┌─ L2a 能力层 ──────────────┐ ┌─ L2b 策略层（Q1/Q3 落点）──────┐
│ derive_capabilities(probe)│ │ decide_sync_plan(probe,policy)│
│  → 每项{available,owner,  │ │  → {mode: full|inc|skip,      │
│         reason}            │ │     reason, owner}            │
│  回答「**能不能**」            │ │  回答「**怎么做**」               │
└───────────┬───────────────┘ └───────────┬───────────────────┘
            └──────────┬──────────────────┘
                       │ GET /api/capabilities（含 plan 预览）
┌─ L3 呈现层（前端，唯一渲染的地方）────────────────────────────┐
│  按 capabilities 渲染；**前端不出现 auto/analyzer/local 字样** │
└──────────────────────────────────────────────────────────────┘
```

> **为什么要拆 L2a / L2b**：你的 Q1（local 要留且日后加策略）与 Q3（同步策略后端自定）其实是**同一个东西的两面** —— 一个统一的"策略层"。**L2a 回答"能不能"，L2b 回答"怎么做"，两者都吃同一个 probe**，所以拆开不增加 IO，只增加一处纯函数（≈45 行）。合并成一层的后果是：日后想加"何时切本地/何时全量"的规则，会再次散落回 12 处。

> **落点分工（直接决定可测性）**：`probe_connection()` 落 **`server.py`**（只有它持有 `_forward_fetcher` / `_sessdata_status` 等网络能力）；`derive_capabilities()` 与 `decide_sync_plan()` 落 **`store.py`** —— 两者都是**纯函数**，可脱离 HTTP 单测（喂一个假 probe 即可）。这正是 §6.4 第 1–4 笔能"零风险、可暂停"的原因。

**三条铁律（UI 一致的判据）**

1. **同一功能只有一套 DOM** —— 不存在"模式 A 的导出按钮"和"模式 B 的导出按钮"。
2. **不可用 = 置灰 + 统一 tooltip**（Q2：内部先灰后隐，见 D7）。
3. **前端零模式词汇** —— 用户永远看不到 `auto/analyzer/local`，只看得到"当前形态：组合 / 独立"这一句人话。

## 3. 关键设计决定

### D1 · 模式三态 → 二态，且从"输入"降级为"输出"

- **删除手切值 `analyzer`**（它与"`auto` 且有数据"完全等价，是冗余分支）。
- **`auto` 成为唯一默认** = "能连上 Analyzer 就用它，否则用本地"。
- `local` **保留**（Q1：需要，**不是隐藏**）—— 但**以「策略」的名义呈现**（「跟随连接（默认）」／「始终用本地库」），界面上不出现 `auto/analyzer/local` 这套内部词；纯调试用的 `?force=local` 仍保留。

### D2 · 一个端点取代两个：`GET /api/capabilities`

响应结构（示意）：

```json
{
  "ok": true,
  "mode": "combined",            // 只读结论：combined | standalone
  "connection": {
    "analyzer": {"reachable": true, "db_count": 4048, "diagnosis": {"level":"ok","code":"ok"}},
    "finder":   {"sessdata": "valid", "db_count": 2865, "last_success_at": 1756...}
  },
  "data": {"analyzer": 4048, "local": 2865, "merged": 4120, "effective": "analyzer"},
  "plan": {"mode": "incremental", "reason": "距上次全量 3 天，无长尾缺口"},
  "capabilities": {
    "fetch":     {"available": true,  "owner": "analyzer", "reason": ""},
    "sync":      {"available": true,  "owner": "analyzer", "reason": ""},
    "remark":    {"available": true,  "owner": "analyzer", "reason": ""},
    "export":    {"available": true,  "owner": "analyzer", "reason": "", "formats": ["excel","db"]},
    "images":    {"available": true,  "owner": "analyzer", "reason": ""},
    "integrity": {"available": true,  "owner": "analyzer", "reason": ""},
    "analysis":  {"available": true,  "owner": "analyzer", "reason": ""},
    "backup":    {"available": true,  "owner": "finder",   "reason": ""}
  }
}
```

不可用时形如：`{"available": false, "owner": null, "reason": "需要 Analyzer 连接（当前不可达）"}`。
  
**典型新增态**（Q1 带来）：`fetch/sync` 在"独立形态 + 凭证无效"时应为
  
`{"available": false, "owner": "finder", "reason": "需要有效 SESSDATA（当前 -101 已失效）"}` —— 而不是"点了然后失败"。

> `/api/fetcher-health` 与 `/api/data-source`（GET）**由它取代**；保留一版兼容别名或直接删（两者都只被本仓前端使用）。

### D3 · 抓取单入口：`/api/sync` 内部按能力 + 策略分派 ⭐

这是 **UI 一致的核心**：

|         | 现状                                                                      | 设计后                                                              |
| ------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 前端按钮    | 「同步数据」+「全量重建」+「实时更新」三选一                                                 | **只有「同步数据」一个**                                                   |
| 后端行为    | `POST /api/sync` 按 `mode` 分派；`/api/fetcher-trigger` 绕过 mode 只走 Analyzer | `/api/sync` **既读状态也触发**：Analyzer 可达 → 中继抓；不可达 → 本地 `collector` 抓 |
| 增量/全量   | **前端传 `?full=1`**                                                       | **后端策略决定**（Q3），`?full=1` 降为隐藏 override                           |
| 前端需要知道的 | 谁在抓、走哪条路、增量还是全量                                                         | **什么都不需要知道**（响应里带 `plan.reason` 一句话解释）                           |

`/api/fetcher-trigger` 降级为 `/api/sync?mode=full` 的别名（或直接退役）。

> **实测（2026-09-26）**：见 §0 更正 —— **骨架与回退逻辑都已存在**，D3 的工作量 = 把 `POST /api/sync` 的 `mode` 判据换成 `probe` + 把 `/api/fetcher-trigger` 的增量/回退分支搬进来。

### D4 · 能力门控取代模式分支

所有 Analyzer-only 入口（图片批量下载 / Excel / 完整性自检 / 分析页 / 备注 / ⑧⑨⑩⑪ 测试入口）统一挂 `applyCapabilities()`：**不可用 → 置灰 + 统一提示**。后端对应端点加前置检查，不可用时返回 `409 {"ok":false,"error":"not_supported","reason":...}`（**不再 502/转发失败**，语义清晰）。

### D5 · 凭证归属显性化

`capabilities` 带 `sessdata: {owner, state}`：

| 形态 | owner                   | 前端一句话                 |
| -- | ----------------------- | --------------------- |
| 组合 | `Analyzer(config.yaml)` | 「凭证由 Analyzer 持有（有效）」 |
| 独立 | `finder(config.json)`   | 「凭证由本机持有（需更新 / 有效）」   |

用户不再需要理解"为什么有两个配置文件、哪个生效"。

### D6 · ⭐ 策略层：`decide_sync_plan(probe, policy)`（Q1 + Q3 的落点）

**一个纯函数，一张规则表，一个可扩展的配置结构。**

```python
def decide_sync_plan(probe, policy, state) -> {"mode": "full|incremental|skip|blocked",
                                              "reason": "...", "owner": "analyzer|finder"}
```

| 规则（自上而下，命中即止）          | 触发条件                                | 产出                         |
| ---------------------- | ----------------------------------- | -------------------------- |
| R1 首次建基线               | 本地 `last_success_at` 缺失 / 库为空       | `full` ·「首次建基线」            |
| R2 缺基线自动升级（**现有逻辑搬入**） | 上次增量返回「未找到本地历史记录」                   | `full` ·「缺基线，自动升级为全量」      |
| R3 长尾缺口修复              | 距上次全量 > N 天 **且** 增量缺口 > M 条        | `full` ·「修复长尾缺口」           |
| R4 防连点（新增）             | 距上次全量 < cooldown（如 10 min）          | `skip` ·「刚刚跑过，冷却中」         |
| R5 凭证闸门（**Q1 新增**）     | `prefer=local` 且 Finder SESSDATA 无效 | `blocked` ·「需要有效 SESSDATA」 |
| R6 默认                  | —                                   | `incremental` ·「常规增量」      |


**配置结构升级**（`data/source_config.json`，**必须兼容旧文件**）：

```json
{
  "policy": { "prefer": "auto", "sync": "auto", "rules": { "full_cooldown_min": 10 } },
  "analyzer_db": "D:\\Program Files (x86)\\BilibiliHistoryAnalyzer\\output\\bilibili_history.db"
}
```

- `prefer`: `auto | local`（**`analyzer` 删除**；两项**都在界面上可见**，以「策略」名义呈现）→ **Q1 的"需要"**。
- `sync`: `auto | full | incremental`（`full`/`incremental` 即原 `?full=1` 的隐藏 override）。
- `rules`: **预留扩展位** → **Q1 的"后续增加具体策略"就是往这里加字段 + 往 R 表加一行**。

**两条纪律（避免"自己做策略"变成黑箱）**：

1. **可解释** —— 每次同步的响应都带 `plan: {mode, reason}`，前端原样显示成一句话（"本次：增量（常规增量）"）。
2. **可覆盖** —— 隐藏 override 永远存在（`?full=1`、`?force=local`），只是不进 UI。

### D7 · Q2 的落地方式：置灰 → 隐藏做成"单点常量"

`applyCapabilities()` **从第一天就表驱动**，否则"先灰后隐"会变成二次重写：

```js
const UNAVAILABLE_MODE = 'gray';        // 日后改 'hide' 即完成迁移（一行）
const CAP_DOM = {                        // 能力 → DOM 清单（唯一映射表）
  images:    ['#anImgStartBtn'],
  integrity: ['#selfCheckBtn'],
  export:    ['#anExportBtn'],
  analysis:  ['.tab-analysis', '#anRealtimeBtn'],
  // ...
};
```

同一功能只有一套 DOM；`gray` / `hide` 只改 `classList` 与 `hidden` 的差别。**迁移成本 = 1 行。**

## 4. ⭐ 与「单 Finder 切换」（`方案-Finder轻量化.md` §7）的关系

做完"连接即模式"，**§7 那条不可逆的切换路径可以被替代**：

| 维度    | §7 拆中继方案        | 连接即模式（本方案）                     |
| ----- | --------------- | ------------------------------ |
| 中继代码  | **删除**（≈500 行）  | **保留**，`available=false` 时不被调用 |
| 模式切换  | 手工拆/装 → **不可逆** | 关掉 Analyzer 即自动独立 → **可逆、零成本** |
| 实施顺序  | 5 步，第 5 步无退路    | 5 步，每步可独立回退                    |
| 数据深度  | 需先做一次性迁移（P2）    | **同**（P2 仍需要，与形态无关）            |
| 代码量收益 | ≈ −360 行        | ≈ +180 行（保留中继）                 |
| 风险    | 中高（拆完无退路）       | **低**（纯增为主）                    |

**建议：先做本方案，再决定要不要真删中继**（= 你 Q4 的选择）。理由：

1. 它把"要不要切形态"从**一次性决策**变成**运行时事实** —— 你可以先让它共存，观察真实使用中到底哪种形态更常用；
2. 若日后确认"我再也不需要 Analyzer"，那时再删中继，**删起来更安全**（因为已经有能力层做门控，删完后端行为不变）；
3. 轻量化核算早已证明：**收益是"形态"而非"代码量"**，所以"保留中继"不构成损失。

## 6. 实施顺序

> **六个阶段**，粒度是「一段连续的改动」，不是单笔编辑。排序只有一条判据：**停下时系统必须可用**。
> 阶段内部的行级顺序若需要，开工时逐阶段展开即可。

### 6.1 阶段总览

```
阶段 0  前置：备份 / 凭证 / 数据迁移        ← 迁移有时限，可与阶段 1 并行
        ↓
阶段 1  新增三层 + 只读端点（纯增，零行为变更）   ← 可随时停
        ↓
阶段 2  切换抓取判据  ★ 唯一改核心路径      ← 必须单独提交
        ↓
阶段 3  后端门控（不可用 → 409）
        ↓
阶段 4  前端切到能力渲染
        ↓
阶段 5  收敛（退役旧端点 / 三入口合一）
        ↓
阶段 6  收尾：置灰 → 隐藏（可选，等 UI 轮）
```

### 6.2 六个阶段

**阶段 0 · 前置（不打代码，可并行）**
备份 `data/`；更新 Finder 侧凭证（现 -101）；把 Analyzer 主库 4048 条**一次性导入本地库**。
为什么在最前：导入是**唯一有时限**的动作 —— 一旦独立形态可用而本地库还没长尾，B 站只保留近三个月，2020–2024 那批就永久失去回补机会。
完成标志：本地库与合并条数都含长尾年份。

**阶段 1 · 新增三层 + 只读端点（纯增）**
探测层（唯一做网络 IO）＋ 能力层（纯函数，回答"能不能"）＋ 策略层（纯函数，回答"增量还是全量"）＋ 一个只读端点 `/api/capabilities`；**旧端点与旧按钮一行不动**。
为什么排第一：**生产行为零变更**，做完就能用浏览器直开新端点看见设计全貌 —— 风险最低、收益最可见的一步。
完成标志：新端点返回 8 项能力 + 连接事实；三个旧按钮行为与之前完全一致。

**阶段 2 · 切换抓取判据（★ 唯一改核心路径）**
抓取入口的判据由「读手切模式」换成「读探测 + 策略」；同时把原本散在另一个触发端点里的「增量失败 → 自动升级全量」**合并进来**；手切的增量/全量降为隐藏覆盖。
为什么单独一步：它**没有旁路**，一出问题就是抓取坏掉 —— 必须独立提交、独立回退。
完成标志：开关 Analyzer 两种状态下各点一次「同步数据」都正确；⑥ 重启链回归不受影响。

**阶段 3 · 后端门控**
Analyzer 专属端点加能力前置检查，不可用时返 **409 不支持**（而不是现在的转发失败 502）。
为什么在阶段 2 之后：阶段 2 已消化掉最常见的失败入口（抓取），门控清单因此更短。

**阶段 4 · 前端切到能力渲染**
轮询改读新端点；横幅由 6 个分支收敛为 2 个；设置面板的「模式三选一」改为**策略区**（见 §7 Q1：选项保留，但以「策略」名义、只留"跟随连接 / 始终用本地库"两项）；测试入口挂统一门控；「全量重建」收进隐藏覆盖。
为什么必须等阶段 1–3：要消费的端点得先存在。
完成标志：**关掉 Analyzer → 界面自动变独立形态，且没有任何"点了必失败"的入口。**

**阶段 5 · 收敛**
退役被取代的两个旧端点；删掉重复的第三个抓取入口 → **界面上只剩一个「同步数据」**。
为什么放最后：**任何"删"都必须晚于其消费方的"改"**。
⚠️ 最易错序的一处：后端收紧手切端点（不再接受三态）必须**晚于**前端设置面板改造 —— 否则前端仍在提交三态值 → 被拒 → 用户直接看到「切换失败」。

**阶段 6 · 收尾（可选，等 UI 轮）**
不可用入口从「置灰 + 提示」改为「隐藏」——**只改一个常量**（见 D7）。

### 6.3 四条排序约束（不可交换）

1. **后端先"提供" → 前端再"切换" → 旧端点最后"退役"**（expand → migrate → contract）。
2. **新端点首版"超集兼容"旧消费方** —— 带上旧端点的字段，让前端切换那一步不必再动下游函数。
3. **抽函数先于改调用点**（否则两个调用点之间会出现半成品状态）。
4. **API 语义变更必须晚于其消费方改造**。

### 6.4 提交与回退

每阶段一个提交，**只有阶段 2 必须单独提交**（唯一改动核心抓取路径，出问题整步 `git revert`）。
阶段 1 与阶段 4 内部若想更细，**在"纯增"处可任意切开** —— 每一步都向后兼容，停下不影响运行。

### 6.5 待你定：单 Finder 的**功能补齐**（§4.1 的 D，≈140 行）放在哪个阶段

现状：这部分工作**没有**被编进阶段表（阶段 1 只含三层架构，阶段 2 只含切换判据）。三种放法：

| # | 放法                       | 优点                                 | 代价                             |
| - | ------------------------ | ---------------------------------- | ------------------------------ |
| ① | **并入阶段 1 的后半**（阶段 1 = 三层架构 ＋ 本地能力补齐） | 同为纯增，一个提交边界；阶段 2 前功能已齐             | 阶段 1 由 ≈+180 胀到 ≈+320 行，"可随时停"的粒度变粗 |
| ② | **独立成一阶段（插在阶段 1 与阶段 2 之间）** | 语义清晰（架构层 / 本地能力 各一段）；可单独暂停、单独回退 | 多一个提交边界                        |
| ③ | **不动阶段表，作并行支线**          | 不阻塞主链（阶段 1 / 2 可先跑）                | 要与阶段 2 抢时间；D 未齐前形态"半可用"        |

**建议 ②** —— 它与阶段 1 同为纯增、可并行，但**语义上是两件事**（一个回答"系统知不知道能不能"，一个回答"本地那部分功能有没有"），混在一起以后回看会分不清。若你偏好"阶段数越少越好"则选 ①；若你打算"先把架构搭起来看看，本地能力晚点补"则选 ③（但要接受阶段 2 后一段时间内形态半可用）。
