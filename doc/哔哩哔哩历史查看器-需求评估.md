# B站历史记录查看器 — 需求评估

> 文档状态：评估稿（Phase 1 已实现并验证；实测结果见《哔哩哔哩历史查看器-原型方案.md》§8）
> 日期：2026-07-22
> 说明：此前生成的采集脚本已搁置，本评估从零出发。

## 1. 背景与问题陈述
- B站观看历史为「账号级、服务端同步」，手机 App 与网页端共用同一份历史池。
- 官方限制：实际仅保留最近约 **1000 条**记录，且**条目上限优先于时间上限**——刷得勤时往往 1–2 周就顶掉最早的记录。官方不提供导出、不提供恢复。
- 用户痛点：
  1. 计划观看的视频（加入「稍后再看」或只是看过没看完）会被漏掉；
  2. 记录一旦被上限挤掉，B站端无法再查到。
- 本文目标：把需求结构化；原型可行性见《哔哩哔哩历史查看器-原型方案.md》。

## 2. 目标（Goal）
构建一个**本地优先**的 B站历史查看器：
- 永久留存账号全部观看历史（突破官方上限）；
- 以接近 B站网页端历史页的版式展示；
- 支持搜索与简单筛选；
- 支持一个**可扩展**的「需要观看」筛选，从**完整历史**中直接找出"潜在还需看"的视频（不依赖是否加入稍后再看）。

## 3. 功能需求（FR）
- **FR1 数据留存**：定时从账号拉取全量历史，本地永久存储；增量更新、按唯一键去重。手机与电脑观看均覆盖（账号同步）。
- **FR2 展示（类网页端）**：列表/卡片式布局，每条展示：封面、标题、UP主、观看时间、视频号(BV)；整体观感尽量接近 B站网页端历史页。
- **FR3 搜索**：按标题 / UP主 / BV号 / 关键词检索，实时过滤。
- **FR4 简单筛选**：按时间范围、按内容类型（视频 / 直播 / 专栏）等。
- **FR5 特殊筛选「需要观看」**：规则 = 观看进度 < 95%（即"开始看但没看完"的视频）；该筛选应做成**可扩展规则**，后续可加更多条件（如按 UP主、标签、时长等）。
- **FR6（可选）自动化**：每日或开机自动同步；SESSDATA 失效可提示重新获取。

## 4. 数据需求与接口
- **数据源**：`https://api.bilibili.com/x/web-interface/history/cursor`，GET，Cookie 携带 `SESSDATA` 认证。
- **分页**：用返回 `data.cursor` 的 `max` / `view_at` / `business` 作为下一页游标；`ps` 最大 30。**注意**：`business` 参数不接受 `"all"`（实测返回空列表），应省略或传具体类型（archive/pgc/live/article），跟随 cursor 返回的 business 翻页。
- **可获取字段（每条）**：
  - `kid`（历史记录唯一键，去重用）
  - `title` / `show_title`（标题）
  - `author_name`（UP主）
  - `view_at`（观看时间，Unix 时间戳）
  - `history.bvid`（视频号 BV）
  - `history.oid`（稿件 / 番剧 / 文章 ID）
  - `history.business`（类型：archive 视频 / pgc 番剧 / live 直播 / article 专栏）
  - `cover` / `covers[0]`（封面）
  - `progress`（已观看秒数）
  - `uri`（跳转链接）
- **时长字段（2026-07-22 实测澄清）**：历史接口**实际直接返回 `duration`（视频总时长）**，1207/1207 条有值；因此 `progress < 95%` 可直接由 `progress/duration` 计算，**无需补充获取时长**（详见原型方案文档 §8.3 / §8.4）。原"不返回时长"的判断已被推翻。

## 5. 关键澄清 / 开放问题（需用户确认）
1. **「观看时间 < 95%」的确切含义**：当前理解为"观看进度 / 已看比例 < 95%"，即没看完。→ **已用真实数据验证**（progress/duration 比例可算，样本合理），确认该口径（详见原型方案 §8.4）。
2. **时长获取策略**：为算百分比，是否接受对每个候选视频额外请求一次时长接口（可接受一定耗时 / 限流），还是 MVP 先用"已看秒数 > 0 且不足某阈值"近似。→ **已解决**：历史接口实测直接返回 `duration`，无需补取（详见原型方案 §8.3）。
3. **登录态**：SESSDATA 会过期，是否接受"失效时手动重新填入配置"作为 MVP 方案。
4. **「需要观看」规则扩展形式**：后续规则希望以何种方式配置（代码规则 / 配置文件 / UI 勾选）。

## 6. 现成方案评估（含对 piliplus 的修正）
| 方案 | 突破上限留存 | 网页同款 UI + 全字段 | 搜索 | 简单筛选 | 「需要观看」(进度<95%, 基于全历史) | 结论 |
|---|---|---|---|---|---|---|
| piliplus（已装，Windows 版） | ❌ 仅镜像官方历史 | ✅ 类客户端观看记录 UI | ✅ | ⚠️ 按时间 | ❌ 其「未看完」只在「稍后再看」列表内，无法对全历史分析 | 不满足 FR1 / FR5 |
| Bilibili 无限历史记录（浏览器扩展） | ✅ 本地永久 | ⚠️ 自有页(非同款)但字段齐 | ✅ 关键词 | ⚠️ 按时间轴 | ❌ 无内置进度筛选（有 `progress` 字段可二开） | 最接近 FR1 / FR3 |
| Bilibili-Evolved（增强脚本） | ❌ | ❌ | ❌ | ❌ | ❌ | 不匹配 |
| 自研（本方案） | ✅ | ✅（目标） | ✅ | ✅ | ✅（可扩展） | 唯一可完全满足 |

**关于 piliplus 的修正说明**：此前认为其「稍后再看 · 未看完」可近似"需要观看"，这是错误的——该分类**仅在用户主动加入「稍后再看」的列表内有效**，无法对完整历史做分析来发现"看过但没看完"的潜在需看视频。因此 piliplus 不能替代 FR5，也不突破官方上限，单独使用无法解决核心痛点。
