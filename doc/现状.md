**抓取判据与策略层（现行）**

- `POST /api/sync` 的判据**不再是手切 `mode`**，而是 `probe_connection()`（`server.py`，全项目唯一做网络 IO 的地方）→ `store.decide_sync_plan(probe, policy, state)`（`store.py`，纯函数规则表 `R1`–`R6`）。
- 规则表产出 `{mode: full|incremental|skip|blocked, reason, owner}`：`owner=analyzer` 走中继转发，`owner=finder` 走本机 `collector.py`。其中 **`R5` 是前置安全闸门**：`owner=finder` 且自有凭证不可用 → `blocked`，不发任何请求。
- **`policy` 的现状（勿按"已落盘"读）**：`store.load_policy()` 会从 `data/source_config.json` 里读 `policy` 段，但**当前没有任何生产写方** —— `store.save_policy()` 只在单测里被调用 → 实测该文件恒为 `{"mode": …, "analyzer_db": …}`，**`policy` 段永远不会出现**，读取时一律回落 `POLICY_DEFAULT`：`{"prefer": "auto", "sync": "auto", "rules": {"full_cooldown_min": 10, "full_interval_days": 7, "gap_threshold_days": 30}}`。策略段真正落盘属**阶段 5** 形态。
- 另有**隐藏 override**（`policy.sync = full|incremental`）：不进 UI、不落盘，只在内存储存里被 `decide_sync_plan()` 读到 —— `POST /api/sync?full=1` 就是走它（前端「强制全量重建」按钮，**阶段 4 起收进设置里的隐藏覆盖区**）。旧文件里的 `mode` 三态仍可被 `store.normalize_policy()` 兼容读取。
- **`mode` 已是二态（`auto` / `local`）** —— 手切值 `analyzer` 已删除（见上表注）；设置面板**不再有手切控件**，只读展示「当前形态（`#srcModeBox`）」。
- `GET /api/capabilities` 返回三样东西：**能力表**（`fetch`/`sync`/`remark`/`export`/`images`/`integrity`/`backup`，逐项 `{available, owner, reason}`）＋ **连接事实** ＋ **本次同步计划预览** `plan{mode, reason}`。**阶段 4 起前端已改为轮询它**（`refreshSourceHealth()` / `loadSourceCfg()`）；旧端点 `/api/fetcher-health` 与 `GET /api/data-source` 降为兼容别名（退役属阶段 5）。

### 2.4 合并与折叠规则

- **合并键**：`(bvid, view_at)`（`_rec_key`）。初版误用 `kid` 合并（Analyzer `kid` 恒 0、Finder `kid`=oid）曾产生大量重复，**任何新增备份源必须先对齐主键**。
- **冲突解决**：`kid` 相同时 **Analyzer 优先**。
- **折叠（Plan B「折叠显示 + 状态聚合」）**：同一 `bvid` 的多次观看会话在展示层折为一条。

| 字段 | 聚合规则 |
| --- | --- |
| 展示字段（标题 / 封面 / 作者 / uri…） | 取 `view_at` 最大的一条（对齐 B站官网「最近一次观看」） |
| `progress` | **任一会话 `== -1` → `-1`**；否则取 `max` |
| `duration` | `max`（防御性） |
| `session_count` / `first_view_at` / `kids` | 会话数 / 最早观看 / 全部会话 kid（新字段） |
| 无 `bvid` 记录（live / article / pgc） | **不折叠**，原样保留 |
| 记录自身 `kid` | 仍为「最近一次」的 kid |

- `classify_record` 支持 **`kids` 多键命中**：`manual_skip / auto_exempt / archived` 命中**任一**会话即生效 → 同一视频重看产生新 `view_at` 后，既有跳过状态不会静默失效。
- `remark` 是 Analyzer 的**按会话**字段（`(bvid,view_at)` 定位），折叠后展示「最近一次会话」的备注 —— 属折叠的固有语义，非缺陷。
- **auto 模式何时跳过读主源（阶段 2 修正）**：`load_raw_records()` 只在**三条同时成立**时跳过 Analyzer 年表 —— ① 最近一次探测结论是「不可达」；② 该结论未过期（`ANALYZER_PROBE_TTL` = 300 秒）；③ **主源库文件的 mtime 不比本地库新**。任一条不成立都照读（**正确性优先于省一次 UNION**）。
  - 判据是「**文件**能不能读」而不是「**服务**能不能连」：读文件不需要 Analyzer 在线；迁移之后若 Analyzer 又写过主源（mtime 更新），它就可能含本地库没有的记录 / 备注，此时必须照读。
  - ⚠️ 「迁移后本地库 ⊇ Analyzer 记录、合并结果不变」只是**迁移那一刻**的时点事实，**不是不变量**（运行期没有任何把 Analyzer 新数据回灌本地库的机制）。

## 5. 统一数据契约（canonical schema）

**结论：统一「逻辑数据契约」，不强求「物理数据库引擎」。**

- **权威层 `raw`**：完整 `cursor` 响应 JSON 原样存储，`key = (bvid|oid)@view_at`（与 §2.4 的 `(bvid, view_at)` 是**同一个键的两种写法** —— 上游 JSON 用 `@` 串接、canonical 用二元组），永不丢字段。
- **派生层 `derived`**：规则引擎所需规范化字段集 ——
  `business` / `progress` / `duration` / `view_at` / `title` / `author_name` / `author_mid` / `bvid` / `uri` / `cover` / `kid` / `dt` / `live_status` + 派生 `progress_pct` / `view_at_age_days` / `skip_state`。
- 规则引擎与 UI **只面向 canonical `derived` 开发一次**；各数据源通过 storage adapter 映射进 canonical 形式。
- **实测校准**：canonical `derived` 以 Analyzer 34 列为基准；Finder 的 `raw_json` 仅 23 键（缺 `business/oid/bvid/cid/page/part/dt/main_category/remark`），**不是真·原始响应权威层**。

## 6. 规则引擎核心

- **输入**：canonical `derived`。`progress == -1` 表示已看完 → `progress_pct = 1.0`；`view_at_age_days = (now − view_at) / 86400`。
- **`rules.json` 结构**：**单 `active` 规则**（同一时刻仅一条，`server.POST /api/rules` 强制校验 C6）+ 多 `groups`（`match:"any"` = OR 语义，命中任一分组即按该分组 `action` 处理）。
- **求值算法**：`eval_condition`（单条件）→ `eval_group`（分组内 AND）→ `evaluate_rule`（返回 `(action,label)` 或 `None`；`progress == -1` 短路返回 `None`；**首命中优先**）。
- **四个互斥分类桶**（不变式 `finished + auto_skip + stale + needs == total`；`/api/query` 的 `counts` 即由这四桶 ＋ `total` 组成，**前端 tab 与桶的映射见 §8.1**）：

| 桶 | 含义 |
| --- | --- |
| `finished` | 已看完（`progress = -1`） |
| `auto_skip` | 命中 auto_skip 分组 |
| `stale` | 命中 stale 分组（久未观看） |
| `needs` | 未完成且未被跳过（待观看） |

- **跳过状态与优先级**：`manual_skip`（人工）> `auto_exempt`（取消自动跳）> `auto_skip`（引擎）。`needs` 有隐含 **95% 门**（`progress_pct ≥ 0.95` 归入 `auto_skip` 而非 `needs`）。
- **冲突校验 `validate_rule`**：返回 `{hard, soft, info}` —— C1 重复条件 / C2 互斥 action / C3 无效字段；C6 多 active 由 server 强制。
- **增量感知 `dirty_count`**：以 `rules_hash` 比对「已应用哈希」与当前规则，统计上次应用以来新增未套用条数；`rules_status()` 返回 `pending + dirty_count`。
- **默认规则**：5 分组（接近看完 / 误触 / 短视频碎片 / 直播回放 / 陈旧）；default 下 `auto_skip` 多为短视频碎片（`duration < 60`），`needs` 多为低进度长视频。
- `stale` 默认恒为 0 —— 由默认规则「首命中优先」+ 陈旧分组排最后导致（老视频先被短视频碎片命中），**非缺陷**，可调 `rules.json` 顺序让 stale 生效。

### 7.1.1 阶段 3 · 409 能力门控（已落地）

Analyzer-only 的端点在**确定不可用**时返 **409**（而非转发失败 502），响应体
`{ok:false, error, reason, capability, available:false, owner:null}` —— 字段对齐能力表 7 项，
前端阶段 4 认 `capability` 即可统一置灰（**T10** 的落点）。

| 端点 | `capability` |
| --- | --- |
| `/api/fetcher-trigger` | `fetch` |
| `/api/fetcher-check` | `integrity` |
| `/api/export/db` · `/api/export/excel/{fn}` · `/api/export/excel` | `export` |
| `/api/remark` | `remark` |
| `/api/images/{start,stop,clear}` | `images` |

**四条设计约束（改这块前必读）**：

1. **滞回（抗抖动）**：**连续 2 次**探测失败才拦（`ANALYZER_GATE_STREAK`），单次失败只放行。
   依据：启动中 / GC 停顿 / 5s 超时擦边 / 风控回包都会产生假阴性，单次失败不足以定性。
2. **恢复不对称**：**1 次成功立刻解封**（`streak` 归零），不等 TTL —— Analyzer 一起来就自动恢复。
3. **记账权只归「不被门控」的探测通路**：`/api/fetcher-health`（`_health_payload()`）与
   `probe_connection()`（`/api/capabilities` · `/api/sync`）—— 两者看的是**同一个 `/health`
   观测**。因为门控在**入口**拦截，被拦路径上的端点**永远不会被调用**、也就无法清零 streak →
   在那里记账会**死锁**；上面两条通路不被门控且前端每 `SRC_POLL_MS` 必轮询 → 解封只需一轮。
   附带一条易踩的坑：记账判据是**业务级** `ok and reachable`，**不能**用 `_forward_fetcher`
   的 `reachable` —— 后者把 **HTTP 502 也算 reachable**（传输层语义）。两条通路必须用**同一判据**，
   否则业务级攒起的 streak 会被传输层判据清零、门控永不触发（2026-10-03 审查 ①）。
4. **`analyzer.ok` = Analyzer 可用性的唯一判据（业务级）** —— 能力层 `derive_capabilities()`、
   策略层 `_plan_owner()`、409 门控**三处共用**；`reachable` 只表示传输层可达，仅留给 §2.4
   「跳过读主源」与旧端点超集兼容用。判据若不统一，会出现「能力表说可用、端点却返 409」
   （2026-10-03 审查 ②）。

**绝不 fail-closed**：从未探测 / 记账过期（> `ANALYZER_PROBE_TTL` 300s）→ 一律**放行**，
行为与阶段 3 之前完全一致（转发失败 → 502）。宁可让用户看到 502，也不被陈旧结论永久挡住。

> `/api/fetcher-health` **自身不门控** —— 它是真相来源，门控它会导致「Analyzer 挂了 → 连
> 『检查 Analyzer 是否挂了』都查不到」的死锁，前端横幅就失去依据。

#### 阶段 4 第三笔：`fetch` 语义裁定 → `CAP_DOM` 拆为**两维**（2026-10-03）

**裁定（用户）**：**「Finder 自己能抓」** —— 独立形态下 `fetch.available=true, owner="finder"` 这个结论**是对的**，错的是把它挂到 Analyzer 的中继按钮上。

**原缺陷**（第四轮审查 §七.1）：`fetch` 能力与 `CAP_DOM.fetch` 语义不等价 → 独立形态下能力表说「可以抓」、`#anRealtimeBtn` 却打的是 Analyzer-only 的 `/api/fetcher-trigger` → **必 409**（「亮着、点了必失败一次才置灰」）。

**修法**：拆成两维，各用各的判据 ——

| 维度 | 表 | 判据 | 回答的问题 |
| --- | --- | --- | --- |
| 能力 | `CAP_DOM`（7 键） | `caps[cap].available` | **这件事**能不能做 |
| 端点归属 | **`ANALYZER_ONLY_DOM`** ＝ `#anRealtimeBtn`/`#anFullBtn` | **`connection.analyzer.ok`（业务级）** | **这个按钮的端点**在不在 Analyzer 上 |

`applyCapabilities(caps, analyzerOk)` 现在**收两个判据**。⚠️ **端点维度绝不能用 `caps.fetch.available`** —— 那正是缺陷本身；`CAP_HINT` 也删掉了 `fetch` 条（它已无 DOM 消费，留着会误导）。

**自动化护栏**：`dev/test_capabilities.py` 新增 **`T2.8`（29 项）＋ `T2.9`（20 项）** —— 逐个校验 `CAP_DOM` 选择器在真实 DOM/样式里存在、`.cap-disabled` 已定义、本地导出按钮存在且**不在** `CAP_DOM`、两个历史坏选择器（`#selfCheckBtn` / `.tab-analysis`）不得复现，并守护 `plan_mode` 的 `skip` / `blocked` 分开渲染与横幅 `sig` 含原因全文。
**第三笔新增 8 条**：`CAP_DOM.fetch`/`sync`/`backup` **必须是空集** · `ANALYZER_ONLY_DOM` **必须恰是那两个按钮** · 两者**不得同时出现在 `CAP_DOM`**（防两维混淆）· `applyCapabilities` **必须收 `analyzerOk` 参数** · 端点维度判据**不得写成 `caps.fetch`**。**已做负向验证**：把两按钮塞回 `CAP_DOM.fetch` → **3 条 FAIL**，恢复后 275 全绿。**`T2.9` 是 `#39` 的护栏**：值域只剩二态 ＋ 遗留值折算 ＋ `set_source_mode` 行为 ＋ **`_pick_sources` 无 analyzer 分支** ＋ auto 两种输入的 `effective` 断言。

## 9. 备份与保留策略

- **端点**：`POST /api/backup` 用 `sqlite3` 在线 `backup()` 对 Analyzer 主源（`ANALYZER_DB`）+ 本地库做快照 → `data/backup/<时间戳>/` + `meta.json`；`GET /api/backups` 列表。
- **策略文件** `data/backup_policy.json`：`{auto: true, delta_threshold: 200, keep: 5}`（**手改**，无写入端点；**文件不存在时即用这组内置默认**）。
- **自动路径**：仅在 ②③ 与 `/api/sync` **拉取成功后**（`_after_data_pull`）检查「自上次备份以来新增条数 ≥ 阈值」；**首次（无备份基线）不触发**，由用户手点 ⑤ 建立基线。
- **手动路径**不受阈值限制，但**同样受 `keep` 约束**（`/api/backup` 后补一次 `_prune_backups`，并把 `pruned` 回传）。
- **定位**：Analyzer 宕机 / 库损坏 / 库被删时，Finder 仍有可浏览的本地一致副本，**不污染主源**。

## 10. 硬约束与原则

1. **源库全程只读**（`file:...?mode=ro`），绝不 INSERT / UPDATE / DELETE 源记录。
2. **唯一可写库 = `canonical_state.db`**（分类 / 视图 / 名单 / 批量），与源库物理隔离。
3. **只监听本机回环**（`127.0.0.1` / `::1`），不提供对外服务。
4. **默认形态下 Finder 不持凭证、不自抓**：抓取由 Analyzer 执行。**独立形态**（Analyzer 不可用）下由 `collector.py` 自抓 —— 依赖自有 SESSDATA，**已于 2026-10-03 更新为有效值**（原 `-101` 失效问题已消除）。两份副本（Analyzer `config.yaml` 与 Finder `config.json`）**各自独立**，更新其一不会同步另一；一旦失效，默认形态下会被 `/api/fetcher-health` 的 `unknown` **静默**（不弹错）→ 排查口径见 §11 与 `方案.md` §6 的 `O4`。
5. **当前阶段作业约束**（验证 / 重构期间）：不启动对外服务；不对历史数据做拉取 / 更新类操作。
6. **验证手段**：① 只读端点实测 ② 进程内调用 + 隔离目录 ③ `dev/` 自动回归脚本 ④ 现场实测 ⑤ 整进程隔离副本验收（`dev/verify_riskfix.py`）。**当前 `dev/` 四个回归脚本全绿**（2026-10-03 复跑）：`test_capabilities` **275 项**（默认零 IO；`--live` 另打本机 8765 则为 **305 项**）· `regression_fallback` **7/7**（含 `/api/sync` 回退组 ＋ A1 缺基线标记组）· `regression_restart` 全部通过 · `verify_riskfix` **97/97**（含阶段 3 门控组 G-P/G-E），均零污染。

## 10.1 数据质量：长尾 `duration` 缺失（2026-10-03 实测）

**这是「很多视频看完了却仍在需要观看」的主要成因之一**，处置方案见 [`待办.md`](待办.md) `#40`。

Analyzer 主源年表的 `duration` 缺失是**结构性**的（本地库 4512 行里缺 462 条 ＝ 10.2%）：

| 年表 | 条数 | `duration` 缺失 | `progress` 分布 |
| --- | --- | --- | --- |
| 2020–2025（六个表） | 363 | **100%** | **全 0，无一条 `-1`** |
| 2026 | 3685 | 95（2.6%） | `-1`×1953 / `0`×452 / `>0`×1262 |

⇒ **2020–2025 那批是「降级态导入」**（`duration`/`current`/`total` 整列全 0/空），**不是「时长恰好为 0」**。连带的：那批数据**永远不可能被判 `finished`**（`engine.py` 只认 `progress == -1`）。

**三处不可行的补全途径（已实测排除）**：① `raw_json` 里没有 `duration`（连有值的记录也没有）；② 重抓取不到（B站接口只保留近三个月，历史条目在接口侧已不存在）；③ 把 `progress == 0` 一律当看完会**废掉 `误触-短暂观看` 与 `短视频碎片` 两条规则**。

**当前受影响的判据**：`store.py` 的 95% 判据 ＋ `engine.py` 的 `接近看完`/`误触-短暂观看`/`短视频碎片` 三条规则，均因**缺分母**而在这批数据上无法判定。实测 `progress == 0` 的 847 个视频里，**393 个因 `duration` 缺失未被任何规则接住**。

> `business` 为 `live` / `article` 的记录**天然无 `duration`**（直播/专栏非普通视频）→ 2026 表那 95 条里 `live`×14 ＋ `article`×6 属**正常**，不必补。

**结论**：Finder 重复 Analyzer 的部分（抓取 / 存储 / 同步 / 完整性 / 查询）要么冗余、要么更弱；**真正独有**的价值在 **skip 规则引擎** + **views/lists 整理层** + **⑤ 轻量备份**。

### 与开源 Frontend 的差异

- Finder 多出**显式诊断 UI**（原 Frontend 无按钮）、**⑤ 备份**、**⑥ 应用变更**（原 Frontend 是 Tauri 桌面端，无「网页内控制后端进程」的需求）。

- 折叠行为**主动对齐 B站官网**（同一视频只显示最近一次），**不**对齐开源 Frontend（后者不折叠）。
