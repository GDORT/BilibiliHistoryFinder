## 二、问题 ①（阻断级）：`test_api_contract.py` 恒定失败，与文档「96 项」不符

**实测**（`python dev/test_api_contract.py`）：

```
结果：93 通过 / 3 失败
  x 含键 status           | 实际=['error','ok','reachable','sessdata','source']
  x ?sessdata=0 → sessdata 标 unknown（未探测） | got=None want='unknown'
  x reason 说明『未探测』（而非谎称已验证）      | reason=None
```

失败**全部集中在 P2 `GET /api/fetcher-health`**（`dev/test_api_contract.py:202-217`）。

**根因**：P2 断言假设 **Analyzer 可达**（`status` 是 Analyzer `/health` 原样透传字段；`sessdata` 期望走「可达但本次不查凭证」分支），
而该用例跑在 `start_sandbox(fake_analyzer=False)` 起的**幽灵 Analyzer 沙箱**里 ——
`dev/test_api_contract.py:75` 把 `base_url` 写死为 `http://127.0.0.1:1`（**必然不可达**）。于是：

- 不可达 → `_health_payload()`（`src/server.py:1233-1257`）走降级体，**不产生 `status` 键** → `含键 status` 必失败；
- `?sessdata=0` 且不可达时，三个 `if/elif`（`server.py:1249-1257`）**全不命中** → 响应**连 `sessdata` 键都没有** → `sess2.get("state")` 恒为 `None`。

⇒ 这 3 条断言在该脚本**自己的沙箱内永远不可能通过**，是**恒定红**，不是环境偶发。

**性质判定**：这是**新版测试自身的设计缺陷**，且恰好踩中本仓《dev/README.md §三 · 7》自记的反模式
——「**断言里不能藏环境前提**」；脚本内注释还把分支写反了（注释称走 `server.py:1254-1256` 的「可达但未探测」，实际走的是不可达分支）。

> 关联附表（见问题 ⑦-b）：`/api/capabilities` 任何情况下都带 `status` 键（`server.py:1526`，值可为 `None`），
> 所以 P1 的同名断言 `for k in ("reachable","status","source","sessdata")`（`dev/test_api_contract.py:187`）**反而通过** ——
> 两个端点对「不可达态」的响应形状不一致，被这个测试同时暴露。

## 七、附带观察（非缺陷，供裁决）

### 7-a `engine.py` `#41` 守卫的覆盖面（设计取舍）

`src/engine.py:160-165` 的 `duration`「有值才判」守卫对**所有非 `exists`/`empty` 的算子**生效 ——
含 `!=` / `not_contains` / `not_in_list` 等**反向算子**：缺时长时统一返 `False`。

- 默认规则只用 `<`，**当前无误伤**；
- 但若日后写「`duration != 60`」类反向规则，缺时长记录会被**排除**而非保留 —— 属**语义取舍**，
  建议在规则文档中明示该边界（默认规则之外的算子组合未纳入护栏）。

### 7-b 两个端点对「不可达态」的响应形状不一致

- `GET /api/capabilities`：**恒带** `status`（`server.py:1526`，不可达时为 `None`）；
- `GET /api/fetcher-health`：**不可达时不含** `status`（降级体）。

二者在超集兼容期声明「顶层字段一致」，但不可达分支实际不同 —— 问题 ① 正是被这一点绊倒。
