## K1 · 🔴 B站改版 → overlay 失效（**唯一的长期高险**）

| 项 | 内容 |
| --- | --- |
| **风险** | B站历史页是 **Vue SPA**，DOM 结构与接口随时可能改版。overlay 依赖注入位置与选择器 ⇒ **改版即失效** |
| **证据** | 原设计 §3.3 与 `测试版评估文档` §7.1 均把「需跟 DOM」列为维护成本项（评分：维护 3/5） |
| **影响** | 不致命（脚本失效 ≠ 数据丢失），但**体验断崖**：角标消失、筛选栏错位 |

**应对**：
1. **选择器尽量用"稳定特征"**（如带语义的 class、aria 属性），**避免**依赖 `nth-child` / 深度嵌套路径；
2. **注入失败要优雅降级** —— 找不到宿主节点时**静默跳过**而不是报错刷屏（否则用户会以为脚本坏了）；
3. **加一条"自检"**：脚本能识别"我注入失败了吗"，并在自己的入口里提示（而不是无动于衷）；
4. **把变更面收敛**：overlay 只做「叠加」，不改动原 DOM 结构 ⇒ 改版时冲击面最小。

> ⚠️ **无法根治** —— 这是所有油猴脚本的共同宿命（同类脚本维护评分都不高）。
> **可接受**：因为失效时**数据仍在 IndexedDB**（不丢），且修复通常是改选择器级别的小改。

## K2 · 🔴 SPA 重渲染跟随

| 项 | 内容 |
| --- | --- |
| **风险** | 历史页翻页/筛选**不重新加载页面** ⇒ 只在 `document-start` 打标的话，**只有第一页有角标** |
| **证据** | 原设计 §3.3 明确要求 `MutationObserver` 跟随 SPA 重渲染 |
| **先例** | 同类脚本 `Bilibili 无限历史记录`（mundane799699）在**独立页**跑；历史页注入的多个脚本（如 Truazusa 的标记脚本）都需要处理此问题 |

**应对**：
1. `MutationObserver` 观察列表容器，**节点新增时补标**；
2. **必须做去抖**（debounce）—— SPA 一次翻页会触发大量 mutation，不打去抖会卡；
3. **幂等**：同一条记录被重复触发补标时**不能重复渲染**（用 `data-*` 标记已处理过）。

⚠️ **这条在流程 M4 已列为"最容易低估的点"**，建议**单独立一个验收项**：翻页 3 次后角标仍在。

## K3 · 🔴 引擎移植语义偏离（**最该担心的，但也最好解决**）

| 项 | 内容 |
| --- | --- |
| **风险** | JS 版与 Python 版**语义不等价** ⇒ 分类结果不同、用户看到的结果"不对" |
| **证据** | `engine.py` **542 行 / 16 个函数**，其中含**两处"反直觉"的实现**，移植时极易漏掉： |
| ① | **`#41` 守卫**：`eval_condition` 对 `duration` 有「**有值才判**」守卫 —— `cur is None or <= 0` 时**直接返 False**，且**刻意不拦** `exists`/`empty`。漏了 ⇒ `duration=0` 被误判「短视频碎片」（历史上误伤 435 条） |
| ② | **`#42` 分段排序**：`apply_sort` 是**分段**（有值段按方向排 ＋ 缺值段**永远**追加末尾），**不是** `sort(reverse=True)`。写成后者 ⇒ **降序时缺值跑到最前**（正是原 bug） |

⭐ **应对（硬解）：流程里的 M3 对拍**
- 用 `dev/test_engine.py` 的 **114 项**既有用例 **＋** `duration=0`/`NULL` 边界，
  **同一批数据**分别喂 Python 与 JS，**逐条比对** `view`/`skip_state`/`conflicts`/`dirty_count`/排序 kid 序列；
- 通过标准 **100% 一致**；
- ⭐ **且必须做负向验证**：故意改坏 JS 版一处（如拿掉 `#41` 守卫），对拍**必须报不一致**
  —— 否则说明对拍本身空转（这正是 A1 阶段 G5/G6 用过的办法，已被证明有效）。

> ⇒ **结论：K3 风险高，但可控度也最高** —— 因为 Python 侧已有 114 项单测 ＋ 两个行为锁，
> 对拍夹具**几乎不用新写**。

## K4 · 🟡 数据窗口天花板（**结构性，无解**）

| 项 | 内容 |
| --- | --- |
| **风险** | `history/cursor` **只回近三个月 / ≈1000 条**（先到者）⇒ 油猴**拿不到全量历史** |
| **证据** | `store.py:134` 实测记录「`history/cursor` 只回近三个月」；`测试版评估文档` §D 评「数据全量性 3/5」 |
| **影响** | 与 Finder（本地库 4198 条）相比，**油猴的数据面明显更窄** |

**这是结构性限制，无解**。应对（**降低预期落差**）：
1. 在脚本入口**明示**数据窗口（"当前可分析最近 N 条 / 三个月内"），避免用户以为是全量；
2. 提供**导出** ⇒ 让油猴抓到的数据**能回灌 Finder**（M6 的导出增强因此很有价值）；
3. 明确**两者定位不同**：Finder＝全量深历史；油猴＝日常随手。**不互相替代**。

> ⚠️ **用户已在 2026-08 评估时接受此项**（记录：「数据天花板锁定近期窗口（用户已接受）」）。

## K5 · 🟡 `fetch` hook 的可靠性

| 项 | 内容 |
| --- | --- |
| **风险** | ① 能否在 `@run-at document-start` 稳定装好 hook；② B站若给接口加**签名**（如 wbi）会不会影响"读响应" |
| **现状** | ⚠️ **未实测** —— 本项目无油猴代码，且 `src/` 与 `历史留档/archive/` 里**无 wbi/签名相关记录** |

**判断（有保留）**：
- **只读响应**通常比"构造请求"安全得多 —— 我们只是**看**页面自己发的请求返回了什么，
  **不自己伪造请求** ⇒ 签名机制的影响**可能有限**；
- 同类脚本（8 个里有 6 个跑在历史页）**都是 fetch hook 方案**，说明这条路**当下可行**。

**应对**：M0 阶段先把这当作**首要验证项**（流程 M0 的验收②就是它）。
⇒ **若 M0 就卡住，整个阶段需要重新评估** —— 所以 M0 必须**先做、单独验**，不要和 M1 混在一起。

## K6 · 🟡 双轨维护成本（Finder ＋ 油猴两套引擎）

| 项 | 内容 |
| --- | --- |
| **风险** | 引擎有两份实现（Python ＋ JS）⇒ 日后改规则语义要**改两处**，容易漏一边 |
| **影响** | 长期：两边行为漂移，用户困惑 |

**应对**：
1. ⭐ **M3 对拍就是这条的护栏** —— 只要对拍在 CI/回归里跑，漂移**会被立刻发现**；
2. **`rules.json` schema 共用** ⇒ 规则文件可互通，减少"两套规则"的心智负担；
3. **改引擎时的纪律**：先在 Python 侧改 ＋ 补单测，**再**同步 JS 侧，**最后**跑对拍 —— 顺序不能反。

## K7 · 🟢 风控额度

| 项 | 内容 |
| --- | --- |
| **风险** | 抓太多被限流（`-412`/`-509`/`-799`） |
| **证据** | `collector.py` 已有**完整的错误码分档表**（`fatal`/`backoff`/`retry`），是已验证的成熟认知 |

**应对**：**直接复用** `collector.py` 的 `API_CODE_TABLE` 分档逻辑，并遵守同一条铁律：
> **backoff（限流/风控）不能靠"重试"解决 —— 重试会加重风控，必须退避。**

⇒ **K7 是这 7 项里最好解决的**：现成的表 ＋ 现成的处置策略，不用重新踩。
