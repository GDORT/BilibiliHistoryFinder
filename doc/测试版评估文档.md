## 0. 背景与原需求

B站官方历史记录存在硬限制：**仅保留最近约 1000 条或约 3 个月（先到者），且滚动覆盖**；直播/专栏略久，短视频高频观看会加速覆盖。官方不提供导出或延长。

原始需求（续看场景）归纳如下：

1. 把「接近看完 / 误触短暂观看 / 短视频碎片 / 直播回放 / 陈旧久未看」等记录自动归类，减少干扰。
2. 提供多视图：**需要观看 / 已跳过 / 已搁置**，并支持手动标记与反悔。
3. 可自定义的**续看规则引擎**：条件分组（field/op/value）、单条激活、冲突校验。
4. 搜索、类型筛选、时间范围、封面展示等基础浏览能力。

当前原型（`src/server.py` + `src/web/` + `data/rules.json`）已实现上述 2–4，且自带采集层（`collector.py`）。

## 1. 当前哔哩哔哩机制事实（可行性边界）

### 1.1 历史接口

- 现行接口：`GET https://api.bilibili.com/x/web-interface/history/cursor`（cursor 式 IFS 无限滚动分页）。
- 关键参数：`max`（上一页末项 id）、`business`（业务类型）、`view_at`（时间戳）、`type`（all/archive/live/article）、`ps`（每页，最大 30）。
- 业务类型 `business`：`archive`（稿件）、`pgc`（番剧/影视）、`live`（直播）、`article`（专栏）、`article-list`（文集）。
- 认证：Cookie 中的 `SESSDATA`（必需，否则只能拿到未登录的空数据）。
- 旧接口 `/x/v2/history?pn=&ps=` 仍可用但分页语义较差。

### 1.2 不可突破的天花板（关键）

- **API 只能回滚到滚动窗口内（~1000 条 / ~3 个月）**。要拿到「全量历史」，唯一办法是**长期、周期性地用 SESSDATA 增量抓取并落库**——谁先抓到、谁就拥有数据。
- 这是 B站服务端机制决定的，与「用什么技术栈」无关。**任何不持续采集的方案，天花板都只是「近期窗口」**。
- 结论：全量历史 = 一个持续运行的采集器。开源的 BilibiliHistoryAnalyzer / BilibiliHistoryFetcher 系列正是做这件事（SESSDATA + 增量去重 + 落本地 SQLite `bilibili_history.db` + 定时任务）。

### 1.3 浏览器插件 / MV3 约束

- Service Worker 易回收 → 全局状态必须进 `IndexedDB` 或 `chrome.storage.local`。
- `chrome.storage.local` 默认 10MB（可申请 `unlimitedStorage`，但需商店审核理由）；**大库应走 `IndexedDB`（GB 级、事务安全）**。
- `chrome.alarms` 最小周期 1 分钟（足够做每日/每小时采集）。
- CSP：禁 `eval`、禁远程脚本，必须用 DOM API 构建 UI。
- 抓 B站 API 需 `host_permissions`（api.bilibili.com）+ `cookies` 权限读取 `SESSDATA` —— **仍然要碰 Cookie，有泄露风险**，且用户需自行提供/导出 SESSDATA。
- `content_script` 可注入 bilibili.com 页面做原生 overlay（体验最佳）。

## 2. 三个正式方案对比评估

> 评分 1–5（5 最优）。「规则引擎保真」指续看规则引擎能否完整保留。

### 方案 A：纯浏览器插件（独立 Extension）

- **形态**：插件内置采集器（SESSDATA + cursor 分页 + 增量）+ IndexedDB 存储 + content script 注入 bilibili.com 做 overlay + popup 管理规则。
- **能实现到什么程度**：全功能。持续采集可做（alarms 驱动），overlay 原生，规则引擎可把 `server.py` 的 Python 逻辑移植为 TS。但 SW 回收 + 异步化会让「常驻采集」偏脆弱，需谨慎处理唤醒。
- **开发量**：**高**。从零搭 manifest/SW/content script/popup，并把规则引擎从 Python 重写成 JS/TS，含冲突校验与三视图。
- **风险**：SESSDATA 在扩展内处理的安全性质疑；Chrome 商店审核；后续 B站接口变动需及时跟进；用户体感「装个插件」最轻，但维护成本最高。
- **评分**：数据全量性 4 / 规则引擎保真 4 / 开发量(低好) 2 / 体验 5 / 安全 2 / 维护 2。

### 方案 B：基于 Analyzer 全量库做二次分析（本地 Web 应用）★推荐

- **形态**：Analyzer 负责全量采集（已验证、可 Docker/打包 exe），本工具**只读**其 SQLite（`bilibili_history.db`）或调其 `:8899` REST API；规则引擎与 Web UI 完全复用。
- **能实现到什么程度**：完整且最稳。拿到全量历史后，`needs/skipped/stale` 三视图才有真实意义；规则引擎零改动保真。
- **开发量**：**低**。仅改 `server.py` 数据源（把 `collector.py` 自采改为「只读 attach Analyzer 的库 / 调用其 API」）+ 字段映射；规则引擎、前端、bat 全部复用。
- **风险**：依赖 Analyzer 落库 schema 稳定性（需适配其字段名）；要求用户先跑一次 Analyzer 建库。属「分工」而非「造轮子」。
- **评分**：数据全量性 5 / 规则引擎保真 5 / 开发量(低好) 5 / 体验 3（独立 Web 页，不在 B站站内）/ 安全 5 / 维护 4。

### 方案 C：混合（本地分析 + 插件采集 / overlay）

- **形态**：本地仍跑规则引擎 + 全量库；插件只做两件事——① 实时补抓（捕捉 B站页面已加载但 API 窗口已丢的记录）；② 在 bilibili.com 上打「续看」角标 overlay。插件与分析层通过本地文件/端口通信。
- **能实现到什么程度**：最佳（全量 + 原生 overlay + 保真规则引擎）。但本质是 A+B 的叠加。
- **开发量**：**很高**。两套前端 + 进程间通信 + 采集逻辑，复杂度是 B 的数倍。
- **风险**：最高复杂度与维护成本；通信协议易碎。
- **评分**：数据全量性 5 / 规则引擎保真 5 / 开发量(低好) 1 / 体验 5 / 安全 4 / 维护 2。

### 方案 D：油猴脚本 / 扩展（原生页面手动拉取 + 本地存储）★新方向（契合「部署方便 / 使用方便 / 不自动全量」）

- **形态**：用户脚本（Tampermonkey / Violentmonkey）或轻量扩展，注入 `https://www.bilibili.com/history`。在页面内 hook `window.fetch`（`@run-at document-start`），捕获历史 `cursor` 接口响应，把条目累积进浏览器 **IndexedDB**；在原生历史页注入「续看筛选」面板，把当前原型的续看规则引擎（条件组 / 冲突校验 / 三视图 / dirty_count）**原样移植为纯 JS**。数据获取完全依赖用户主动在历史页滚动 / 点击「加载更多」（脚本可半自动加速「加载全部」），**不做后台定时采集**。
- **能实现到什么程度**：
  - 数据范围 = **API 时间窗内**（≈最近 1000 条 / 3 个月，先到者）。超出部分服务端已裁剪，无法获取——这是 B站机制决定的硬上限，与「手动 / 自动」无关，用户已接受「不自动全量」。
  - 续看规则引擎 = **100% 可移植**。所需字段（`business` / `progress` / `view_at` / `author_name` / `duration` / `title`）全部来自 cursor 响应；`needs`(progress 0–100) / `skipped`(auto_skip/manual_skip) / `stale`(view_at 久远) 三视图与当前 engine 一一对应，条件组、冲突校验 C1/C2/C3、`auto_skip` 绑定、`dirty_count` 逻辑可直接复用。
  - 本地存储 = IndexedDB 无容量上限（用户授权即可），足够数万条记录。
- **开发量**：**低–中**。无后端、无 Python、无打包，单文件 JS。主要成本 = ① 规则引擎 Python→JS 移植；② 历史页 DOM 注入与样式隔离；③ 跟进 B站历史页（Vue SPA）DOM / 接口变动。
- **可行性佐证（已有先例）**：GreasyFork 上 `Bilibili 观看历史智能分析`（v3.2.0，github: hyhAsma/bili-history-analyzer-userscript）已注入 `www.bilibili.com/history`，用 `GM_xmlhttpRequest` 取数 + 本地存储 + 浮动面板 + 筛选条件；另有多个历史导出 / 持久化脚本。证明「原生页注入 + 取数 + 本地存储 + 筛选」链路完全跑得通。
- **风险**：① 数据天花板锁定近期窗口（用户已接受）；② B站历史页是 SPA，改版需跟进（用 `MutationObserver` + fetch hook 比依赖固定 DOM 更稳）；③ 跨域取数走 `GM_xmlhttpRequest`（绕过 CORS）或 hook 页面自有 fetch（自带认证）均可行，SESSDATA 始终在浏览器内，无额外泄露面，安全性优于交给 Python。
- **评分**：数据全量性 3 / 规则引擎保真 5 / 开发量(低好) 4 / 原生体验 5 / 安全 5 / 维护 3 / 分发便捷度 5。

## 3. 当前原型工程是否必要继续开发

### 3.1 现状盘点（基于 `src/server.py`、`data/rules.json`）

- **规则引擎（差异化价值，成熟）**：单条 active 规则 + 多分组条件（`progress_pct`/`duration`/`business`/`view_at_age_days` 等字段，`>=`/`</`/`in`/`not_in`/`contains`/`between` 等操作符）；冲突校验 C1/C2/C3；`auto_skip` 与 `auto_skip_reason` 绑定共存；`manual_skip` 反悔；三视图（needs/skipped/stale）；`rules_status` 的 `pending` / `dirty_count` 脏计数；增量/全量同步；封面缓存。
- **采集层（商品化，与 Analyzer 重复）**：`collector.py` 用 SESSDATA + cursor API 自采，与 BilibiliHistoryAnalyzer 做的是同一件事。

### 3.2 判断

- **规则引擎：必须保留并继续完善**——这是本项目的真正壁垒，且与 B站机制无关，任何方案都能、也应该复用它。
- **独立采集层：不值得继续重造**——全量采集是已被 Analyzer 解决的硬骨头，自采只是在重复造轮子，且用户要维护两套 SESSDATA 流程。
- **结论：继续开发，但转换定位**——从「自采 + 分析一体」转为「**可插拔的续看分析层**」：保留 `rules.json` 引擎与 Web UI；数据源切换为 Analyzer 的 SQLite（只读 attach）；`collector.py` 降为可选/逐步淘汰。

> 换言之：**原型值得继续，但应停止强化采集，转向「分析层」角色**。这也使原型的续看规则能力可以立刻服务于 Analyzer 已有的全量数据，价值最大化。

### 3.3 若走方案 D（油猴/扩展·原生手动拉取）对原型的影响

- **Python 服务端（server.py / collector.py / bat）不再是必需品**：方案 D 把取数、存储、UI 全部搬进浏览器，无需本地 HTTP 服务、无需 Python 运行环境、无需 start/stop.bat——这正是「部署方便、使用方便」的兑现。
- **续看规则引擎必须保留，且应作为「可移植的纯逻辑」继续开发**：当前 `server.py` 中的条件组、冲突校验 C1/C2/C3、`auto_skip` 绑定、三视图、`dirty_count` 计算，应抽离为与语言无关的算法规格（或先移植为 JS 模块），供油猴脚本直接复用；`data/rules.json` 的 schema（单 active、多分组、字段/操作符集合）可直接沿用为脚本端的规则存储格式（存 IndexedDB 或 `GM_setValue`）。
- **结论微调**：原型本身的「Web 应用外壳」可逐步让位于单文件脚本；但规则引擎这一壁垒逻辑，必须继续打磨并沉淀为跨形态可复用的核心。

## 4. 三种方案之外的其他实现形式探索

针对「续看/历史管理」这类需求，业界还有以下常见形态：

### 4.1 油猴 / 用户脚本（Userscript，如 Tampermonkey / Violentmonkey）
- 代表：`RocommendationRecordForBilibili`（推荐流记录+导出）、`B站历史记录持久化`（存浏览器 IndexedDB，提供搜索）、`Bilibili Boring`（自带 key/op/value 过滤规则引擎，可作为「续看规则」的脚本端范本）。
- 优点：零安装、跨浏览器、可直接在 B站页面 overlay；开发轻。
- 缺点：**同样受 API 窗口限制（通常只抓 ~400 条）**，全量仍需周期抓取；`GM_setValue` 存储小，大库要靠 IndexedDB；调试/分发弱于正式扩展。
- 适配度：中（作为「其他形态」背景）。注：该形态已升级为正式方案 **D（原生页面手动拉取 + 本地存储）** 纳入 §2 对比——用户新方向即指向此。

### 4.2 桌面应用（PyInstaller / Electron / Tauri，打包为 exe）
- 代表：BilibiliHistoryAnalyzer 即打包为 `BilibiliHistoryAnalyzer.exe`，双击即用。
- 优点：数据主权最强、无商店审核、可直接内嵌本工具的规则引擎（server.py 已是零依赖 stdlib，极易打包）；体验接近原生。
- 缺点：需用户运行一个本地程序；无站内 overlay。
- 适配度：高。本质是「方案 B 的发行形态升级」，分发最省心。

### 4.3 PWA / 本地静态站点 + Service Worker
- 浏览器内离线应用，安装到桌面；存储与扩展类似受 `IndexedDB` 约束。
- 优点：跨平台、免商店；缺点：仍需采集逻辑、无站内 overlay、推送/后台能力弱。
- 适配度：中低（与 B 方案重叠，但分发无显著优势）。

### 4.4 服务端定时任务（VPS / Docker）
- 代表：Analyzer 已验证（`8899` API + 每日 0 点定时拉取）。
- 优点：全量库集中在服务器，多端（手机/电脑）随时访问；最适合「数据在中央」的模式。
- 缺点：需一台常驻机器；SESSDATA 在服务器上，安全考量上移。
- 适配度：高（尤其多设备用户）。可与 B 方案结合：Analyzer(Docker) 供数，本工具读库分析。

### 4.5 导出 + 本地分析（最轻量）
- 定期把历史导出为 JSON/CSV，本地小工具分析。
- 优点：极简、零依赖、最安全；缺点：非实时、需手动/半自动导出。
- 适配度：低（不满足「自动续看归类」的实时性需求）。

### 4.6 扩展 + 后端分离（松耦合版 C）
- 扩展只负责「站内 overlay + 写本地文件」，后端（本工具）负责分析与全量库。比完整 C 更松、维护更可控。
- 适配度：中高（若坚持要站内体验，这是比 C 更现实的折中）。

## 5. 综合建议与推荐路线

1. **主路线（契合新方向）：方案 D（油猴脚本/扩展·原生页面手动拉取 + 本地存储）**。最符合「部署方便、使用方便、不自动全量拉取」三项诉求：零后端、零 Python、装插件即用的单文件脚本；续看规则引擎 100% 可移植；数据范围锁定在 B站 API 时间窗（用户已接受）。落地第一步是把规则引擎从 `server.py` 抽离/移植为 JS，并在 `www.bilibili.com/history` 注入 fetch hook + IndexedDB + 筛选面板。GreasyFork 已有同类脚本印证链路可行。
2. **若日后想要真正全量历史**：在 D 之上接 Analyzer 全量库（方案 B 思路），把数据源从「页面手动拉取」升级为「只读 Analyzer 的 SQLite」——规则引擎与 UI 不变，仅换数据层。即 D 是轻量现用版，B 是未来的全量升级版。
3. **若追求更强的站内体验/后台补抓**：走 4.6 松耦合扩展或混合 C（复杂度更高，按需）。
4. **当前原型**：继续打磨**续看规则引擎**，但将其作为「可移植纯逻辑」沉淀（Python→JS 均可）；Web 应用外壳与 Python 采集层在 D 路线下可逐步退场。

## 7. 市场同类插件调研与效果评估（新增）

> 本节回应「是否已有人实现类似功能」——结论：**「历史记录的持久化 / 搜索 / 筛选 / 标记」能力已有多个成熟脚本覆盖（甚至能做到全量存储 + 时间轴回溯），但「基于观看进度的续看三视图分类 + auto_skip 理由 + 结构化规则引擎 + 业务类型预设」这一特定组合仍无人实现**。底层管道与规则范式均已被验证。

### 7.1 已存在的近似插件/脚本清单

| 插件/脚本 | 形态 | 历史页注入 | 取数+本地存储 | 筛选/规则能力 | 续看分类(needs/skipped/stale) | 自动全量 | 备注 |
|---|---|---|---|---|---|---|---|

### 7.2 能力映射：我们的续看规则引擎 vs 现有插件

| 三视图 needs/skipped/stale（基于 progress） | ❌ 全覆盖缺失 | 智能分析只做统计；标记已看仅为手动透明度；无限历史只做搜索 |

| 单活跃规则 + 多条件组（AND/OR）+ 冲突校验 | ❌ | Boring 有规则但为扁平黑白名单，无分组/冲突校验/单活跃约束 |

| 历史页 fetch 注入 + 本地存储 + 筛选面板 | ✅ 已被验证 | 智能分析/导出工具/标记已看 三个先例证明管道可行 |
| 规则引擎在油猴里跑（key/op/value 解析） | ✅ 已被验证 | Bilibili Boring 证明范式可行 |

### 7.3 效果评估结论

1. **组合缺口明确，但泛筛选能力并非空白**：市场已有多个「历史记录持久化 + 搜索 + 筛选 + 标记」的成熟脚本（Ice_wilderness 的历史搜索/统计图表、bilibili history manage 的 IndexedDB+搜索、进度备份的阈值隐藏、无限历史记录的全量存储）。但「基于观看进度的续看三视图分类 + auto_skip 理由 + 结构化规则 + 业务类型预设 + dirty_count」这一**特定组合**仍无任何插件实现。差异化空间真实存在——我们不是从零造筛选，而是把已验证的筛选/存储能力升维成「续看分类规则引擎」。
2. **底层风险已被前人消除**：
   - 「注入历史页 + fetch 取数 + 本地存储 + 浮动筛选面板」已被 `观看历史智能分析`、`历史记录导出工具`、`手动标记已看` 三个油猴脚本验证可行；
   - 「在油猴里跑 key/op/value 规则引擎」已被 `Bilibili Boring` 验证可行。
   - 即我们的工作 = **把两条已被验证的路径组合成「历史页续看分类」这个无人占据的细分**，纯增量创新，技术风险低。
3. **与最接近的「无限历史记录」扩展相比**：它走后台每分钟自动同步（违背「不自动全量」诉求）且需商店审核；我们的「手动拉取油猴脚本」更贴合需求、分发更轻、无审核门槛。

### 7.4 我们的差异化机会点（立项理由）

- 唯一把「基于 progress 的续看三视图」做成**规则引擎**的工具（泛筛选/标记已有，规则化续看分类无）；
- auto_skip + 理由绑定（可解释性，优于纯隐藏）；
- 结构化规则（单活跃 + 多组 + 冲突校验）优于扁平黑白名单；
- 按 business 类型的预设一键加入；
- dirty_count 增量感知；
- 契合「用户主动拉取、本地存储、不自动全量」的轻量定位。

### 7.5 需注意的复用点/风险

- 现有脚本多用 `GM_setValue` 存配置（小）；我们要存**条目**必须走 IndexedDB（智能分析没做，但技术成熟）。
- Boring 的规则是字符串解析；我们的多组条件 + 冲突校验更复杂，但仍是纯前端逻辑，可借鉴其解析思路。
- 历史页是 Vue SPA，所有先例都需跟进 DOM 改版——这是共同维护成本。

## 8. 方案 D 落地形态细化：UI 形态抉择 & 被挤掉记录的处理（新增·回应实践疑问）

> 本节回答两个落地层面的实际问题：**(a) 已存储的历史记录是重新插入 B站原生历史页，还是重开独立页面可视化？(b) 已被 B站实际挤掉（服务端删除）的记录如何处理？** 结论先行：两个都不是死路，且业界都有先例。

### 8.1 UI 形态：注入原生历史页 vs 独立可视化

**A. 注入原生历史页（overlay）— 推荐作主形态**
- 做法：脚本 `@match https://www.bilibili.com/history*`，在原生历史列表上叠加——顶部筛选栏（按规则/视图切换）、每条记录的分类角标（续看/已跳过/已搁置）、命中规则项的隐藏/置顶；规则管理用「浮动面板（右下角抽屉）」或历史页侧边抽屉。
- 可行性：Truazusa、Ice_wilderness、bilibili history manage 均注入历史页，链路已验证。
- 优点：最贴合「在原生网页操作」诉求；零上下文切换；标记/分类与 B站原生 UI 融合。
- 限制：只能增强「当前服务端仍存在」的记录（近期窗口内）；需跟进 B站 SPA 的 DOM 改版。

**B. 独立可视化页（浮动面板 / 独立路由）**
- 做法：注入一个浮动按钮，点击展开独立浮动面板（如 RocommendationRecordForBilibili 的浮动面板），或新开 `data:` URL / 独立视图（如 `bilibili.com/#/ext-history`）做完整可视化。
- 优点：不受原生历史页 DOM/分页约束，可做时间轴、统计图、三视图完整列表；**能展示「本地独有（被 B站挤掉）」的记录**（历史页无原生卡片可挂靠，需脚本注入额外区块才显示；但 Ice_wilderness 已证明本地标记可打到首页/搜索/视频封面等原生卡片上）。
- 限制：脱离 B站原生体验，有上下文切换。

**C. 混合（推荐）**：主 UI = 原生历史页 overlay（满足「在原生网页操作」）；规则管理 + 本地独有记录浏览 = 浮动面板 / 独立视图。恰好对应两个诉求：平时在原生页看，要管理规则或翻「被挤掉的老记录」时开面板。

**关键澄清 —「重新插入原生网页」指什么**：技术上能「注入 DOM 增强」，但**不能改写 B站服务端数据**（SESSDATA 不能增删服务端历史条目）。所以：
- 对当前服务端仍存在的记录：在原条目上叠加分类角标/标记/筛选，点击跳 B站原播放页；
- 对「本地有、服务端已删」的记录：原生网页里看不到（服务端已无），只能在独立面板/浮动视图展示。
- 即：**原生网页 = 近期窗口的增强视图；本地库 = 你的私人全量超集；二者通过 `bvid` 关联**。

### 8.2 被 B站实际挤掉的记录如何处理

**事实（多来源确认）**：B站官方历史 = FIFO 滚动覆盖（~1000 条 / 3 个月），超出即服务端删除，**不可逆**；第三方无法恢复已删服务端记录（guofenba / zol / tsight.io 均确认）。
**但关键点**：你本地 IndexedDB 缓存的快照是持久的——只要手动拉取时它还在服务端，本地就永久留存，**不受 B站删除影响**（本地数据与服务端解耦）。这恰恰是「手动拉取 + 本地存储」相对「不自动全量」的**隐藏优势**：用户主动采集 = 把数据从 B站沙盒剥离到本地主权。

**方案 D 的落地处理策略**：
1. **本地库 = 私人全量超集（时间窗内拉取过的一切）**：IndexedDB 容量充足（百万条，bilibili history manage / 无限历史记录已验证）。
2. **增量合并（去重保旧）**：每次用户在历史页滚动/点加载，hook cursor 响应按 `bvid` upsert；本地**不做 FIFO 淘汰**，旧记录永久保留，新记录追加。
3. **被挤掉记录的呈现**：独立视图/面板提供「本地独有（服务端已无）」分组——你本地有、但 B站当前历史已看不到。这是本插件**最大价值点之一：帮用户找回被 B站「蒸发」的历史**（无限历史记录扩展主打的也是此痛点）。
4. **可解释性**：对每条本地记录标注来源（手动拉取时间）与「是否仍存于服务端」，让用户清楚「这条还在 B站」还是「只在你本地」。
5. **备份/导出**：JSON 导出（RocommendationRecordForBilibili 已验证导出可行）防浏览器清理丢失；可选 WebDAV（进度备份脚本、无限历史记录已验证）跨设备。
6. **不回写服务端**：本地是超集、服务端是子集，仅单向采集，绝不尝试往 B站写回（也写不进）。

### 8.4 概念澄清：本地有记录 ≠ 能无限制「写入」原生历史页

> 针对「只要本地有历史记录就可以推到原生网页里并且没有限制、也能做到无限记录」这一常见误解，做精确拆解：

- **「推到原生网页」是 DOM 增强，不是服务端写入，但本地记录确实能上原生页**：脚本往 `bilibili.com/*` 注入额外 DOM（角标、区块、筛选栏、列表项），**无法把记录写回 B站服务端**，但完全可以把本地库存渲染到原生页面。实证：Ice_wilderness「Bilibili视频观看历史记录」(v3.5.0) 把本地「已观看/进度%」标记打到首页、搜索页、历史页、视频封面各处——某 BV 即便已被服务端淘汰，只要它出现在原生卡片上就带标记。可行形式是「叠加标记 / 注入额外区块」，不是「写回服务端」。边界：① 不能写回服务端；② 不能无缝并入 B站原生无限滚动列表、像服务端条目一样存活于 B站自身重渲染；③ 不跨设备、不同步、清存储即失。
  - 对「本地有、服务端已删」的记录：在**历史页**没有原生卡片可挂靠标记（B站不渲染它），故历史页里看不到它作为「列表项」；但它出现在**独立管理面板**（Ice_wilderness 的「历史管理」即此），且只要该 BV 在首页/搜索/视频封面出现就带本地标记。若想让它也显式出现在历史页，需脚本**额外注入一个「本地独有」区块**（技术上可行，需自行实现）。
- **「无限记录」成立，但有前提**：本地 IndexedDB 确实不做 FIFO 淘汰、容量近乎无上限 → 本地库会随「多次手动拉取」滚动累积成**私人全量超集**（真·无限）。但它**不是一次拉取就无限**，仍需用户在记录尚存服务端时分次拉取累积；若想要「开箱即无限」，依赖后台自动同步（已被本方案否决）。
- **「独立筛选」这部分完全成立、无限制**：一旦数据在本地，筛选/排序/分类/三视图全是纯前端逻辑，不受 B站任何约束——这是本方案最稳、最强的一环。
- **结论**：把「无限 + 无限制筛选 + 全量记录」放在**独立可视化视图**里才是真·无限（一步到位可视化在此完成）；原生页 overlay 既能增强近期窗口、也能叠加本地记录标记，但受「无原生卡片处无法挂靠」约束，二者互补而非互相替代。

## 9. 存储层评估：原始响应为权威、结构化为派生（新增·回应「最关键的存储」）

> 用户决定：像 BilibiliHistoryFetcher 那样把「实际数据单独记录管理」，目标是保证将来能把原生数据迁到任意插件适配的数据库而不缺失。本节评估 Fetcher 的数据完整性与可迁移性，并给出本项目的存储设计建议。

### 9.1 BilibiliHistoryFetcher 的数据完整性
- **抓取范围**：基于 `/x/web-interface/history/cursor`，抓的是接口返回的**全部字段**（非子集）。增量同步（fetch 仅取比本地最新 `view_at` 更新的记录，到 cutoff 即停）使其能跨时间累积，逼近超窗口全量。
- **「全」的上限**：受 B站机制约束——API 窗口内（约 1000 条 / 3 个月，滚动覆盖）且在记录被覆盖前抓到。Fetcher 的「全」= 持续运行下累积的超集；本项目「用户主动拉取」模型下，「全」取决于用户拉取时机（拉取时窗口内的一切都能拿到）。
- **落库字段（结构化表 `bilibili_history_YYYY` 摘要）**：`id / title / long_title / cover / covers(JSON) / uri / oid / epid / bvid / page / cid / part / business / dt / videos / author_name / author_face / author_mid / view_at / progress / badge / show_title / duration / current / total / new_desc / is_finish / is_fav / kid / tag_name / live_status` —— 覆盖了大多数续看规则所需字段（`business / progress / duration / view_at / author`）。

### 9.2 可迁移性：关键在「是否保留原始响应」
- **Fetcher 的设计保证无损**：数据流水线五阶段含 **raw JSON archival**；落盘同时保留两份原始数据——`api_responses/`（原始 API 响应缓存，便于重放/排错）与 `history_by_date/YYYY/MM/DD.json`（按日期归档的原始观看历史快照）。SQLite 只是派生的查询优化视图。
- **结论**：只要迁移源用**原始 JSON**（而非只取 SQLite 派生表），就能零缺失地映射到任意目标插件 DB——因为 raw 含 API 给的全部字段。
- **风险点**：若只拿 Fetcher 的 SQLite 派生表，则表未建模的字段（`live` 对象、`child`、`tags` 数组、`history` 嵌套的 `viewed/progression` 等）在迁移时会缺失。所以「足够全且可迁移」的前提是**以原始响应为权威层**。

### 9.3 本项目（方案 D 油猴脚本）的存储设计建议
- **双存储（对齐 Fetcher 思路）**：
  1. **权威层 `raw`**：IndexedDB 对象仓库，`key = ${bvid}@${view_at}`（非稿件类用 `${oid}@${view_at}`），`value` = **完整 cursor 响应 JSON 原样**（不丢任何字段）。**永不 FIFO 淘汰**。
  2. **派生层 `derived`**：同 key，`value` = 规则引擎所需的扁平字段（`business / progress / duration / view_at / author_name / title / ...`），供快速筛选。
- **取数**：hook cursor 响应，逐条 upsert `raw` + `derived`。
- **迁移**：将来写个小工具读 `raw` → 映射到目标插件 DB，零缺失。
- **复合 key 原因**：B站以 `(oid, view_at)` 为标识，`bvid` 可在不同 `view_at` 重复；复合 key 保证唯一且幂等。
- **备份**：`raw` 整库导出 JSON（对齐 Fetcher 的 `history_by_date` 归档），防浏览器清理丢失。

### 9.4 对「是否足够全」的最终回答
- **字段层面**：Fetcher（及本方案 D 直接 hook cursor）抓的都是**接口全字段**，足够支撑任何续看/筛选规则。
- **时间覆盖层面**：「全」受 API 窗口 + 拉取时机约束，非工具缺陷；Fetcher 靠持续同步逼近全量，本方案靠用户主动分次拉取累积。
- **可迁移层面**：**只要以原始响应为权威层（本项目 `raw` 存储），将来迁到任意插件 DB 都不会缺失**——这是设计保证，非运气。
