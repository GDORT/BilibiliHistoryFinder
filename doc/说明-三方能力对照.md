## 1. #4 备份：三方对比 + 「保持一样」到底意味着什么

### 实读事实

| 能力 | Analyzer | Frontend | Finder（现状） |
|---|---|---|---|
| 自动/定时备份 | ❌ **无内置备份任务**（`config/scheduler_config.yaml` 默认 4 个任务全是抓取/导入/健康检查，**无 backup**） | ❌ 无 | ❌ 无（仅手动） |
| 手动备份方式 | README §233 建议：**「备份 `output` 整个文件夹（直接拷贝或压缩打包）」** | ❌ 无 | ✅ `POST /api/backup` |
| 快照粒度 | 全文件夹拷贝（粗） | — | ✅ **SQLite 在线快照**（`sqlite3` backup API，不用停服、不拷垃圾）+ `meta.json` |
| 保留策略 | 无（取决于你拷几份） | — | ❌ **无**（`data/backup/` 会无限累积） |
| 定时任务框架 | ✅ 有 `scheduler`（可挂任意端点） | ✅ 只是它的 UI | ❌ 无 |

### 「保持一样即可」的正确解读

Analyzer **不自动备份**，所以「和它一样」= **不做定时自动备份**。
但 Analyzer 有一个**你还没用上的能力**：`scheduler` 可以**定时调任意端点**——
理论上可以自建一个任务定时调 `/export/download_db` 来"定时导出"。

**建议**（三选一，按你偏好）：
- **(a) 真·保持一致**：保持手动 ⑤，**不加定时**。零工作量。← **默认推荐**
- **(b) 轻量补保留策略**：只给 `data/backup/` 加「保留最近 N 份」清理（≈10 行），避免无限累积。**这是现实中唯一真会咬人的点。**
- **(c) 定时备份**：手动 ⑤ 之外加定时。**不建议**——现有 ⑤ 已在手动点上超前 Analyzer，再堆定时属于为一致性牺牲简洁。

> **结论**：待办 #4 的实质只剩一件事 —— **保留策略**（(b)）。定时备份(Analyzer 也没有)可以明确记为「不做」。

## 2. #6 导出：跟随 Frontend 的「零实现、全中继」策略

### 实读事实

| 层 | 做什么 |
|---|---|
| Frontend `Settings.vue` §数据导出 | UI：年份 / 月份 / 日期范围三选 + 「导出 Excel」按钮 |
| Frontend `api/api.js:443` | `POST /export/export_history`（带 `year`/`month`/`start_date`/`end_date`） |
| Frontend `api/api.js:450` | `GET /export/download_excel/{filename}`（下载生成的 xlsx） |
| Frontend `api/api.js:474` | `GET /export/download_db`（**下载整库 .db**） |
| Analyzer `routers/export.py` | 真正实现：`export_to_excel.export_bilibili_history()` + 两个下载端点 |

**关键**：Frontend **没有自己生成任何文件**，全是转发。这与 Finder 现在的定位**完全一致**。

### 「保持一样」的落地形态

Finder 只需**中继 3 个端点**（复用现有 `_forward_fetcher()`，含 POST 支持——上一轮已泛化）：

| Finder 新增端点 | 转发到 | 用途 |
|---|---|---|
| `POST /api/export/excel` | `POST /export/export_history` | 生成 xlsx，回传 `filename` |
| `GET  /api/export/excel/{filename}` | `GET /export/download_excel/{filename}` | 下载 xlsx |
| `GET  /api/export/db` | `GET /export/download_db` | 下载整库 .db |

**测试入口**（curl 级，无需建 UI 即可验）：
```
POST http://localhost:8765/api/export/excel?year=2026
GET  http://localhost:8765/api/export/excel/<返回的 filename>
GET  http://localhost:8765/api/export/db
```
UI 侧只需在设置弹窗加「导出 Excel / 下载整库」两个按钮（与 Frontend `Settings.vue` 同款）。
**不要自写 Excel 生成** —— Python 侧已由 Analyzer 完成，Finder 重写等于制造第二个口径。

## 3. #7 remark：效果是什么 + Finder 的实际落差比想象中小

### 效果（Frontend「我的备注」页 `page/Remarks.vue`）
- 卡片列表，每张卡片含：**封面 + 时长角标 + 观看进度条 + 标题 + UP头像/名 + 备注文本**；
- 页头显示「**共 N 条备注**」；
- 数据来自 `GET /history/remarks`。

### Analyzer 接口（`routers/history.py`）
| 端点 | 作用 |
|---|---|
| `GET /history/remarks` | 取全部带备注的记录 |
| `POST /history/update-remark` | 单条更新：`{bvid, view_at, remark}` |
| `POST /history/batch-remarks` | 批量取备注 |

### 存储位置（重要）
`routers/history.py:746 update_video_remark()` 明确：
```sql
UPDATE bilibili_history_<year>
   SET remark = ?, remark_time = ?
 WHERE bvid = ? AND view_at = ?
```
→ **备注存在 Analyzer 主库的年表里**，按 `(bvid, view_at)` 定位（与我们 `kid` 一致）。

### Finder 现状（实读 `store.py:37`）
```python
ANALYZER_COLS = [..., "remark", "is_fav", "videos"]
```
→ **Finder 已经在读 `remark` 字段了**，只是**没有 UI 展示、也没有写入通道**。

### 结论
| 是否要做 | 说明 |
|---|---|
| 展示备注 | **成本极低**：字段已在 `record` 里，卡片加一行即可（需确认前端是否已丢弃该字段） |
| 编辑备注 | **建议中继** `POST /history/update-remark` 到 Analyzer（写主库），**不要**存本地侧库——否则与 Frontend/官网的备注不互通，变成第三份数据 |
| 独立「我的备注」页 | 可选；Frontend 有，但你的浏览主流程不一定需要 |

> 待办 #7 的答案：**效果 = 每条视频一段自由文本备注 + 集中浏览页**；
> 落地方向 = **展示免费拿、编辑走中继**。

## 4. #8 图片批量下载：接入方式 + 测试入口（你要的）

### Analyzer 接口（`routers/image_downloader.py`）
| 端点 | 参数 | 作用 |
|---|---|---|
| `POST /images/start` | `year`(可选) / `use_sessdata`(默认 true) | 后台任务下载**封面 covers + 头像 avatars**；不传 `year` = 全部年份 |
| `POST /images/stop` | — | 停止 |
| `GET  /images/status` | — | 返回 `covers`/`avatars` 各自的 `total / downloaded / failed / total_planned / failed_urls` + `last_update` |
| `POST /images/clear` | — | 清空所有已下载图片 |
| `GET  /images/local/{image_type}/{file_hash}` | — | 取本地图片文件 |

> `use_sessdata=false` 的用处：公开内容（封面/头像）**不需要凭证**也能下 → 恰好规避你担心的凭证问题。

### Frontend 的效果（`page/Images.vue`）
- 「下载图片 / 停止下载」按钮 + 「清空图片」；
- 勾选框：**使用 SESSDATA 下载图片**；
- 状态区：**covers / avatars 两套进度条**，显示 `计划下载 / 已下载 / 失败 / 待下载` 四个数字，并列出 `failed_urls`；
- 显示「最后更新」时间。

### Finder 接入建议（3 步，全部复用现有转发器）
1. **中继**（≈40 行）：`POST /api/images/start|stop|clear`、`GET /api/images/status`、`GET /api/images/local/...`（后者是二进制流，需单独处理 `Content-Type`）。
2. **UI**：设置弹窗或 ⑤ 备份旁加一个小面板 —— 两个按钮（开始/停止）+ 一个进度条 + 失败数。
3. **与图片代理的关系**：Finder 现有 `/cover/` 是**按需代理**（不落盘）。
   接入后应改为「**优先读本地已下载，回退外链**」，否则下载了也没用上。

### 测试入口（可直接复制执行）
```bash
# 1) 健康：确认图片下载模块在（应返回 covers/avatars 结构）
curl -s http://localhost:8765/api/images/status

# 2) 只下一年的封面，且不使用凭证（最安全的冒烟测试）
curl -s -X POST "http://localhost:8765/api/images/start?year=2026&use_sessdata=false"
curl -s http://localhost:8765/api/images/status      # 观察 downloaded 递增
curl -s -X POST http://localhost:8765/api/images/stop

# 3) 清空（谨慎，会删掉已下图片）
# curl -s -X POST http://localhost:8765/api/images/clear
```
**验收标准**：`status.covers.total > 0` 且 `downloaded` 递增；`failed_urls` 为空或很少。
**注意**：这是**写盘操作**（会往 Analyzer 的输出目录写图片），建议先 `year=2026` + `use_sessdata=false` 冒烟，再决定全量。
