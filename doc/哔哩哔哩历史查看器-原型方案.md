# B站历史记录查看器 — 原型方案

> 文档状态：讨论稿（技术路线未定，可选方案待逐项讨论）
> 日期：2026-07-22
> 关联：需求见《哔哩哔哩历史查看器-需求评估.md》
> 说明：本文件聚焦"如何做"（可行性、技术栈、MVP、分阶段、风险）；具体可选方案见 §6，仍在讨论中。

## 1. 可行性结论
**可以快速开发原型，且最终能完成预期功能（含一项固有局限）。** 核心数据通路（SESSDATA + cursor 分页接口 + 本地存储）已确认可行；展示与筛选均为标准前端工作。**最大不确定点（时长获取）已被实测消除**——历史接口实测直接返回 `duration`，`progress<95%` 判定无需额外请求（详见 §8）。预计可分阶段交付，MVP 即可跑通"留存 + 类网页展示 + 搜索 + 基础筛选"。
- **固有局限（必须接受）**：本地留存只能"从现在起"生效。B站端已被 1000 条上限顶掉的**过去历史无法恢复**——无论哪种方案都救不回。原型的价值是"以后一条不漏"。
- **能达成的功能**：FR1 突破上限留存、FR2 类网页展示、FR3 搜索、FR4 筛选、FR5「需要观看」、FR6 自动化——全部可在本方案框架内实现。

## 2. 流程完整性评估（是否遗漏步骤）
### 2.1 端到端流程（完整步骤链）
```
① 凭证获取   → 取 SESSDATA（浏览器 F12 / 后续扫码）
② 拉取历史   → 调 history/cursor，用 max/view_at/business 翻页，直到无更多
③ 写入存储   → 按 kid 去重写入 SQLite；注意 progress 更新语义（见 2.3）
④ 封面处理   → 存远程 URL（Phase1）【或】下载缓存到本地（后续，离线/永久）
⑤ 时长        → 接口已直接返回 `duration`（实测 1207/1207 有值），**无需补取**；可直接算 progress/duration 百分比（详见 §8.4）
⑥ 展示       → Web 单页 或 MD 导出
⑦ 搜索/筛选  → 关键词 + 时间/类型 + 「需要观看」开关
⑧ 打开视频   → 由 bvid/uri 生成链接/深链（影响展示实现，见 §6.4）
```
### 2.2 当前方案相对完整流程的遗漏 / 薄弱点
| 步骤 | 原方案状态 | 结论 |
|---|---|---|
| ④ 封面缓存 | 仅存远程 URL，未本地化 | **遗漏**：离线/封面失效时不显示；应在后续阶段补"下载落盘" |
| ⑤ 时长补全 | 列为独立步骤（缓存+限速+批量） | **实测已消除**：历史接口直接返回 `duration`（1207/1207 有值），FR5 无需补取，详见 §8.3 |
| ③ progress 更新去重 | 仅说"去重"，未定义更新语义 | **遗漏**：同一 kid 二次观看 progress 变大时应**覆盖更新**，而非简单跳过 |
| ⑧ 打开视频 | 未提及 | **影响展示**：卡片须是可点击链接，原型即预留 bvid→URL，深链留后续 |
| ① 凭证刷新 | 仅说"手动重填" | 可接受为 MVP；后续可加扫码/过期提示 |

### 2.3 功能达成度（对照需求 FR）
- FR1 留存 ✅（仅覆盖从现在起）；FR2 展示 ✅；FR3 搜索 ✅；FR4 筛选 ✅；FR5 需要观看 ✅（duration 已直接返回，无需补全，见 §8.4）；FR6 自动化 ✅（任务计划）。
- 唯一"不能"的是恢复已丢失的过去历史（非方案缺陷，是 B站服务端限制）。

## 3. 推荐技术栈（轻量、低依赖）
- **采集 / 服务**：Python（Flask 或内置 `http.server` 起本地 Web）；标准库即可完成 HTTP 请求与 SQLite。
- **存储**：SQLite（两张表：`history` 全量历史；`video_meta` 缓存 `bvid → 时长`）。封面用"文件路径/URL 字段"，不塞 BLOB。
- **前端**：原生 HTML / CSS / JS 单页，类 B站历史卡片列表；无需构建工具。零框架、零 npm。
- **调度**：Windows 任务计划程序每日跑采集脚本；或采集作为常驻后台线程。
- **导出（后续）**：Python 生成 Obsidian 兼容 Markdown，作为零依赖视图。

## 4. 阶段目标概览
> **Phase 1 只做"数据"**：把所有后续步骤会用到的字段一次性拉全并落库；展示、封面、筛选都往后放。目的是先把最不可逆的"留存"做扎实——数据一旦每天在跑，就不会再被官方上限顶掉。

- **Phase 1（仅数据）**：采集器拉全量历史 → SQLite，按 kid 去重且**覆盖更新 progress**。**一次性拉全后续所有步骤需要的字段**（见 §4.1），不做展示、不下封面。
- **Phase 2（展示 + 封面 + 搜索/筛选 + 需要观看 + 数据层增强）**：本地 Web 类 B站列表（封面 + 标题 + UP主 + 时间 + BV，可点击链接）；封面下载缓存到本地；关键词搜索 + 时间/类型筛选；**「需要观看」开关（直接基于已落库的 progress/duration 算 <95%，无需时长补取）**；数据层同步增加 `archived_only` 归档标记、`--incremental` 增量同步、同步统计（见 §10）。
- **Phase 3A（功能扩展与体验优化 — 优先）**：直接增强已有能力，让核心功能"更好用、更完整"。
  - **3A.1 规则引擎化**：当前「需要观看」硬编码 `progress < 0.95×duration`。改为可配置阈值 + 可叠加多规则（如"未看完且>5分钟""指定UP主""指定类型"），是核心筛选能力的直接扩展（关联 §6.9）。
  - **3A.2 「需要观看」闭环交互**：当前只有筛选、没有反馈动作。加本地状态表支持"标记已看/稍后/忽略"，点过的不重复出现，构成完整使用闭环——优化核心流程。
  - **3A.3 深链 `bilibili://`**：当前卡片是网页 URI 能打开但体验一般。深链让客户端直接跳到对应进度位置（弱依赖，可与 3A.1 并行）。
  - **3A.4 浏览体验优化**：分页/无限滚动、封面懒加载、按"今天/昨天/更早"分组、加载/空状态、1207 条列表性能（虚拟滚动或分页）、类 B站网页端卡片布局还原（两列网格、封面叠加时长/已看完徽标、相对时间格式等）。
  - **3A.5 数据呈现增强**：`archived_only` 在 UI 标注"B站端已无此记录"（仅初始全量校准，见 §12.4；增量下 frozen）、进度条可视化优化、`--incremental` 更智能（只拉新增不重算全部）。
  > 建议顺序：3A.1 → 3A.2 → 3A.3 → 3A.4 → 3A.5（前两项有先后依赖，其余可并行）。
- **Phase 3B（锦上添花 — 不影响核心功能，可放最后）**：独立增强 / 附加渠道，Web 查看已满足全部 FR，以下均为额外便利。
  - **3B.1 Obsidian / Markdown 导出**：额外输出渠道，纯锦上添花（关联 §6.2）。
  - **3B.2 自动化定时拉取（任务计划）**：便利增强；手动点"同步"按钮已能更新，不影响功能完整性。
  - **3B.3 纯视觉打磨**：主题/暗色模式、动画过渡、移动端响应式适配——不影响功能。
  - **3B.4 多账号 / 多 SESSDATA**：超出当前单账号范围的额外能力。
  - **3B.5 统计与可视化**：观看趋势图、时长统计、UP主榜等分析维度，非核心需求。

### 4.1 Phase 1 必须落库的字段（后续步骤所需，一次拉全）
| 字段 | 来源 | 后续用途 |
|---|---|---|
| `kid` | 历史条目 | 唯一键，去重/覆盖更新 |
| `title` / `show_title` | 历史条目 | 展示、搜索 |
| `author_name` / `author_mid` | 历史条目 | 展示、按 UP主搜索/筛选 |
| `view_at` | 历史条目 | 展示、时间筛选、排序 |
| `bvid` | `history.bvid` | 展示链接、打开视频、时长补全键 |
| `oid` / `epid` / `cid` | `history` | pgc/live/article 定位、打开视频 |
| `business` | `history.business` | 类型筛选（archive/pgc/live/article） |
| `cover` / `covers[0]` | 历史条目 | Phase2 下载封面用（先存 URL） |
| `progress` | 历史条目 | 「需要观看」判定（已看秒数） |
| `duration` | 历史条目 | **实测接口直接返回总时长（1207/1207 条有值）**，可直接算 progress/duration 百分比；原"需补取时长"假设已被推翻（见 §8.3） |
| `uri` | 历史条目 | 打开视频兜底链接 |
| `tag_name` / `badge` | 历史条目 | 后续规则扩展可用 |
> 原则：**宁可多存不漏存**。Phase 1 把原始 JSON 里所有可能有用的字段都落库（可整条 `raw_json` 也存一列做兜底），避免后续想加功能时"当初没拉"而要重刷。
> 补充（实测）：cursor 接口**不接受 `business="all"`**（返回空列表），初始应不传 business、跟随 cursor 返回的 business 翻页（详见 §8.5）。

## 6. 可选方案讨论（待定）
> 本节记录原型实现路线上的多种可选方案，逐项对比后再定。以下 6.1–6.4 为本次补充，6.5–6.9 为既有待定项。

### 6.1 拉取：自研 vs 参考 BilibiliHistoryFetcher
- **MVP 自研即可**：cursor 接口清晰、分页简单，自写约百行即可跑通，无外部依赖。
- **后续参考开源（BilibiliHistoryFetcher 等）的定位**：当作"健壮性对照清单"而非直接依赖——重点借鉴其对多 `business` 类型（archive/pgc/live/article）、分页边界、错误码（如 -101/-111）、时长补全与限流的处理，避免自研遗漏边界。
- **结论建议**：不自接第三方库做核心，但实现后与其对一遍覆盖度。

### 6.2 存储：SQLite 与图片；是否要接 Obsidian 等轻量存储
- **SQLite 支持图片吗**：技术上可用 BLOB 存二进制，但**不推荐**——会撑大数据库、拖慢查询。封面最佳实践是"文件落盘（封面图存本地目录）+ SQLite 存路径/URL"。**Phase1 只存远程 URL（不下载）**；**Phase2 加"下载缓存到本地"**实现离线/永久显示。
- **Obsidian / 其他轻量存储的定位 = 导出目标，不是存储替换**：SQLite 保持为**可查询真源**；后期加一个"导出为 Obsidian 兼容 Markdown"模块（每条约 note：frontmatter 含 BV/UP主/时间/标题，正文嵌封面 + 链接）。不要试图把活数据直接塞进 Obsidian vault——会破坏查询与去重。
- **结论建议**：存储引擎不变（SQLite + 封面文件）；Obsidian 通过导出模块接入。

### 6.3 展示：前端是否必须用 JS？纯 MD 可行吗？
- **实时搜索 / 筛选必须 JS**：FR3/FR4/FR5 是交互式的，纯静态 MD 无法在浏览器内实时过滤。
- **纯 MD 的可行路径（零依赖）**：由**脚本预过滤**后生成多份 MD 视图（如 `全部.md`、`需要观看.md`、`按UP主.md`、`按日期.md`），用任意 MD 阅读器（Obsidian / VS Code）打开。局限：无实时搜索框，筛选靠"打开对应文件"；且天然与 6.2 的 Obsidian 方案统一。
- **结论建议（双轨）**：
  - 主界面：原生 JS 单页 + 本地 Web（零框架、零构建，已满足"尽量依赖少"）；
  - 后续：加 MD 导出，作为零依赖 / Obsidian 视图。两者不冲突。

### 6.4 打开视频（不在原型，但影响展示实现）
- 数据已含 `uri` / `bvid`，可生成：网页 `https://www.bilibili.com/video/{BV}`；App 深链 `bilibili://video/{BV}`（手机端直接唤起 App）。
- **对展示的影响**：原型阶段就应把每张卡片渲染为 `<a>` 链接（而非纯文本），数据模型确保保留 `bvid`。"在 App 打开"深链按钮留到后续阶段，但结构现在就要留好口子。
- **结论建议**：原型即做可点击链接；深链按钮列入 Phase 3 打磨。

## 7. 分阶段路线（Phase 1 收敛为"仅数据"）
- **Phase 1（仅数据 / 最优先）**：① 凭证→② 拉取→③ 写入(按 kid 去重 + progress 覆盖更新)。**一次性拉全 §4.1 全部字段**（含 cover URL、business、oid 等后续所需），可整条 `raw_json` 兜底。产出：一个持续增长、不再被上限顶掉的本地 SQLite。**到此即为 Phase 1 终点，不含展示。**
- **Phase 2（展示 + 封面 + 搜索/筛选 + 需要观看）**：⑥ 本地 Web 类网页列表(可点击链接)；④ 封面下载缓存到本地目录；⑦ 关键词搜索 + 时间/类型筛选；**「需要观看」开关（基于已落库 progress/duration 直接算 <95%，步骤 ⑤ 已消除）**。
- **Phase 3A（功能扩展与体验优化 — 优先）**：规则引擎化（§3A.1）；「需要观看」闭环交互（标记已看/忽略，§3A.2）；深链 bilibili://（§3A.3）；浏览体验优化——类 B站网页端卡片布局/分组/性能（§3A.4）；数据呈现增强——归档标注/智能增量（§3A.5）。

## 8. Phase 1 实施结果（2026-07-22 实测）
> 本节记录 Phase 1 已落地并经真实数据验证的结果，用于修正上文假设、精简后续规划。完整工程代码见 `src/collector.py`、`config.example.json`。

### 8.1 已完成与工程状态
- `src/collector.py`：纯标准库（urllib + sqlite3，零第三方依赖）采集器；`config.example.json` 配置模板；`.gitignore` 已忽略 `config.json`（凭证）与 `data/`（用户数据）。
- 已**全量拉取并落库**；工程已上传 **gitcode**（`basic_597/BilibiliHistoryFinder`，PAT 已绑定到 `origin`，后续 push/pull/fetch 免输令牌；当前仓库为 **public**——gitcode 免费账号限制私有仓库，因凭证与数据均已忽略，无泄露风险）。

### 8.2 SESSDATA 获取 — 实测结论
- 浏览器 Cookie 中存在**多个同名 SESSDATA**（`.bilibili.com`、`.bilibili.cn`、`biligame.com`、`.huasheng.cn`）。
- 仅 **`.bilibili.com` 的 SESSDATA** 适用于 `api.bilibili.com` 历史接口（实测 `code:0`，登录态有效）。
- `.bilibili.cn` 为移动端子域、其余为游戏/花生等无关子域，本项目**不需要**。
- 结论：取 SESSDATA 认准 `bilibili.com` 这一条即可，填入 `config.json`（已被 gitignore）。

### 8.3 拉取数据实测（关键发现）
- 全量拉取：**41 页、1207 条**写入本地 SQLite。**已超过 B站官方约 1000 条上限**——本地留存价值被直接验证。
- 字段完整度（1207 条）：`bvid`、`author_name`、`cover`、`progress` 均有值；`duration` **1207/1207 有值**。
- ⚠️ **推翻原假设**：历史接口**实际返回 `duration` 视频总时长**（原以为"不返回、需补取"）。故「时长补全管线 ⑤」**被消除**，FR5「需要观看」可直接用现有数据计算，无需任何额外请求。

### 8.4 progress / duration 语义（已实现验证）
- `progress` = 已观看秒数；`duration` = 视频总时长。
- `progress = -1` 表示"已看完"（B站对看完的标记）。
- 「需要观看」判定：
  - 需观看：`progress >= 0` 且 `progress < 0.95 * duration`
  - 已看完：`progress = -1` 或 `progress >= 0.95 * duration`
- 实测样本：122/153s=79.7%、1468/1515s=96.9%，比例合理。

### 8.5 已修正的实现细节（采集器内已生效）
- **`business="all"` 是无效参数**：B站 cursor 接口不接受它（返回空列表、`ps:0`）。改为初始不传 `business`，跟随 cursor 返回的 `business` 翻页。
- **progress 防回退**：同一视频若某次抓到更小进度（如重头看一小段），不会把已看进度覆盖小——仅当 `progress=-1`（看完）或更大值才覆盖。（演进见 §12.2：已看完/已手动标记"不需要观看"即粘性不更新。）
- **view_at 取较大值、duration 用 COALESCE 保护**：避免时间回退；后续补充 duration 时重跑采集也不会清空。

### 8.6 对后续规划的影响
- Phase 3 的「时长补全管线」删除 → FR5 可前移至 **Phase 2**，与展示一起实现「需要观看」开关（见 §7）。
- 项目已"有真实数据可喂"——Phase 2 展示层可直接基于 1207 条数据开发联调。
- 最大风险（时长获取）已被实测消除，方案确定性显著提升。

## 10. 数据库更新策略评估（多场景）
> 用户关注点：采集器不能只做"新增拉取"，还要正确处理"重看导致顺序/进度变化""在 B站端删除/被裁剪"等更新场景。本节逐项评估当前 Phase 1 已覆盖与缺失，并落点各 Phase。

### 10.1 用户核心场景——"重看未看完的视频"：当前已正确覆盖 ✅
- 现象：重看同一视频 → B站返回**同 kid**、**更晚的 view_at**、**可能更大的 progress**。
- 当前逻辑（`collector.py` upsert，已实测）：
  - `view_at = MAX(excluded.view_at, history.view_at)` → 更新为更晚时间，UI 按 view_at 倒序即"跳到顶部"，顺序正确 ✅
  - `progress` 仅当 `-1`（看完）或**更大值**才覆盖 → 反映最新观看位置；若重头看了一小段（更小 progress）则保留较大值，**不回退** ✅
- 结论：该场景无需改动，已符合预期。

### 10.2 其他场景与缺口
| # | 场景 | 当前行为 | 缺口 | 建议落点 |
|---|---|---|---|---|
| S1 | 在 B站网页/App 删除某条历史 | upsert 只增改，不删 | 该条永久留本地且无"已不在 B站"标记 | 加 `archived_only` 标记：**全量同步**时未被本次返回的条目置 1（保留不硬删）；UI 显示"仅本地存档"徽标。永不硬删（留存即目的）（最终策略见 §12.3：⑤ 选 A 接受限制，增量不再更新 archived_only；当前已有 2 条被标） |
| S2 | B站超出 1000 条被裁剪 | 同上，我们保留 | 理想行为，但无法区分"被裁剪"vs"被删除" | 同 S1 标记；UI 一视同仁 |
| S3 | 每次都全量重拉 1207+ | 每跑从 cursor=0 拉全 | 每日自动化慢、易限流 | **增量同步**：拉到 `view_at < 上次同步时刻` 即停（重看必更晚、出现在顶部）。UI"立即同步"仍用全量（也抓删除/封面） |

## 12. 增量同步策略（最终决策，2026-07-23）
> 基于 §10 评估 + 多轮讨论确定，为**最终可执行版**（§10 保留评估过程）。核心：全量仅建基线、之后只增量；细化增量 upsert 字段替换规则与删除检测（⑤⑥）。

### 12.1 总体范式
- **全量同步 = 仅初始建基线**（一次性，无基线无法增量续拉）。
- **之后只做增量同步**（`--incremental`）：拉到 `view_at < 上次同步时刻` 即停。
- **完成判定**：以采集器结论文件 `completed` 为准（cursor.is_end / 空列表 / 增量边界），非子进程退出码。部分拉取 = 未完成，不 bump 数据版本（已落地）。
- **失败重试**：本次会话内最多 2–3 次、间隔退避；重试分叉——无基线→全量重试，有基线→增量续拉（每页持久化游标）；全部失败→提示"重试失败，等待下次手动同步"。

### 12.2 增量 upsert 字段替换规则（核心）
以 `kid` 为唯一键查重（视频的 `kid = archive_{aid}`，与 BV 一一对应但更稳定，且覆盖 pgc/直播/专栏；**BV 仅作展示/深链，不用于主键**）。命中已存在记录时：

| 字段 | 策略 | 理由 |
|---|---|---|
| `view_at` | **总是替换为新值**（正常增量返回的即最新观看时间；用 `MAX` 仅防极端乱序） | 用户明确要求"观看时间肯定替换新的" |
| `progress` | **粘性保护**：若 `stored.progress == -1`（已看完）或 `stored` 被手动标记"不需要观看"（Phase 3A.2 本地状态）→ **不更新**；否则当 `new.view_at ≥ stored.view_at` 时替换为新值（最新观看会话权威）；`new.view_at < stored`（乱序）→ 保留 stored | 已看完/已标记不应被"重头看一小段"降级 |
| `duration` | 保持不变（COALESCE 保护） | 同一视频时长稳定 |
| `title` / `author_name` / `cover` | **直接更新为当前 B站状态** | 视频可能改名、UP 改名、换封面；用户确认其余信息可直接更新 |

- 相对 §8.5 演进：原"progress 仅当 -1 或更大值才覆盖"升级为"已看完/已手动标记即粘性不更新"。
- ⑥ 加固：当 `new.view_at == stored.view_at` 时也比对 `progress`，若 `new > stored` 则更新（覆盖"仅进度变、时间未变"的盲点）。
- "如何区分需校验"：增量接口只回传游标之后的近期记录，每条返回记录天然需校验；校验 = kid 查 DB，无需全表扫描；`business` 仅用于 UI/深链，不进校验分支。

### 12.3 删除检测（⑤ = 选 A：接受限制）
- 增量接口不返回"在 B站端被删"的记录 → 无法自动发现删除。
- **决策**：增量模式**不更新** `archived_only`；`archived_only` 仅由初始全量基线（及未来若主动跑全量时）标记。UI 注明"存档状态仅初始全量校准"。**永不硬删**（留存即目的，见 §10 S1）。
- 未选"轻量对账扫描"方案 → 接受此限制，换取不周期全量/不对账的简洁性。

### 12.4 archived_only 现状与后续处理
- **数据层**：有列（`collector.py`）、有全量标记逻辑、服务端有 `archived_only=1` 筛选参数。
- **当前数据**：**已有 2 条被标记为 archived_only=1**（来自某次全量同步时未被 B站返回，即已超出 B站可见范围或被删）——说明该字段确实在起作用。
- **UI 层**：有"含存档"开关按钮（点击可筛出这 2 条）；但卡片**未渲染"仅本地存档"徽标**（最近一次 UI 重写删除了徽标）。
- **后续处理（归入 Phase 3A.5 数据呈现增强，不单独成阶段）**：① 补回卡片"仅本地存档"徽标；② UI 注明"存档状态仅初始全量校准"。增量模式下 archived_only 不再变化，处理量极小。
