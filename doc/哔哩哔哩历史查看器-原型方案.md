# B站历史记录查看器 — 原型方案

> 文档状态：讨论稿（技术路线未定，可选方案待逐项讨论）
> 日期：2026-07-22
> 关联：需求见《哔哩哔哩历史查看器-需求评估.md》
> 说明：本文件聚焦"如何做"（可行性、技术栈、MVP、分阶段、风险）；具体可选方案见 §6，仍在讨论中。

## 1. 可行性结论
**可以快速开发原型，且最终能完成预期功能（含一项固有局限）。** 核心数据通路（SESSDATA + cursor 分页接口 + 本地存储）已确认可行；展示与筛选均为标准前端工作；主要不确定点（时长获取）有成熟对策。预计可分阶段交付，MVP 即可跑通"留存 + 类网页展示 + 搜索 + 基础筛选"。
- **固有局限（必须接受）**：本地留存只能"从现在起"生效。B站端已被 1000 条上限顶掉的**过去历史无法恢复**——无论哪种方案都救不回。原型的价值是"以后一条不漏"。
- **能达成的功能**：FR1 突破上限留存、FR2 类网页展示、FR3 搜索、FR4 筛选、FR5「需要观看」、FR6 自动化——全部可在本方案框架内实现。

## 2. 流程完整性评估（是否遗漏步骤）
### 2.1 端到端流程（完整步骤链）
```
① 凭证获取   → 取 SESSDATA（浏览器 F12 / 后续扫码）
② 拉取历史   → 调 history/cursor，用 max/view_at/business 翻页，直到无更多
③ 写入存储   → 按 kid 去重写入 SQLite；注意 progress 更新语义（见 2.3）
④ 封面处理   → 存远程 URL（Phase1）【或】下载缓存到本地（后续，离线/永久）
⑤ 时长补全   → 对候选视频补 view 接口取 duration，缓存（用于进度%）
⑥ 展示       → Web 单页 或 MD 导出
⑦ 搜索/筛选  → 关键词 + 时间/类型 + 「需要观看」开关
⑧ 打开视频   → 由 bvid/uri 生成链接/深链（影响展示实现，见 §6.4）
```
### 2.2 当前方案相对完整流程的遗漏 / 薄弱点
| 步骤 | 原方案状态 | 结论 |
|---|---|---|
| ④ 封面缓存 | 仅存远程 URL，未本地化 | **遗漏**：离线/封面失效时不显示；应在后续阶段补"下载落盘" |
| ⑤ 时长补全 | 仅列为风险，未作为一等管线 | **薄弱**：它是 FR5 的前提，需明确为独立步骤（缓存+限速+批量） |
| ③ progress 更新去重 | 仅说"去重"，未定义更新语义 | **遗漏**：同一 kid 二次观看 progress 变大时应**覆盖更新**，而非简单跳过 |
| ⑧ 打开视频 | 未提及 | **影响展示**：卡片须是可点击链接，原型即预留 bvid→URL，深链留后续 |
| ① 凭证刷新 | 仅说"手动重填" | 可接受为 MVP；后续可加扫码/过期提示 |

### 2.3 功能达成度（对照需求 FR）
- FR1 留存 ✅（仅覆盖从现在起）；FR2 展示 ✅；FR3 搜索 ✅；FR4 筛选 ✅；FR5 需要观看 ✅（依赖 ⑤ 时长补全）；FR6 自动化 ✅（任务计划）。
- 唯一"不能"的是恢复已丢失的过去历史（非方案缺陷，是 B站服务端限制）。

## 3. 推荐技术栈（轻量、低依赖）
- **采集 / 服务**：Python（Flask 或内置 `http.server` 起本地 Web）；标准库即可完成 HTTP 请求与 SQLite。
- **存储**：SQLite（两张表：`history` 全量历史；`video_meta` 缓存 `bvid → 时长`）。封面用"文件路径/URL 字段"，不塞 BLOB。
- **前端**：原生 HTML / CSS / JS 单页，类 B站历史卡片列表；无需构建工具。零框架、零 npm。
- **调度**：Windows 任务计划程序每日跑采集脚本；或采集作为常驻后台线程。
- **导出（后续）**：Python 生成 Obsidian 兼容 Markdown，作为零依赖视图。

### 3.1 开发环境依赖与检查

#### 3.1.1 分阶段依赖清单
- **Phase 1（数据采集 + SQLite 落库）**
  - Python ≥ 3.10，仅用标准库：`urllib.request` / `sqlite3` / `json` / `datetime` / `os` / `argparse`，**无需 pip 安装任何第三方包**。
  - 网络可访问 `api.bilibili.com`（HTTPS）。
  - 凭证：登录态 Cookie 中的 `SESSDATA`（浏览器 F12 → Application → Cookies 获取）。
- **Phase 2（本地 Web 展示 + 搜索/筛选）**
  - 复用 Phase 1 的 Python，用标准库 `http.server` 起本地静态服务（**零依赖、零构建**）。
  - 任意现代浏览器打开 `http://127.0.0.1:PORT`。
  - 前端：原生 HTML/CSS/JS，**无 npm、无框架、无 CDN**（可完全离线运行）。
  - *可选*：若改选 Flask 等框架则需 `pip install flask`（不推荐，徒增依赖）。
- **后续阶段（Obsidian 导出 / 自动化 / 封面缓存）**：无额外依赖，自动化用 Windows 任务计划程序即可。

#### 3.1.2 可选 / 增强组件（非必需）
- **Node.js**：仅当后续想加前端工具链（打包、ESLint）才需要；MVP 不用。
- **Git**：版本管理推荐，但非运行必需。
- **Python venv**：纯标准库项目不必建虚拟环境；仅当引入第三方包（如 Flask）时再建。


## 4. 阶段目标概览
> **Phase 1 只做"数据"**：把所有后续步骤会用到的字段一次性拉全并落库；展示、封面、筛选都往后放。目的是先把最不可逆的"留存"做扎实——数据一旦每天在跑，就不会再被官方上限顶掉。

- **Phase 1（仅数据）**：采集器拉全量历史 → SQLite，按 kid 去重且**覆盖更新 progress**。**一次性拉全后续所有步骤需要的字段**（见 §4.1），不做展示、不下封面。
- **Phase 2（展示 + 封面 + 搜索/基础筛选）**：本地 Web 类 B站列表（封面 + 标题 + UP主 + 时间 + BV，可点击链接）；封面下载缓存到本地；关键词搜索 + 时间/类型筛选。
- **Phase 3（需要观看 + 补全 + 打磨 + 自动化）**：时长补全管线（算进度%）→「需要观看」筛选；规则扩展框架；深链"在 App 打开"；UI 打磨；任务计划自动化；导出 Obsidian 兼容 MD。

### 4.1 Phase 1 必须落库的字段（后续步骤所需，一次拉全）
| 字段 | 来源 | 后续用途 |
|---|---|---|
| `kid` | 历史条目 | 唯一键，去重/覆盖更新 |
| `title` / `show_title` | 历史条目 | 展示、搜索 |
| `author_name` / `author_mid` | 历史条目 | 展示、按 UP主搜索/筛选 |
| `view_at` | 历史条目 | 展示、时间筛选、排序 |
| `bvid` | `history.bvid` | 展示链接、打开视频、时长补全键 |
| `oid` / `epid` / `cid` | `history` | pgc/live/article 定位、打开视频 |
| `business` | `history.business` | 类型筛选（archive/pgc/live/article） |
| `cover` / `covers[0]` | 历史条目 | Phase2 下载封面用（先存 URL） |
| `progress` | 历史条目 | 「需要观看」判定（已看秒数） |
| `duration`(若接口返回) | 历史条目 | 有则直接算进度%，省去补全 |
| `uri` | 历史条目 | 打开视频兜底链接 |
| `tag_name` / `badge` | 历史条目 | 后续规则扩展可用 |
> 原则：**宁可多存不漏存**。Phase 1 把原始 JSON 里所有可能有用的字段都落库（可整条 `raw_json` 也存一列做兜底），避免后续想加功能时"当初没拉"而要重刷。

## 5. 工作量估计（量级）
- Phase 1（仅拉取 + 完整落库）：小，核心接口已验证。
- Phase 2（展示 + 封面缓存 + 搜索/筛选）：小 ~ 中。
- Phase 3（需要观看 + 时长补全 + 规则扩展 + UI 打磨 + 自动化 + 导出）：中。
- 总体：可作为"几天内可交付原型"的项目，非重型工程。

## 6. 可选方案讨论（待定）
> 本节记录原型实现路线上的多种可选方案，逐项对比后再定。以下 6.1–6.4 为本次补充，6.5–6.9 为既有待定项。

### 6.1 拉取：自研 vs 参考 BilibiliHistoryFetcher
- **MVP 自研即可**：cursor 接口清晰、分页简单，自写约百行即可跑通，无外部依赖。
- **后续参考开源（BilibiliHistoryFetcher 等）的定位**：当作"健壮性对照清单"而非直接依赖——重点借鉴其对多 `business` 类型（archive/pgc/live/article）、分页边界、错误码（如 -101/-111）、时长补全与限流的处理，避免自研遗漏边界。
- **结论建议**：不自接第三方库做核心，但实现后与其对一遍覆盖度。

### 6.2 存储：SQLite 与图片；是否要接 Obsidian 等轻量存储
- **SQLite 支持图片吗**：技术上可用 BLOB 存二进制，但**不推荐**——会撑大数据库、拖慢查询。封面最佳实践是"文件落盘（封面图存本地目录）+ SQLite 存路径/URL"。**Phase1 只存远程 URL（不下载）**；**Phase2 加"下载缓存到本地"**实现离线/永久显示。
- **Obsidian / 其他轻量存储的定位 = 导出目标，不是存储替换**：SQLite 保持为**可查询真源**；后期加一个"导出为 Obsidian 兼容 Markdown"模块（每条约 note：frontmatter 含 BV/UP主/时间/标题，正文嵌封面 + 链接）。不要试图把活数据直接塞进 Obsidian vault——会破坏查询与去重。
- **结论建议**：存储引擎不变（SQLite + 封面文件）；Obsidian 通过导出模块接入。

### 6.3 展示：前端是否必须用 JS？纯 MD 可行吗？
- **实时搜索 / 筛选必须 JS**：FR3/FR4/FR5 是交互式的，纯静态 MD 无法在浏览器内实时过滤。
- **纯 MD 的可行路径（零依赖）**：由**脚本预过滤**后生成多份 MD 视图（如 `全部.md`、`需要观看.md`、`按UP主.md`、`按日期.md`），用任意 MD 阅读器（Obsidian / VS Code）打开。局限：无实时搜索框，筛选靠"打开对应文件"；且天然与 6.2 的 Obsidian 方案统一。
- **结论建议（双轨）**：
  - 主界面：原生 JS 单页 + 本地 Web（零框架、零构建，已满足"尽量依赖少"）；
  - 后续：加 MD 导出，作为零依赖 / Obsidian 视图。两者不冲突。

### 6.4 打开视频（不在原型，但影响展示实现）
- 数据已含 `uri` / `bvid`，可生成：网页 `https://www.bilibili.com/video/{BV}`；App 深链 `bilibili://video/{BV}`（手机端直接唤起 App）。
- **对展示的影响**：原型阶段就应把每张卡片渲染为 `<a>` 链接（而非纯文本），数据模型确保保留 `bvid`。"在 App 打开"深链按钮留到后续阶段，但结构现在就要留好口子。
- **结论建议**：原型即做可点击链接；深链按钮列入 Phase 3 打磨。

## 7. 分阶段路线（Phase 1 收敛为"仅数据"）
- **Phase 1（仅数据 / 最优先）**：① 凭证→② 拉取→③ 写入(按 kid 去重 + progress 覆盖更新)。**一次性拉全 §4.1 全部字段**（含 cover URL、business、oid 等后续所需），可整条 `raw_json` 兜底。产出：一个持续增长、不再被上限顶掉的本地 SQLite。**到此即为 Phase 1 终点，不含展示。**
- **Phase 2（展示 + 封面 + 搜索/筛选）**：⑥ 本地 Web 类网页列表(可点击链接)；④ 封面下载缓存到本地目录；⑦ 关键词搜索 + 时间/类型筛选。
- **Phase 3（需要观看 + 补全 + 打磨 + 自动化）**：⑤ 时长补全管线(批量+限速+缓存)→「需要观看」筛选(进度<95%)；规则扩展框架；⑧ 深链"在App打开"；UI 像素级打磨；FR6 任务计划；导出 Obsidian 兼容 MD。
