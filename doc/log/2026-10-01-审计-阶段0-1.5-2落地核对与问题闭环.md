## 四、代码问题（按严重度）

### 🔴 A1 · `no_baseline` 粘住 → `/api/sync` 此后**每次都全量**，且绕过冷却

- **事实**：全仓只有两处写 `sync_state["no_baseline"]` —— `server.py:1537`（置 `True`）、`server.py:1547`（置 `False`），**都在 `_analyzer_incremental_with_fallback()` 内**。
- `/api/sync` 一旦命中 **R2**，走的是 **`full` 直连分支**（`_forward_fetcher("/fetch/bili-history")`），**不经过该 helper** → 标记**永不清除**。
- 实测：`decide_sync_plan(state{last_incremental_no_baseline:True})` → `full`「缺基线，自动升级为全量」；把标记清掉后同一状态 → `skip`「刚刚跑过（100 秒前），冷却中」。
- **加重项**：**R2 排在 R4（冷却）之前** → 冷却对 R2 完全不生效。
- **后果**：回退发生过一次后，**每点一次「同步数据」都跑一次全量**，无冷却、无提示、用户无感。
- **为什么测试没抓到**：`dev/regression_fallback.py` 新增的 `/api/sync` 组用 `policy.sync="incremental"` 覆盖把 R2 **短路**了（覆盖排在 R1–R4 之前），并每例前手动 `sync_state["no_baseline"]=False`。
- **建议**：全量成功分支（或更好的位置：`_after_data_pull()` 成功即清）显式清 `no_baseline=False`；并给 R2 补一条「冷却内也已全量过 → 不必再全量」的收敛，或把 R2 移到 R4 之后。

### 🔴 A2 · `store._ANALYZER_USABLE` 是**没有失效点**的全局缓存

- **事实**：`probe_connection()` 只在两处被调用 —— `GET /api/capabilities`（`server.py:1375`）与 `POST /api/sync`（`server.py:2097`）。**前端从不调用 `/api/capabilities`**（前端走 `/api/fetcher-health` / `/api/sync`）。
- 因此：一次「Analyzer 不可达」的同步之后，`_ANALYZER_USABLE = False` **长期粘住** → 之后**所有** `/api/query` / `/api/history` / `reload_all()` 在 `auto` 模式都**跳过 Analyzer 年表**，**即使 Analyzer 已重新启动**；而同一时刻横幅（独立轮询 `/api/fetcher-health`）会显示「已连接」→ **横幅说连着、数据却是旧快照**，`effective` 也会一直报 `local`。
- **更要紧的是「跳过」跳过的是可读且可能更新的文件**：本地库只是**迁移那一刻**的快照；此后 Analyzer 侧的新记录、新备注（`POST /api/remark` 写 **Analyzer 主库**）**都不进本地库**（运行期没有任何回灌机制）。**旧实现会照读 Analyzer 文件**，所以这些更新原本是可见的 → 新逻辑在「Analyzer 服务不可达」这条路径上**静默降级成旧快照**。
- `store.py:277` 的注释把「阶段 0 迁移后本地库已含 Analyzer 全部记录（合并结果不变）」写成**不变量**，实际只是**迁移时点**成立。
- **建议（择一或组合）**：① 判据改用「Analyzer **库文件是否可读**」而非「HTTP 是否可达」（HTTP 可达性才决定"能不能抓"，与"能不能读"是两件事）；② 给缓存加**失效点**（如 `/api/fetcher-health` 也发布结论，或 `reload_all()` 前不采用该缓存，或加 TTL）；③ 至少补一句注释说明「该等价关系仅在迁移后、且 Analyzer 侧无新写入时成立」。

### 🟠 A3 · `/api/local/delete` 在 `auto` / `analyzer` 形态下**看不出效果**

删的是本地库行；合并视图 = `Analyzer ∪ 本地` → 只要 Analyzer 可达，被删记录**立刻从主源回来**。
→ `现状.md` §7.2 未注明「仅对 `owner=finder` 的独立形态有意义」。建议加约束（后端在 `owner=analyzer` 时直接拒绝并说明原因），或至少写进文档。

### 🟠 A4 · `/api/sync` 新增的 `blocked` / `skip` 文案**到不了用户**

`app.js` 的同步按钮是 `fetch("/api/sync", {method:"POST"}).then(() => pollSync())` —— **完全忽略响应体**。`blocked`（HTTP 200 + `{ok:false, blocked:true, reason}`）时既不弹提示、也不写进度文件 → 用户观感仍是「点了没反应」。
server 端注释「不再『点了然后失败』：先把阻断原因讲清楚」**要等阶段 4** 才兑现。建议：至少把 reason 落一条到日志/进度文件，或提前让前端 toast 一下。

### 🟡 A5 · `/api/export/local/db` 裸读文件字节流

- 直接 `open(...,"rb").read()` 回吐，**没有** `sync_state["running"]` 闸门（`/api/local/delete` 有），且与 `POST /api/backup`（用 `sqlite3` 在线 `backup()`）**不一致**。
- 本地库非 WAL（目录下无 `-wal`/`-shm`），但 Finder 自身抓取正在写时仍可能取到不一致副本。
- 建议：改走 `sqlite3.backup()`（与 ⑤ 备份同源），或至少加 running 闸门。

### 🟡 A6 · `_probe_finder_sessdata()` 把 HTTP 错误报成「网络不可达」

`urllib.error.HTTPError` 是 `URLError` 的子类 → 被第一个 `except` 接住，412 风控会显示成「探测失败（网络不可达）：HTTP Error 412」。
既然已经有 `collector.classify_http_status()`，这里应分流（`HTTPError` 先按状态码分类）。

### 🟡 A7 · `probe_connection(with_sessdata=False)` 的 analyzer 凭证段 reason 误导

`else` 分支写死 `{"state":"unknown", "reason":"Analyzer 不可达"}` —— 当 `with_sessdata=False` 且**实际可达**时该 reason 是错的。`/api/sync` 现在固定用 `with_sessdata=False`，这个 probe 会随 `plan` 一起回给前端。

### 🟢 A8 · 小项（不影响正确性）

| 项 | 说明 |
| --- | --- |
| `store.load_raw_records()` | `get_source_mode()` 被读**两遍**（`mode` 与 `_pick_sources` 内各一次）→ 理论上可读到两个值 |
| `_analyzer_incremental_with_fallback()` | `inc` 不 ok（Analyzer 不可达、**没结论**）时也把 `no_baseline` 置 `False` —— 语义上应是「保持原值」 |
| `collector.run()` | `last_kind` 初值 `"retry"`，成功路径不更新它（无实际影响，但读起来像遗漏） |
| 退避公式 | `max(min(5, attempt*2), 20*attempt)` 在 `attempt≥1` 时**恒等于** `20*attempt` → 可简化（当前 `max_attempts` 固定，无风险） |
| `collector.delete_records()` | 顺带 `init_db()`，本地库不存在时会**凭空建空库**；且与 `store.delete_skip_states()` 是**两个独立事务** → 可能只成功一半 |
