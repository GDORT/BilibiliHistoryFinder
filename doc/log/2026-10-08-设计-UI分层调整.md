## 一、诊断：现状的三个问题

读 `index.html` 顶栏实测（2026-10-08）：

| # | 问题 | 具体表现 |
| --- | --- | --- |
| **1** | **15 个按钮平铺一行** | 日常的「搜索/设置/同步」与一年用一次的「健康探测/下载整库」**权重完全相同** |
| **2** | **①–⑪ 序号暴露开发史** | 编号跳号（没有 ⑦）、`⑩⑪` 是图片功能 —— 联调期逐步追加的痕迹，暴露给用户无意义 |
| **3** | **两件不同的事混在一排** | 「续看规则」（Finder 自身）与「健康探测」（调 Analyzer）**视觉上无区分** |

⚠️ **要说清**：这不是"设计失败"，是**功能长出来的必然结果** —— 阶段 0–5 一路加功能，顶栏没重排过。
**此刻正是整理的时点**（功能已定型）。

## 二、三条原则（用户明确要求）

| # | 原则 | 落地含义 |
| --- | --- | --- |
| **P1** | **原有功能按 B 站网页版排版** | 浏览层完全照 B站历史页：**分类 tab → 状态筛选 → 搜索 → 时间侧栏 → 卡片列表** |
| **P2** | **新加功能分离出来** | **Finder 自身功能**（续看规则、批量标记、同步）与**调用 Analyzer 的功能**（抓取/探活/自检/备份/导出/图片）各自独立成组 |
| **P3** | **不合并、入口保持独立** | ⭐ **禁止**「增量同步＋重新同步合并」、「导出 Excel＋下载整库合并」、「备份＋查看备份合并」。**每个功能仍是独立按钮 / 独立 id / 独立 title** |

⚠️ **P3 为什么重要**：合并会让用户失去"这个功能到底被调用了没有"的判断力 —— 本项目大量功能**依赖 Analyzer 可用性**（独立形态下部分能力置灰）。合并后用户看到一个灰按钮，根本不知道是哪几个能力没了。**入口独立 = 状态可辨。**

## 三、目标结构：标准 app shell

> ⭐ **第 2 版的核心理念**：**不做定制组件**。用最常见的三段式 shell ——
> **顶栏（搜索 ＋ 3 个图标）／ 内容区（分类 tab ＋ 状态筛选 ＋ 列表）／ 左时间侧栏**。

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏   [标题]   [🔍 搜索……]              [↻同步] [⚙设置] [⋯更多]│
├────────┬─────────────────────────────────────────────────────┤
│ 时间   │  内容区                                              │
│ 侧栏   │  ┌ 分类 tab：综合 · 视频 · 直播 · 专栏 ┐              │
│ 今天   │  ┌ 状态筛选：全部 · 需要观看 · 已跳过 · 已搁置 ┐       │
│ 昨天   │  ┌ 操作：筛选 · 高级筛选 · 续看规则 · 批量标记 ┐       │
│ 近一周 │  ┌───────────────────────────────────────┐          │
│ …      │  │ 卡片列表（封面色块＋标题＋UP＋时长＋进度）│          │
│        │  └───────────────────────────────────────┘          │
└────────┴─────────────────────────────────────────────────────┘
        ⋯更多 ▾  → 下拉菜单（分组，见 §五）
```

### 三个区域各自要点

| 区域 | 装什么 | 谁可见 |
| --- | --- | --- |
| **顶栏** | 标题 · 搜索 · **↻ 同步**（Finder 自身，高频）· **⚙ 设置** · **⋯ 更多** | 所有人，常驻 |
| **内容区** | 分类 tab · 状态筛选 · 列表级操作（筛选/高级筛选/续看规则/批量标记）· 卡片列表 | 所有人，常驻 |
| **⋯ 更多 菜单** | **调用 Analyzer 的低频运维**（抓取/探活/自检/备份/导出/图片） | 需要时展开，默认收起 |

⭐ **关键判断**：**日常高频动作不进菜单**（"需要观看""续看规则""批量标记""同步"留在明面），
**只有低频运维进「⋯ 更多」**。这既满足 P2 的"两类分离"，又是最主流的"overflow menu"做法。

## 四、方案对比与取舍

| | **A 仅分组折叠** | **B′ 标准 shell（推荐）** | **C 完整侧边导航** |
| --- | --- | --- | --- |
| 做法 | 顶栏按分组加折叠箭头 | 顶栏精简（搜索＋3 图标）＋ 分类/状态沉入内容区 ＋ 运维进「⋯更多」 | 左侧加竖导航，三层各一入口 |
| 改动量 | 最小 | **中**（顶栏重排 ＋ 按钮归位） | 最大（动布局骨架） |
| 是否满足 P1/B站排版 | ✗ 仍是"工具型顶栏" | ✅（内容区就是 B站骨架） | ✅ |
| 是否满足 P3 不合并 | ✅ | ✅ | ✅ |
| 定制组件 | 无 | **无**（菜单是原生/clip-path 常规做法） | 多 |
| 风险 | 低 | 中（**只搬位置、不改 id**，见 §六） | 高（响应式＋布局重排） |

**推荐 B′**，理由：① 真正满足 P1；② **零定制组件**（比第 1 版的"抽屉"更省）；③ 顶栏从 15 个降到
**1 搜索 ＋ 3 图标**，视觉负担最小；④ 窄屏由「⋯更多」天然吸收（§八 的第 3 问自动消解）；
⑤ 只动前端布局，不动后端、不动端点。

**C 的问题**：本项目只有"一个页面"，为单页做竖导航属过度结构，且窄屏会挤。

## 五、顶栏右侧两个入口（＝ 原"工具箱"，但改为菜单）

```
[⚙ 设置] → 设置面板（现有设置内容原样搬入；形态/后端地址等）
[⋯ 更多] → 下拉菜单：
   【抓取与同步】 增量同步 · 重新同步 · 实时更新（催分析） · 本地库
   【健康与诊断】 健康探测 · 数据自检 · 应用变更     ● 连接状态点
   【备份与导出】 本地备份 · 查看备份 · 导出 Excel · 下载整库
   【图片与维护】 图片状态 · 下载图片 · 停止下载
```

- **每一行都是独立按钮 / 独立 id / 独立 title**（P3）。
- ⭐ **「增量同步」与「重新同步」必须分开**（虽调同一端点，语义不同：一个增量、一个不要求增量）。
- ⭐ **`①–⑪` 序号全部去掉**（诊断问题 2）。
- **「设置」归 ⚙（顶栏右侧）** —— 第 1 版曾把它画进抽屉，本版修正：设置主要是 Finder 自身配置。
- 连接状态点跟随「健康与诊断」组；Analyzer 不可达时菜单内按钮置灰，层 1 横幅照旧提示。

## 六、⚠️ 落地约束与连带影响

### 6.1 实施第一原则：**只搬位置、不改 id**（⭐ 本版最重要的一条）

`CAP_DOM`（能力→DOM 映射）与 A1 的基线断言都**按 id 选择器**工作。因此：

> **所有现有按钮 / 输入框的 `id` 一律保持不变**，只改它们的**父容器与摆放位置**。
> 这样 `dev/test_capabilities.py::T2.8`（选择器存在性）与 `dev/e2e/smoke_frontend.py` 的
> `G2.0b`（`BASELINE_SELECTORS` 字面基线）**都不会因为改 UI 而变红**。

### 6.2 可能仍要同步的护栏

| # | 连带影响 | 处置 |
| --- | --- | --- |
| **1** | **`G2.0b` 基线** | 只要**不改 id、不删元素**，就不红；若确需改 id → **同步更新** `BASELINE_SELECTORS` |
| **2** | **`G2.0` 锁 `UNAVAILABLE_MODE=='gray'`** | 本稿不动该常量（阶段 6 才动，见 §七） |
| **3** | **`T2.8` 选择器存在性** | 元素搬进「⋯更多」菜单后**仍在 DOM**（`display:none` 不影响存在性）→ **不红** |
| **4** | **菜单展开态** | 若 A1 要验"展开菜单后按钮可见"，需补一条"菜单展开"断言；**默认收起不影响**现有"直接喂函数"的断言 |
| **5** | **响应式断点** | 「⋯更多」本身就是窄屏收敛手段 → **无需单独定断点** |
