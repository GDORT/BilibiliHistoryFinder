## 1. 问题诊断

现象：文档越来越多、即便已尽量归档仍吃力，而项目本身很小。

根因不是"文档数量"，而是**副本数量**：同一个事实被抄写在多份文档里，且所有文档共享同一种"现在时"语气，读者无法判断哪份为准，于是必然漂移。

实证（本轮审查已抓到，见 `log/` 冻结后的《代码设计与风险审查》§8.4，共 8 条一致性债）：

| 典型债 | 形态 |
| --- | --- |
| `except` 计数（110 / server 80 / store 13） | 同一组数字抄在 §2 / §3.2 / §5.2 / §7.3 四处，代码一改全部过期 |
| 能力数 `8` vs `CAPABILITY_KEYS` 实际 7 项 | 跨文档表述不一致 |
| "接入 9 个点" | 源头是**代码注释**里的错误计数，反向传播进多份文档 |
| `T7` 归属、`L29` 与 §9 自相矛盾 | 同一事实两处定义，各自演化 |
| `store.py` 行号（53–98 / 181–190 / 195 / 1022…） | 行号是"修复前快照"，代码 +621 行后全部失效 |

**结论**：数量不是问题，**副本**是问题。每多抄一份，未来就多一个需要同步的失败点。

## 5. ADR 规范

文件名：`doc/adr/NNNN-短标题.md`，模板固定六段。

```
# NNNN · <一句话决策>
- 状态：已接受 | 已取代（被 NNNN）
- 日期：YYYY-MM-DD
- 背景：为什么必须做这个决定（2–3 句）
- 决策：一句话
- 理由：为什么不选另一条路
- 影响：谁要跟着改
```

**规则**：一条决策一页，**永不修改**。被推翻时在新 ADR 里写 `状态：已取代（被 NNNN）` 并回指旧页，旧页只加一行状态。

好处：以后不必再去《待定项与流程影响》的 §9.1/§9.2 考古"当初为什么这么定"。

## 6. 四条铁律（止住出血的部分）

1. **事实只写一次**：能力数、端口 `8765`、`ANALYZER_DB` 路径、`PAGE=60` 等，只在 `现状.md` 定义；其余文档一律**链接引用**，不复制。§1 表中的债，绝大多数由这一条直接消灭。
2. **文档头三行元信息**（见 §4）。
3. **轮次记录剪切而非积累**：`待办.md` 只留未完成；做完的剪到 `log/`。
4. **闭环即冻结**：审查 / 评估类文档一旦所有条目都有处置结论 → 移入 `archive/`；新发现**开新报告**，不追加章节。

## 7. 前置条件与执行顺序

### 7.1 与代码状态的关系（推荐：**先固定代码，再重构文档**）

重构文档前，应先把当前代码状态提交固定为一个干净基线，理由：

1. **diff 可读性**：文档重构会大量移动 / 改写文件。若代码改动仍未提交，`git diff` 会把「代码差异」与「文档搬运」混在一起，无法分辨。
2. **参照系固定**：`现状.md` 里的行号与事实（如审查稿 §8 的 `server.py:1809`）**绑定当前代码快照**。先固定代码＝先固定参照系；否则重构后无法判断这些行号是否还准。
3. **可回退**：文档重构出错需要回退时，工作区若同时有代码改动，回退会误伤代码。
4. **元信息头**：§4 的 `@<短commit>` 需要一个 commit 才写得出来。

因此推荐顺序：**提交代码 → 文档重构（单独成 commit）**。

例外情形：若近期还计划做《代码设计与风险审查》§8.5 的代码修复（如 `C-H3` 前端一行改动），则**先做完这些修复再提交**，避免文档刚冻结、行号又失效。
