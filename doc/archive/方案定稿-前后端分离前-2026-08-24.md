## 1. 需求与差异化壁垒

### 1.1 需求本质
不是「再做一个历史抓取器」，而是「一套历史续看 / 筛选分类的规则引擎」。核心价值在**分类逻辑**，不在采集。B站官方历史接口仅保留最近约 1000 条 / 3 个月且滚动覆盖，因此：
- 采集交给成熟的 Analyzer / Fetcher（或用户手动拉取）；
- 我们专注做「续看三视图 + 结构化规则 + 可解释跳过」这一被市场验证为缺口的细分。

### 1.2 必须保留并沉淀的差异化壁垒（跨形态复用）
以下逻辑是项目真正壁垒，与 B站机制无关，须抽离为「与语言无关的算法规格 / 可移植模块」（Python 当前可用，JS 待移植），供 D / A / B 任意路线复用：
- `needs`（待续看）/ `skipped`（已跳过）/ `stale`（久未动）三视图，基于 `progress`；
- `auto_skip` + **理由绑定**（可解释性，优于纯隐藏）；
- 单活跃规则 + 多组条件 + 冲突校验 C1/C2/C3；
- `business` 预设一键加入（archive / live / article / pgc）；
- `dirty_count` 增量感知（自上次应用以来新增未套用）。

## 2. 数据源与接入方式选型

### 2.1 2个数据源现状（实测校准，2026-08-24）
| 源 | 位置 | 表结构 | 体量 | 角色 |
|---|---|---|---|---|
| **Analyzer** | `D:\Program Files (x86)\BilibiliHistoryAnalyzer\output\bilibili_history.db` | 按年分表 `bilibili_history_YYYY`，**34 列** | 2813 条（2020–2026） | **主源（read-only 直连）** |
| **Finder 自有** | `D:\Programs\Share\BilibiliHistoryFinder\data\bilibili_history.db` | 单表 `history`，27 列 | 2865 条（近期窗口） | 补充源 |

- 两源互非超集，**合并唯一集 = 3278 条**（Analyzer 2813 + Finder 独有 465，按 `(bvid,view_at)` 去重）；Analyzer 含 Finder 永远抓不到的 2020–2025 深历史。Finder 库默认不运行，仅作兜底备份源。
- **canonical `derived` 以 Analyzer 34 列为基准**（最完整 B站 元数据投影）；Finder 多出的仅是分类层与同步簿记，且其 `raw_json` 实测仅 23 键（缺 `business/oid/bvid/cid/page/part/dt/main_category/remark`），**不是真·原始响应权威层**。

### 2.2 接入 Analyzer 的连接方式选型（如何接？有哪些选择？）
均映射进 canonical `derived`（以 Analyzer 34 列为基准，映射量最小）：

| 选项 | 接入方式 | 需起 Fetcher | 数据新鲜度 | 与 Analyzer schema 耦合 | 开发量 | 推荐度 |
|---|---|---|---|---|---|---|
| **① read-only 直连 SQLite（方案 B）** | `file:...?mode=ro` 打开 Analyzer 库，跨年表 `UNION` | 否 | = Analyzer 末次同步 | 强（年表分片 + `_fts`） | 最小 | **已验证·主源（推荐）** |
| **② 调 Fetcher REST API（路径 A）** | `server.py` 瘦适配器，`GET /history/all` + `/history/search`，`X-API-Key` | 是（常驻） | 常新（可触发同步） | 弱（API 契约稳定） | 小 | 常新升级版 |
| **③ 混合（SQLite 读 + API 触发同步）** | 平时读 SQLite 保性能，需刷新时调 API 触发增量再读 | 是（按需） | 常新（按需） | 中 | 中 | 后期优化 |

**选项细节**：
- **① 直连 SQLite**：跨 `bilibili_history_2020…2026` 做 `UNION ALL`，直接拿 34 列原生形状，几乎零映射；跨进程读用只读模式 + 短事务规避写入锁。**最大风险**：Analyzer 改表 / 加年表会断查询——适配器须动态枚举 `bilibili_history_%` 基表（**排除 `_fts` 全文虚拟表**，实测 `SELECT *` 会因 FTS 虚拟表报错）。
- **② 调 Fetcher API**：`GET /history/all?page=&size=&business=&date_range=` 跨年全量分页，返回 `data.records` 含完整字段；可另调同步接口触发增量，拿到比直连 SQLite 更新鲜的全量。CORS 对 `server.py` 服务端调用无影响。
- **③ 混合**：首版不必，待「常新全量」成为刚需再上。

### 2.3 能否替代官方 BiliHistoryFrontend（源码评估结论整合）
> 背景：官方 BilibiliHistoryFetcher（FastAPI `:8899`）是数据后端，**打包产物即用户本机的 `BilibiliHistoryAnalyzer.exe`**；官方 BiliHistoryFrontend（Vue3+Tauri）是它的纯前端。
> 评估依据：已置本地的真实源码副本 `doc/BiliHistoryFrontend-master/`（前端）与 `doc/BilibiliHistoryFetcher-master/`（后端），**仅读源码、不运行**。
> 核心问题：**我们的网页+服务能否替代这个官方前端？**

#### 2.3.0 主结论（一句话）
**能完整替代，且是「功能子集」级别的替代。** 官方前端没有任何独占能力——它是 Fetcher/Analyzer 产物的「显示器 + 遥控面板」，不掌握数据、不掌握控制逻辑、不掌握凭证。我们工程已具备它的全部展示能力（且筛选更强），唯一缺的「触发分析」只是 Fetcher 后端接口，加一层转发即可；Analyzer 是否在运行只影响「能否触发新分析」，不影响「能否替代前端」。

#### 2.3.1 官方前端的真实架构（源码实证）
- **纯前端壳，零后端逻辑**：`src-tauri/tauri.conf.json` 仅窗口/打包配置，无内嵌 HTTP server；`lib.rs`/`main.rs` 为标准 Tauri 入口。**它完全依赖外部后端。**
- **「控制 Analyzer 更新」= 前端调 Fetcher 后端的 `/fetch/*` 接口**（`src/api/api.js`）：实时增量 `GET /fetch/bili-history-realtime`、首次全量 `GET /fetch/bili-history` → `POST /importSqlite/import_data_sqlite`、登录走 `/login/qrcode/*`。**前端只是触发者与展示者，执行者在 Fetcher 后端。**
- **数据展示契约**（`HistoryContent.vue`）：`bvid/oid/aid/avid/epid/ssid/cid/cover/covers/author_face/author_mid/author_name/tag_name/name/business/dt/view_at/progress/duration/remark`——与 §4.3 Analyzer 34 列同构。
- **20+ 分析页 / 收藏 / 评论 / 动态 / 下载 / 计划任务**：均来自 Fetcher 后端 API 面，前端只是消费。

#### 2.3.2 Fetcher 后端 = Analyzer 的控制大脑（源码实证）
- **Analyzer 无独立源码**：它是 Fetcher 的 PyInstaller 打包产物（`dist/BilibiliHistoryAnalyzer/BilibiliHistoryAnalyzer.exe`），能力全部来自 Fetcher 后端。
- **控制端点无头可触发**（`routers/fetch_bili_history.py`）：`GET /fetch/bili-history`（全量，:94）、`GET /fetch/bili-history-realtime`（增量，:131）；**无需请求体，SESSDATA 从服务端 `config.yaml` 读取**——外部只要能访问 `localhost:8899` 即可触发，无需前端传凭证。
- 写库链路完整：拉取 → 落 JSON 快照 → `import_all_history_files()` 更新 Analyzer 读的那个 `bilibili_history.db` → 顺带补互动。
- 路由面庞大（`/history` `/analysis` `/viewing` `/download` `/favorite` `/dynamic` `/comment` `/scheduler` `/mcp`…），其中 `/mcp` 是**只读 MCP 服务**（只暴露读、不暴露写），印证我们 read-only 路线正确。

#### 2.3.3 替代可行性矩阵（前端功能逐项）
| 官方前端功能 | 我们能否替代 | 说明 |
|---|---|---|
| **展示历史记录**（列表/卡片/封面/UP主头像） | ✅ 完全能 | 已 read-only 消费 Analyzer 产物，字段契约同构，渲染不成问题 |
| **搜索 / 筛选**（FTS5 全文 + 基础筛选） | ✅ 完全能，且更强 | 我们高级筛选器（布尔组合/相对时间/正则/聚合等）是其超集 |
| **触发分析 / 导入**（点按钮让 Analyzer 重跑） | ✅ 能，但需转发到 8899 | 原非前端自身能力，是借 Fetcher 的；`server.py` 加转发 + 前端加「刷新/分析」按钮即可 |
| **年度分析 20+ 页 / 收藏 / 评论 / 动态 / 下载** | ❌ 不直接替代 | 这些是 Fetcher 后端 API 面，前端只是消费；需对接或共存，非「重写前端」范畴 |
| **二维码登录 / 计划任务** | ❌ 不直接替代 | 同样来自 Fetcher 后端，前端仅按钮 |

> 结论：展示层（核心使用场景）**完整覆盖且更强**；控制层是 Fetcher 接口、加转发即接；全家桶分析/下载属后端能力，按需对接共存，不阻替代。

#### 2.3.4 与官方前端对比（差异化位置）
| 维度 | 官方 BiliHistoryFrontend | 我们（替代后） |
|---|---|---|
| 技术栈 | Vue3+Vite+Tailwind+Tauri（重，桌面 exe） | 原生 HTML/JS + 1 个 Python 服务（轻，浏览器即用） |
| 覆盖功能 | 全家桶（历史/年度/收藏/评论/媒体下载/计划任务/动态…） | 聚焦「历史列表 + 续看规则分类」 |
| 续看三视图 + auto_skip 理由 + 单活跃多组 + 冲突校验 + dirty_count | ❌ 均无 | ✅ 完整（我们的壁垒） |
| 高级筛选 | 基础（类型/日期/分区） | ✅ 超集级（已实现） |
| 全量历史 | ✅ 后端持续同步 | ✅ 借 Fetcher 后端或直读 Analyzer 等同 |

> 定位：官方是「全家桶」分析器；我们是「续看分类器」——展示层可替代、控制层可对接、分析/下载层互补共存。

#### 2.3.5 两条对接路径（替代后的控制层如何接）
- **路径 A（server.py 加 Fetcher 转发层，最轻，推荐）**：不动前端；`server.py` 加薄代理——`POST /api/trigger-realtime` → `GET http://localhost:8899/fetch/bili-history-realtime`；前端加「实时更新」按钮；分类层（`auto_skip` 等）仍由我们引擎补算注入 `/api/history`。**规则引擎与前端 100% 复用，零重写拉取逻辑。** 前提：用户本机 Fetcher 后端（Analyzer 后台）在运行。
- **路径 B（去 server.py，前端直连 Fetcher API）**：浏览器因 CORS 全开可直 `fetch('http://localhost:8899/history/all')`；但规则引擎须移植成 JS（重写），工作量等同重写引擎。**除非要彻底去 Python，否则不如路径 A。**

#### 2.3.6 字段 / 契约映射（规则引擎需求 ↔ Fetcher/Analyzer 返回）
| 需求（规则引擎 / 前端） | Fetcher/Analyzer 字段 | 处理 |
|---|---|---|
| `business`（archive/pgc/live/article） | `business` ✅ | 直用 |
| `progress`（秒，-1=看完）/ `duration` / `view_at` | ✅ | 直用；`progress_pct` / `view_at_age_days` 派生 |
| `title`/`long_title` / `author_name`/`author_mid` / `bvid`/`uri`/`cover` | ✅ | 直用；封面走 `/cover/` 代理 |
| `kid`（skip 主键） | `kid` ✅ | 直用；无则 `(bvid,view_at)` 合成 |
| `dt`/`live_status` / `tag_name` / `remark` | ✅ | 直用 |
| `aid/avid/epid/ssid/cid/covers/author_face` | ✅ 但当前 `ANALYZER_COLS` 未全纳入 | 若直连 Fetcher `/history/all` 需补齐（按表安全选列） |
| `archived_only`（私有概念） | ❌ 无 | 适配层省略或按「是否近期」近似 |
| `auto_skip`/`manual_skip`/`auto_skip_reason`/`skip_state`（分类层） | ❌ 不提供 | **我们的引擎计算后注入** `/api/history`（路径 A 核心） |

> 映射结论：规则引擎所需字段**全部提供**；唯一需补算的是我们自己的分类层——技术上无缺口。

#### 2.3.7 风险与待验证（R1–R5）
- **R1 字段名精确对齐**：Fetcher `/all` 单条确切键名对 `:8899/docs` 实测；落地第一步核对 `progress`/`business`/`view_at`/`kid`。
- **R2 分页拉全量**：`/all` 默认 `size=10`，需逐页拉到 `total` 才能套规则；适配层做「全量缓存 + 增量刷新」。
- **R3 `X-API-Key` / SESSDATA**：Fetcher 其余端点需 `X-API-Key`（取自 `config.yaml`）；`/fetch/*` 仅需本机可达 + SESSDATA 已配。
- **R4 分类状态归属**：`auto_skip` 等是我们的层，Fetcher 不存；落 canonical side 小库（`(kid,view_at)→skip`）。
- **R5 与官方前端并存**：同一 Fetcher 后端可同时服务官方前端与我们，互不冲突（只读 + 分类侧存储隔离）。
- **R6 本机可达性（仅验证项）**：`localhost:8899` 是否实际运行需 `curl /health` 探测；SESSDATA 过期则拉取失败需重登。属部署前置检查，非源码问题。

### 2.4 接入选型结论
- **主源 = ① 直连 Analyzer SQLite（已验证）**：零新增运行时、映射最小（canonical 即以 Analyzer 34 列为基准），直接作全量基。
- Finder 自有采集作**近期窗口补充源**（已走通但为子集，合并进 canonical 即可，后续可退役 `collector.py`）。
- 若需「常新全量」或「替代官方前端 + 获得触发分析能力」（见 §2.3 评估结论），升级到 **② Fetcher API**：`server.py` 加转发层对接 `localhost:8899`（路径 A），或前端直连（路径 B）。
- 三者共用 Phase 0 的 canonical 契约与规则引擎，切换无损。

## 3. 开发路线与阶段编排

### 3.1 总体顺序与理由
**地基（Phase 0）→ 先接 Analyzer 全量（Phase 1）→ 油猴 D（Phase 2）→ 维护（Phase 3）**。
理由：Analyzer 已躺着 2020–2026 深历史（2813 条），是 Finder 近期窗口采集器永远抓不到的；先在全量数据上验证规则引擎，油猴 D 直接复用同一套引擎与 canonical 契约，**避免走两遍**。

### 3.2 Phase 0 — 冻结契约与抽离引擎（前置，不依赖任何存储）
1. 定义并冻结「统一逻辑数据契约」（见 §4.2：raw 权威层 + derived 规范化层，复合主键）。
2. 将 `server.py` 规则引擎（`eval_condition` / `evaluate_rule` / `validate_rule`，行 191–317）抽离为独立可移植模块；`rules.json` schema 定稿（单 active、多分组、字段/操作符集合）。
3. 输出「cursor 响应 / Analyzer 34 列 → canonical derived」字段映射表（一次性工作，供 D / A / B 复用）。

### 3.3 Phase 1 — 接 Analyzer 全量（✅ 已落地并验证 2026-08-24；先于油猴 D）

## 4. 统一数据契约（canonical schema）

### 4.1 问题
各路线物理存储不同：D 在浏览器 IndexedDB；A / B 在本地 SQLite（Fetcher / Analyzer 已各自落库）。是否要「统一 DB」？统一到什么程度？

### 4.2 结论：统一「逻辑数据契约」，不强求「物理数据库引擎」
- **不统一物理引擎**：浏览器 IndexedDB 与本地 SQLite 各擅其场，且 Fetcher / Analyzer 已各自落库；强行单一物理库会引入 IPC / 跨进程依赖，得不偿失，也破坏「D 零后端」的部署优势。
- **统一逻辑契约（canonical schema）**，所有路线必须遵守：
  - **权威层 `raw`**：完整 `cursor` 响应 JSON 原样存储，`key = (bvid|oid)@view_at`，永不丢字段、永不 FIFO 淘汰。
  - **派生层 `derived`**：规则引擎所需的规范化字段集——`business` / `progress` / `duration` / `view_at` / `title` / `author_name` / `author_mid` / `bvid` / `uri` / `cover` / `kid` / `dt` / `live_status`，加派生字段 `progress_pct` / `view_at_age_days` / `skip_state`（我们的分类层）。
- 规则引擎与 UI **只面向 canonical `derived` 开发一次**；各路线通过 storage adapter 把自身存储映射进 canonical 形式。

### 4.3 实测校准与路线适配
- **canonical `derived` 以 Analyzer 34 列为基准**（最完整 B站 元数据投影）；Finder 多出的仅是分类层 `auto_skip`/`manual_skip`/`auto_skip_reason` 与同步簿记 `created_at`/`updated_at`/`last_seen_sync`/`archived_only`，且**Finder 的 `raw_json` 仅 23 键**（缺 `business`/`oid`/`bvid`/`cid`/`epid`/`page`/`part`/`dt`/`main_category`/`remark`），**不是真·原始响应权威层**——故 Finder 侧 `page`/`part`/`dt`/`main_category`/`remark` 合并进 canonical 时会为空（需重新全量抓取补齐）。
- **路线适配**：
  - **D**：直接在 IndexedDB 建 `raw/derived` 两仓库（双存储设计）。
  - **A（Fetcher）**：其 `/history/all` 返回即 `derived`，字段与 canonical `derived` 几乎一致，仅需整形；`raw` 由 Fetcher 的 `api_responses/`、`history_by_date/*.json` 保留，适配器可读取以保迁移零缺失。
  - **B（Analyzer）**：read-only attach 其 SQLite，映射 `raw/derived` 视图到 canonical。
- 由此，**R1（字段名精确对齐）从「每路线重写引擎」降为「canonical ↔ 各源的一次性映射」**；**R4（分类状态归属）** 统一落 canonical 侧的小 side 存储（`(kid,view_at)→skip 状态`），与源库解耦、互不污染。

### 4.4 统一 DB 的取舍
- **收益**：① 路线间无损切换、零缺失迁移（`raw` 权威层保证）；② 规则引擎 / UI 单一代码库，跨形态复用；③ 迁移工具只需读 `raw`；④ 将来若新增第四种数据源（如 Import JSON），只要映射进 canonical 即可复用全部能力。
- **代价**：① 前期须定义并冻结 canonical schema（设计成本，但一次性的）；② D 路线须自行实现双存储，且**必须抓取「完整 cursor 响应」作 raw 权威层**（实测 Finder 现版 `raw_json` 是裁剪子集，缺 `business`/`oid`/`bvid` 等关键字段，不能作为权威层）；③ 合并两源时，Finder 侧缺的 `page`/`part`/`dt`/`main_category`/`remark` 会留空，属可接受的可选元数据缺失。
- **裁定：是——应基于统一的逻辑 DB 契约开发（非统一物理引擎）。** 这是降低总开发量、保证数据主权（本地超集、不回写服务端）的关键架构决策。

| 维度 | D 主路线（油猴） | A 接 Fetcher | B 接 Analyzer |

### 6.5 保留 collector 历史拉取作为 Analyzer 备份源的必要性评估（仅评估）

**背景**：用户要求保留原型 `collector.py` 的历史拉取功能，作为 Analyzer 的备份源。本节**仅评估必要性，不实现额外 wiring**——合并逻辑已在 Phase 1 落地（`store.py` 以 read-only 把本地 Finder 库作为备份源自动并入）。

**实测结论（2026-08-24）**：
- 合并唯一集 = **3278 条** = Analyzer 2813 + **Finder 独有 465**（按 `(bvid,view_at)` 去重后）。即 Finder 贡献 465 条 Analyzer 未覆盖的记录。
- 这 465 条全部落在 2026 近期窗口——只要 Analyzer 保持同步，本就会被它捕获。Finder 的增量价值 = 在「Analyzer 末次同步之后、Finder 又抓到的少量新记录」补漏。

**必要性评估**：
- **覆盖角度：低必要性**。Analyzer 是 2020–2026 深历史超集；Finder 近期窗口是其子集，差集仅来自 Analyzer 未同步的近期窗口。若 Analyzer 持续同步，collector 在覆盖上冗余。
- **健壮性角度：中必要性（安全网）**。Analyzer 未运行 / 未同步 / 损坏时，collector 提供近期窗口兜底，Phase 1 合并自动并入，不丢近期记录——属廉价保险。
- **维护成本：中**。collector 需维护 SESSDATA 处理 + 跟进 B站 API 变动；两套采集链路并存增加长期负担。
- **数据主权角度：正面**。Finder 库在本地、与 Analyzer 独立，互为离线备份。

**关键风险（实施时暴露，务必记取）**：
- **合并键必须对齐，否则备份变灾难**。初版按 `kid` 合并时，Analyzer `kid` 列恒为 0、Finder `kid`=oid（无 `view_at`），导致零重叠、合并成 **5678 条重复记录**；修正为统一复合键 `(bvid,view_at)` 后才正确去重到 3278。若后续引入其他备份源，必须先对齐主键再合并。

**裁定**：
- **保留 `collector.py`（不删除、保持可用），但默认不运行**——Analyzer 为唯一权威源；仅当 Analyzer 不可用或需补近期窗口时跑 collector 作兜底。Phase 1 合并已对其自动包含，无需额外开发。
- 不建议为「备份」再写任何同步 / 去重逻辑；现有 read-only 合并已足够。若 Analyzer 长期不维护，再评估把 collector 设为周期性补漏。
