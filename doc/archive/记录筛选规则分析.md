# 记录筛选规则分析 — BilibiliHistoryFinder 续看分类器

> 分析对象：规则引擎逻辑（`src/engine.py`）+ 规则配置（`data/rules.json`）+ 分类落点（`src/store.py`）
> 配套：架构见 `doc/架构分析.md`；设计意图见 `doc/正式版方案.md` §1.2 / §3
> 实测基线：2026-08-24，合并 3278 条（Analyzer 2813 + Finder 独有 465），default 规则

---

## 1. 规则引擎解决什么问题

B站官方历史页只提供「全部 / 按类型」粗筛，且记录会被上限滚动覆盖。本工程的差异化壁垒是**一套可解释的「续看分类」规则**：

> 从完整历史中，自动把「不需要再看」的视频标记为 `auto_skip`（并绑定理由），剩下的就是「需要观看（needs）」；人工还能 `manual_skip` 或 `auto_exempt`（取消自动跳过）。

分类逻辑与采集、存储、UI 完全解耦（`engine.py` 零 I/O），因此可跨数据源、跨形态（Python / 油猴 JS）复用。

---

## 2. 数据模型与进度语义

规则引擎操作的输入是 **canonical derived 记录**，关键字段：

| 字段 | 含义 | 规则可用性 |
|---|---|---|
| `business` | archive / pgc / live / article | 直接条件 |
| `progress` | 观看进度（秒）；**`-1` 表示已看完** | 由它派生 `progress_pct` / `progress_sec` |
| `duration` | 总时长（秒） | 直接条件 |
| `view_at` | 观看时间（Unix 秒） | 由它派生 `view_at_age_days` |
| `title` / `author_name` / `author_mid` | 文本/ID | 文本条件 |
| `archived_only` | 是否仅本地存档 | 私有概念，当前恒 0 |
| `bvid` / `oid` / `kid` | 标识 | 主要用于合并键与 skip 主键 |

**进度派生（`engine._derived`）**：
- `progress == -1` → `progress_pct = 1.0`、`progress_sec = duration`
- `progress` 与 `duration` 均有效 → `progress_pct = progress/duration`、`progress_sec = progress`
- 否则 `progress_pct = None`（不可用数值条件比较）
- `view_at_age_days = (now - view_at) / 86400`

## 3. `rules.json` 结构

```json
{
  "rules": [
    {
      "id": "default",
      "name": "默认续看规则",
      "active": true,            // 同一时刻仅一条 active
      "match": "any",            // "any"=命中任一分组即生效; "all"=须命中全部分组
      "groups": [
        {
          "label": "接近看完",
          "action": "auto_skip",  // auto_skip=自动跳过 / stale=已搁置
          "conditions": [
            {"field": "progress_pct", "op": ">=", "value": 0.95}
          ]
        }
        // ... 更多分组
      ]
    }
  ]
}
```

- **rule**：一条完整规则，`active` 标记是否生效。v1 仅允许一条 active（C6）。
- **group**：「条件 AND」单元，命中后按 `action` 处理，并带上 `label` 作为可解释理由。
- **condition**：`{field, op, value}` 三元组。

### 可用字段 / 运算符
- 字段：`progress_pct` `progress_sec` `duration` `business` `author_name` `author_mid` `title` `archived_only` `view_at_age_days`
- 运算符：`>= <= > <`、`between`、`in` / `not_in`、`contains`、`==`

---

## 4. 求值算法

### 4.1 单条件 `eval_condition(rec, cond, now)`
1. 取 `field` → 当前值 `cur`（数值/文本字段直取；`progress_pct`/`progress_sec`/`view_at_age_days` 来自派生层）。
2. 按 `op` 比较：
   - `in` / `not_in`：把 `value` 按逗号或列表拆成集合，判断 `cur` 是否在其中（文本字段常用，如 `business in "live"`）。
   - `contains`：`value` 是否为 `cur` 子串。
   - `==`：严格相等。
   - `between`：`a <= cur <= b`（value 形如 `"10-100"`）。
   - `>= <= > <`：数值比较；`cur is None` 一律返回 `False`（缺进度时不误判）。
3. 任何异常（类型错、缺字段）→ `False`，保证单条脏数据不崩整个分类。

### 4.2 分组 `eval_group(rec, g, now)`
分组内**所有** condition 为 AND：任一不满足即返回 `False`。

### 4.3 规则 `evaluate_rule(rec, rule, now)`
```python
if rec.get("progress") == -1:        # 已看完是固有状态，规则不可纳入
    return None
matched = [g for g in groups if eval_group(rec, g, now)]
if not matched:
    return None                      # 未命中 → 进入 needs
if rule["match"] == "all" and len(matched) < len(groups):
    return None                      # all 模式须全中
g = matched[0]                       # 首命中分组决定 action/label
return (g["action"], g["label"])
```
**关键语义**：
- `progress == -1`（已看完）直接短路为 `None`，永远计入 `finished`，不被任何 auto_skip 规则反转为「跳过」。
- `match:"any"`（默认）：命中任一分组即分类；**取 `matched[0]`，即「分组列表中第一个命中者」决定动作与理由**——分组顺序影响标签（见 §7 细微点）。

## 5. 三视图模型

`engine.classify()` / `store._view_counts()` 把每条记录归入且仅归入一类，**不变式：`finished + auto_skip + stale + needs == total`**。

| 视图 | 判定 | 语义 |
|---|---|---|
| `finished` | `progress == -1` | 已看完（固有状态） |
| `auto_skip` | 规则命中且 `action=="auto_skip"` | 被规则自动判为「不需要看」 |
| `stale` | 规则命中且 `action=="stale"` | 久未动（陈旧）未看完 |
| `needs` | 未完成 且 未被规则跳过 | 「需要观看」 |

> `stale` 与 `auto_skip` 同属「规则命中、不进 needs」，区别仅在 action 标签，用于 UI 区分「主动跳过」与「陈旧搁置」。

### 实测三视图（default 规则，3278 条合并集）
| 视图 | 条数 | 占比 |
|---|---|---|
| total | 3278 | 100% |
| finished（已看完） | 1473 | 45.0% |
| auto_skip（自动跳过） | 1226 | 37.4% |
| stale（已搁置） | 0 | 0% |
| needs（需要观看） | 579 | 17.7% |

校验：1473 + 1226 + 0 + 579 = **3278** ✓

**分组命中分布（仅非 finished 的 1805 条中）**：

| 分组 label | 命中条数 | 动作 |
|---|---|---|
| 误触-短暂观看 | 580 | auto_skip |
| 短视频碎片 | 535 | auto_skip |
| 接近看完 | 111 | auto_skip |
| （未命中→needs） | 579 | — |
| 直播回放 | 0 | auto_skip |
| 陈旧-久未观看 | 0 | stale |

> 说明：每条记录只计入「第一个命中分组」，故 短视频535 + 误触580 + 接近看完111 = auto_skip 1226 ✓；无直播/陈旧命中 → 对应 action 计数为 0。

## 6. 跳过状态与优先级

分类结果可由用户干预，状态存在侧库 `canonical_state.db.skip_state(kid, manual_skip, auto_exempt)`：

| 状态 | 来源 | 含义 |
|---|---|---|
| `auto_skip` | 规则计算 | 命中规则自动跳过，绑定 `auto_skip_reason = "action::label"` |
| `manual_skip` | 用户手动（`/api/skip?kind=manual`） | 人工标记跳过 |
| `auto_exempt` | 用户取消（`/api/skip?kind=auto`） | 人工取消某条的自动跳过 |

`store.classify_record()` 的优先级：
1. `finished` → 永远 `finished`，无视任何 skip。
2. 否则若 `auto_exempt` 为真 → 不套用 auto_skip（用户覆盖规则）。
3. 否则若规则命中 → `auto_skip=1`、`skip_state="auto"`。
4. `manual_skip` 为真 → `skip_state="manual"`（手动优先展示）。
5. 其余 → `skip_state=""`，进入 needs。

**应用规则时的清理**（`apply_rules`）：重扫全量，若某条被规则命中且其旧 `manual_skip=1`，则清除 `manual_skip=0`（auto 覆盖 manual）。`dry=True` 仅计数不落库。

### `needs` 视图的隐含 95% 门（需注意的语义细节）
`store._filter()` 的 `needs` 分支除排除 `finished` 与 `auto_skip` 外，还有一行：
```python
if dur and p is not None and p >= 0 and p >= 0.95 * dur:
    continue   # 接近看完（>=95%）不进 needs
```
即：**进度 ≥ 95% 时即便 `auto_exempt` 取消了自动跳过，也不会出现在 needs 视图**。这是一条独立于规则引擎的「硬门」，与「已看完(95%+) 视为不需要观看」的直觉一致，但意味着用户无法把「仅剩 5% 想看完」的视频显式放回 needs（auto_exempt 对它无效）。属可接受的产品取舍，但迁移/维护时务必知道这条门不在 `engine.py` 而在 `store._filter`。

## 7. 冲突校验 `validate_rule`

保存规则前由 `server.POST /api/rules` 调用，返回 `{hard, soft, info}`：
- **C1（hard，阻断）**：同一分组内同字段既有 `≥a` 又有 `≤b` 且 `a>=b` → 无记录可同时满足。
- **C2（soft，警告）**：同字段重复/包含的条件（如 `<5` 与 `<10`），后者冗余。
- **C3（hard，阻断）**：进度条件 `progress_pct <= 1.0`（会把「已看完」纳入跳过，违反固有状态不可反转）。
- **C6（hard，阻断，在 server 层）**：多条 `active` 规则并存，或零 active。

> 校验缺口提示：`>= 0.95`（默认「接近看完」）是允许的，且会命中 `progress_pct=1.0` 的已看完记录——但 `evaluate_rule` 的 `progress==-1` 短路已兜底，故运行时安全；C3 仅拦 `<= 1.0` 未拦 `>= 0.95`，属轻微不一致（功能无碍）。

## 8. 增量感知 `dirty_count`

`store.rules_status()` 基于 `meta` 中存的上次应用时间 `last_rule_apply_at` 与规则哈希：
- `pending`：当前规则哈希 ≠ 已应用哈希（规则改过、尚未重扫）。
- `dirty_count`：自 `last_rule_apply_at` 以来**新增**（`view_at > 上次应用时间`）且**未被规则覆盖**的非 finished 记录数（已命中的不计入脏）。

前端 ⚙ 抽屉用「橙色圆点=待应用」「数字=脏计数」提示用户何时该「应用规则」。实测当前 `pending=False`、`dirty_count=0`（已应用且无新增）。

## 9. 默认规则行为复盘

default 规则 5 个分组（顺序即优先级）：
1. **接近看完**：`progress_pct >= 0.95` → auto_skip（111 条）
2. **误触-短暂观看**：`progress_pct < 0.03 AND progress_sec < 15` → auto_skip（580 条）
3. **短视频碎片**：`duration < 60` → auto_skip（535 条）
4. **直播回放**：`business in "live"` → auto_skip（0 条）
5. **陈旧-久未观看**：`view_at_age_days > 90` → stale（0 条）

**现象解读**：
- `stale == 0`：深历史（2020–2025）多数已看完（`progress==-1`）计入 finished，而非「陈旧未看完」；近期未看完且超过 90 天的记录恰为 0。
- `auto_skip` 占总 37%，主要由「误触短暂观看 + 短视频碎片」贡献——说明历史里大量是刷过即走/极短视频。
- `needs == 579`（17.7%）：即真正「值得回头看」的存量，是规则引擎的核心产出。

## 10. 可扩展性与迁移建议

- **加字段**：在 `eval_condition` 的 `field` 分支新增映射即可（前端抽屉同步加选项）。
- **加运算符**：在 `eval_condition` 的比较段追加分支。
- **加分组/预设**：`rules.json` 直接加 `groups` 项；`business` 预设即现成范式。
- **移植到 JS（油猴 D）**：把 `eval_condition/eval_group/evaluate_rule/validate_rule/classify` 逐函数移植，输入同一 canonical `derived`，输出同一 `(action,label)`——语义基准已由本 Python 版验证（3278 条三视图），JS 版只需对齐字段派生（`progress_pct` 等）与运算符实现即可。
- **切换数据源**：规则引擎不变，仅改 `store` 的读层映射（Analyzer/Fetcher/Finder/IndexedDB 各自 adapter），符合统一逻辑契约（见 `正式版方案.md` §4）。

## 11. 高级筛选器演进（必须内嵌当前引擎规则）

### 11.1 评估口径纠正
早前曾用"本地数据分布"（如本库 business 仅 14 条非 archive）来判定某维度是否必要——**这是错误的评估口径**：那只是个人使用分布，不代表通用产品该不该提供该功能。正确口径是：**用户普遍诉求 + 业界数据处理软件标配的高级筛选能力**。规则维度的取舍应与"本用户数据多不多"脱钩。

### 11.2 当前引擎已经具备的"筛选/分类"能力（高级筛选器必须保留，不得丢失）
- **字段派生层**：`progress_pct` / `progress_sec` / `view_at_age_days`（`engine._derived`）。
- **运算符**：`>= <= > <`、`between`、`in` / `not_in`、`contains`、`==`。
- **规则结构**：分组内 AND、`match: any/all`、首命中分组决定 `action`/`label`。
- **三视图分类**：`finished` / `auto_skip` / `stale` / `needs`，**不变式 `finished+auto_skip+stale+needs==total`**。
- **skip 优先级**：`finished` > `auto_exempt` > 规则命中 > `manual_skip`（见 §6）。
- **validate_rule 冲突校验**（C1/C2/C3/C6）+ **dirty_count 增量感知**（§7/§8）。
- 当前 `rules.json`（单 active 规则 + 分组→action）即"分类核心"，高级筛选器是其**超集**，以上语义全部必须仍可表达。

### 11.3 业界标准高级筛选能力矩阵（用户诉求 × 常见度）
| 高级筛选能力 | 用户诉求 | 业界常见 | 当前引擎 | 优先级 |
|---|---|---|---|---|
| 组合布尔（跨条件组 AND/OR/NOT） | 强 | 标配 | ❌ 仅首命中分组 | **P0** |
| 相对时间（最近 N 天 / 超过 N 天） | 强 | 标配 | ❌ 仅绝对 `view_at` | **P0** |
| 空值 / 存在判断（exists / empty） | 中 | 标配 | ❌ | **P0** |
| 排序 + 多列 + 分页语义 | 强 | 标配 | 部分（前端） | **P1** |
| 保存多视图 / 筛选预设 | 强 | 标配 | ❌ 仅单 active 规则 | **P1** |
| 包含 / 排除列表（白黑名单） | 强 | 标配 | ❌ | **P1** |
| 分组聚合 + HAVING（同 UP>3 次） | 中 | 常见 | ❌ 逐行无聚合 | **P2** |
| FTS 全文搜索 | 强 | 常见 | ✅ Analyzer 已有 `_fts` 可借 | **P2** |
| 结果批量操作（标 / 跳 / 归档 / 删） | 强 | 常见 | ❌ 仅单条 skip | **P2** |
| 去重 / 重复观看识别 | 中 | 常见 | 部分（合并键） | **P2** |

> 真实开源 BiliHistoryFrontend 已提供"日期、分区筛选 + 搜索 + 实时更新"，说明基础筛选是行业基线；上表是把它补齐到"高级筛选器"的差距。

### 11.4 设计约束：高级筛选器 = 当前引擎规则的超集（关键）
高级筛选器**不是替换**当前规则引擎，而是**叠加**在分类核心之上：
- **分类核心（engine 职责，保持不变）**：决定每条记录的归属（`skip` / `finished` / `needs`），产出三视图，维护 skip 优先级与冲突校验。
- **筛选视图（新增查询层）**：在归属结果之上，做 AND/OR/NOT 组合的呈现过滤、排序、聚合、全文搜索、保存预设、批量操作。
- 约束清单：
  1. 现有 `rules.json` 单 active 规则 + 分组→action 必须仍可被表达（可视为"筛选视图"的一个命名预设）。
  2. 三视图不变式 `finished+auto_skip+stale+needs==total` 必须保持——高级筛选只改变"呈现哪些"，不改变"归属"。
  3. `progress==-1` 短路为 `finished`、skip 优先级链、§6 的 95% 硬门均不可被筛选器绕过。
  4. 新增算子（`regex` / `exists-empty` / `before-after` / `ratio`）只在"筛选视图"层生效，分类核心的 `eval_condition` 接口可同步扩展但语义不变。
