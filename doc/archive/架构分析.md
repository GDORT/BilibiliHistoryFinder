# 架构分析 — BilibiliHistoryFinder 续看分类器（Phase 1 现状）

> 分析对象：当前工程代码（Phase 1 落地版，2026-08-24 验证通过）
> 工程根：`D:\Programs\Share\BilibiliHistoryFinder\`
> 配套设计文档：`doc/正式版方案.md`（本文件只描述「代码实际长什么样」，不重复设计论证）

## 1. 一句话定位

本工程不是一个「历史抓取器」，而是一个**本地优先的「续看 / 历史筛选分类」规则引擎**：
以现成的 B站历史 SQLite（Analyzer 全量库 + Finder 近期库）为**只读数据源**，把多源记录归一化后，用一套可移植的规则引擎算出 `needs / skipped / stale` 三视图，并通过一个零依赖的本地 Web 界面浏览、搜索、编辑规则。

核心价值在**分类逻辑**（抽离在 `engine.py`，零 I/O、可跨路线复用），不在采集。

## 3. 分层与数据流

```

                       │  (仅 collector 备用)              │ 34 列 / 年表                │ 27 列 / 单表 history
                       ▼                                  │                            │
              data/bilibili_history.db ◄─────────────────┘  store.py 合并 ──────────────┘

                       │
              ┌────────┴───────────────────────────────────────────────────────┐

              │    _read_local()     file:?mode=ro 读 history 表                  │

              └────────┬───────────────────────────────────────────────────────┘
                       │  get_raw()  →  list[canonical dict]
              ┌────────┴───────────────────────────────────────────────────────┐
              │  engine.py — 纯逻辑规则引擎（无 I/O）                              │
              │    eval_condition / eval_group / evaluate_rule / validate_rule   │
              │    classify()  →  三视图计数 + 命中样本                          │

              │    + 侧状态库 canonical_state.db（manual_skip / auto_exempt）    │
              │    query() / apply_rules() / rules_status()                      │
              └────────┬───────────────────────────────────────────────────────┘
                       │
              ┌────────┴───────────────────────────────────────────────────────┐
              │  server.py — ThreadingHTTPServer + 后台线程                      │
              │    GET/POST /api/*  ·  /cover/ 封面代理  ·  静态资源              │

```

**分层原则**：数据源（只读）→ 读层/合并（store）→ 规则引擎（engine，纯函数）→ 分类/查询（store）→ HTTP 编排（server）→ 前端（web）。规则引擎位于最内层、不依赖任何上层，因此可被油猴 D（JS 移植）、Fetcher 适配器（路径 A）无损复用。

## 4. 模块逐一分析

### 4.1 `engine.py` — 规则引擎（纯逻辑资产）
- **定位**：Phase 0 抽离的「可移植纯逻辑」核心；不 `import` 任何 DB / 网络 / collector，可被任意数据源复用。
- **关键函数**：
  - `default_rules()`：随软件下发的默认规则（5 个分组）。
  - `get_active_rule(rules)`：同一时刻至多一条 `active` 规则。
  - `load_rules_from_file(path)`：读 `rules.json`；损坏/缺失/无 active 时回退默认并强制首条 active。
  - `_derived(rec, now)`：从固有字段派生规则旋钮 `progress_pct` / `progress_sec` / `view_at_age_days`。
  - `eval_condition(rec, cond, now)`：单条件求值（字段/运算符/值）。
  - `eval_group(rec, g, now)`：分组内「全部条件 AND」。
  - `evaluate_rule(rec, rule, now)`：返回 `(action, label)` 或 `None`；`progress==-1`（已看完）直接短路返回 `None`。
  - `validate_rule(rule)`：冲突校验，返回 `{hard, soft, info}`（C1/C2/C3 见筛选规则分析文档）。
  - `classify(records, rule, now)`：对一组记录跑三视图，返回计数 + 每类最多 5 条样本（只读、不写库）。
  - `rules_hash(rules)`：规则内容 MD5，用于「已应用 / 待应用」比对。
- **对外契约**：输入 canonical derived dict，输出分类动作。**不持有状态、不触盘**。

### 4.2 `store.py` — Phase 1 数据层
- **职责（读）**：把 Analyzer（主源）+ Finder（备份源）两库以 `file:...?mode=ro` 只读打开，归一化为 canonical records。
  - `_list_base_year_tables()`：动态 `GLOB 'bilibili_history_[0-9][0-9][0-9][0-9]'`，**排除 `_fts` 全文虚拟表**（否则 `SELECT *` 会因 FTS 报错）。
  - `_rec_key(d)`：统一合并键 `f"{bvid}_{view_at}"` → 回退 `(oid,view_at)` → `(kid,view_at)`。这是两源正确去重的关键（详见 §6 风险）。
  - `_read_analyzer()`：跨 7 张年表 UNION，取 17 列子集（34 列基准里规则/展示相关者），缺的 `archived_only` 补 0。
  - `_read_local()`：读 Finder `history` 表，从 `raw_json` 补 `dt`/`live_status`。
  - `load_raw_records()`：Analyzer 优先、Finder 补齐独有 → 合并为 list。
  - `RAW_CACHE`：模块级缓存，避免每请求重读 7 张年表。
- **职责（侧状态库，唯一可写）**：
  - `_state_conn()` / `_ensure_state_schema()`：建 `canonical_state.db`，含 `skip_state(kid PK, manual_skip, auto_exempt)` 与 `meta(key,value)`。
  - `load_state()` / `save_skip()`：读 / 写单条 skip 状态（manual_skip、auto_exempt 可单独更新，`ON CONFLICT` upsert）。
  - `set_meta()` / `get_meta()`：存「规则已应用哈希」「最后应用时间」等。
- **职责（分类/查询）**：
  - `classify_record(rec, rule, now, state)`：计算 `finished` / `auto_skip` / `auto_skip_reason` / `manual_skip` / `skip_state`，**不修改源**。
  - `query(raw, rule, state, params)`：按 q/business/view/时间/时长/设备过滤 + 分页，返回 `(items, total, counts)`。
  - `_filter()`：实际过滤逻辑；含 `needs` 视图的隐含 95% 门（见筛选规则分析文档 §6 语义细节）。
  - `apply_rules(raw, rule, state, dry)`：按 active 规则重扫，固化「已应用」状态、清理被 auto 覆盖的 manual_skip。
  - `rules_status()`：返回 pending（规则哈希变化）+ `dirty_count`（上次应用以来新增未套用条数）。
  - `get_meta_banner()`：常驻文字（主源/备份源/合并条数），供前端展示。

### 4.3 `server.py` — Web 服务与编排
- **依赖**：`import collector, engine, store`（复用 collector 的 `DEFAULT_DB/DEFAULT_CONFIG/UA/REFERER/init_db/load_config`，复用 engine/store 的全部能力）。
- **启动流程（main）**：`ensure_rules()` 保证 `rules.json` 存在 → `reload_all()` 读多源 + 建封面缓存 → 首次启动若无「已应用哈希」则 `_store_applied_rules()` 固化一次 → 双栈绑定（`::`/`0.0.0.0`/`127.0.0.1` 依次尝试，端口占用即提示已在运行）→ 打印数据源 banner 与规则状态 → `serve_forever()`。
- **HTTP 端点**：
  | 方法 | 路径 | 作用 |
  |---|---|---|
  | GET | `/` `/index.html` | 前端首页 |
  | GET | `/static/*` | 静态资源（app.js / style.css） |
  | GET | `/api/history` | 历史列表（items + total + counts），参数过滤/分页 |
  | GET | `/api/sync` | 同步状态（running/progress/last/meta） |
  | GET | `/api/rules` | 读取当前规则 |
  | GET | `/api/rules-dry` | 规则应用 dry-run（仅计数不写库） |
  | GET | `/api/rules-status` | 待应用 / dirty_count |
  | GET | `/api/auto-skip-status` | 规则应用后台任务进度 |
  | GET | `/cover/<kid>` | 封面代理（本地缺则下载缓存） |
  | POST | `/api/sync` | 触发同步（`?full=1` 全量重建） |
  | POST | `/api/rules` | 持久化规则（先冲突校验 + 强制单 active） |
  | POST | `/api/rules-dry` | dry-run 应用 |
  | POST | `/api/apply-rules` | 后台重扫全量、写 auto_skip |
  | POST | `/api/skip` | 单条标记（`?kind=manual` 手动跳 / `?kind=auto` 取消自动跳） |
- **后台任务**：`run_sync_background()`（守护线程跑 `collector.py` 子进程）、`apply_rules_background()`（守护线程跑 `store.apply_rules`）。前端轮询 JSON 进度文件，避免长请求阻塞。
- **封面**：`ensure_cover()` 仅在本地缺文件时按 `collector.UA/REFERER` 下载缓存到 `data/covers/`。

### 4.4 `collector.py` — 备份源采集器（默认不运行）
- **角色**：按 §6.5 评估结论，**保留但默认不运行**；仅当 Analyzer 不可用或需补近期窗口时作兜底。
- **能力**：`history/cursor` 分页（SESSDATA 鉴权）、全量建基线 + 增量续拉、断点续拉（游标持久化）、完成判定以 `sync_result.json.completed` 为准（与退出码解耦）、进度写 `sync_progress.json`。
- **粘性 upsert**（§12/§13）：`progress` 已看完(-1)/手动标记/自动标记则不更新；`manual_skip`/`auto_skip` 同步不覆盖；`archived_only` 仅全量标记。
- **与 Phase 1 的衔接**：`store._read_local()` 以只读方式把它的产出（Finder 库）并入主源，无需额外 wiring。

### 4.5 `adapter_analyzer.py` — 只读适配器验证脚本
- **作用**：独立的验证入口（不入服务），直接 `file:?mode=ro` 跨年表读 Analyzer 全量 → `engine.classify()` 跑三视图 → 打印计数 + 命中样本 + 校验和。
- **价值**：证明「方案 B 直连 SQLite」可行性，且全程零写入。验证报告见 `doc/adapter-验证报告.md`。

### 4.6 `web/` — 前端
- 原生 HTML/CSS/JS 单页，零框架零 npm，可完全离线运行。
- 顶部工具栏：类型 tab（综合/视频/直播/专栏）、视图 tab（全部/需要观看/已跳过/已搁置）、筛选▾（时长/时间/设备/含存档，临时不落库）、搜索、⚙ 规则抽屉、同步按钮。
- 每条展示封面 + 标题 + UP主 + 相对时间 + 进度条，可点击跳转 B站。

## 5. 存储与「只读原则」

| 存储 | 路径 | 角色 | 工程写权限 |
|---|---|---|---|
| Analyzer 库 | `D:\Program Files (x86)\BilibiliHistoryAnalyzer\output\bilibili_history.db` | 主源（34 列 / 2813 条 / 2020–2026） | **只读**（`mode=ro`） |
| Finder 库 | `data/bilibili_history.db` | 备份源（27 列 / 2865 条，独有 465） | **只读**（`mode=ro`） |
| canonical_state.db | `data/canonical_state.db` | 本工程私有分类状态（skip + meta） | **可读写**（唯一） |
| covers/ | `data/covers/` | 封面缓存 | 可读写（仅缺时下载） |
| rules.json | `data/rules.json` | 规则 | 可读写（用户编辑） |
| sync_*.json / auto_skip_progress.json | `data/` | 运行时进度 | 可读写（运行时） |

**只读原则落地方式**：
- `store._read_analyzer()` / `_read_local()` 均用 `sqlite3.connect(f"file:{db}?mode=ro", uri=True)`，连接即禁止写入。
- 分类状态（auto_skip / manual_skip / auto_exempt）**只落 `canonical_state.db`**，与两源库物理隔离、互不污染。
- `server.get_sync_meta()` 读 Finder 库用普通只读连接，亦不写源。
- 唯一「可能写源」的入口是 `collector.py`（写 Finder 库），但其默认不运行，且其写的是本工程自有备份库、非 Analyzer 主源。

## 6. 关键架构决策与风险

### 6.1 统一「逻辑契约」而非物理引擎
规则引擎与 UI 只面向 canonical `derived` 开发一次；Analyzer / Finder / 未来 Fetcher / 油猴 D 各自通过 storage adapter 映射进 canonical。切换数据源是无损的（见 `正式版方案.md` §4）。

### 6.2 合并键必须对齐（已踩坑，务必记取）
初版按 `kid` 合并：Analyzer `kid` 列恒为 0、Finder `kid`=oid（无 view_at），零重叠 → 合并出 **5678 条重复**。修正为统一复合键 `(bvid,view_at)` 后正确去重到 **3278**（Analyzer 2813 + Finder 独有 465）。**任何新增备份源都必须先对齐主键再合并**。

### 6.3 单 active 规则 + 多分组
v1 仅允许一条 `active` 规则（`server.POST /api/rules` 强制校验，C6）。多分组是「OR」语义（默认 `match:"any"`），命中任一分组即按该分组动作处理。

### 6.4 规则引擎作为跨路线资产
Phase 2 油猴 D 将把 `engine.py` 移植为 JS，输入同一套 canonical `derived`，保证分类语义一致；路径 A（Fetcher 适配器）则零改动复用 Python 引擎。

### 6.5 已知薄弱点（维护时注意）
- **Analyzer 表结构耦合**：若 Analyzer 改表 / 加年表 / 取消 `_fts`，`_list_base_year_tables` 的 GLOB 可能漏表；已用动态枚举缓解，但字段名变动需同步 `ANALYZER_COLS`。
- **绑定主机依赖**：Analyzer 路径硬编码（`D:\Program Files (x86)\...`），可用环境变量 `ANALYZER_DB` 覆盖便于迁移（代码已支持）。
- **后台任务靠轮询 JSON**：`_job_running()` 仅做互斥，长任务进度依赖前端轮询进度文件，无 WebSocket/SSE。
- **collector 双链路维护成本**：两套采集并存，SESSDATA 过期需手动更新（`server` 暂无重填 UI）。
