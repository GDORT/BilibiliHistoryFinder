## 0. 决策速览（一页结论）

| 项 | 结论 |
|---|---|
| **需求本质** | 一套「续看 / 历史筛选分类」规则引擎：`needs/skipped/stale` 三视图（基于 `progress`）+ `auto_skip` 理由绑定 + 单活跃多组条件 + 冲突校验 + `business` 预设 + `dirty_count` 增量感知 |
| **最终交付形态** | **方案 D：油猴脚本 / 轻量扩展**（原生历史页手动拉取 + 浏览器本地存储） |

| **主数据源** | **Analyzer SQLite（read-only 直连）**：34 列、2813 条、2020–2026 深历史 |
| **补充数据源** | Finder 自有库（27 列、2865 条近期窗口）；两源互非超集，**合并唯一集 = 3277 条** |
| **统一 DB 战略** | 基于**统一「逻辑数据契约」**（raw 权威层 + derived 规范化层），**非统一物理引擎** |
| **开发三原则** | ① 源库全程只读（`mode=ro`）② 参考其他代码**无需下载**（Analyzer 本地已有；Fetcher 仅契约）③ 分类状态只写 canonical 侧小库，绝不回写源库 |

## 1. 需求与差异化壁垒

### 1.1 需求本质
不是「再做一个历史抓取器」，而是「一套历史续看 / 筛选分类的规则引擎」。核心价值在**分类逻辑**，不在采集。B站官方历史接口仅保留最近约 1000 条 / 3 个月且滚动覆盖，因此：
- 采集交给成熟的 Analyzer / Fetcher（或用户手动拉取）；
- 我们专注做「续看三视图 + 结构化规则 + 可解释跳过」这一被市场验证为缺口的细分。

### 1.2 必须保留并沉淀的差异化壁垒（跨形态复用）
以下逻辑是项目真正壁垒，与 B站机制无关，须抽离为「与语言无关的算法规格 / 可移植模块」（Python 当前可用，JS 待移植），供 D / A / B 任意路线复用：
- `needs`（待续看）/ `skipped`（已跳过）/ `stale`（久未动）三视图，基于 `progress`；
- `auto_skip` + **理由绑定**（可解释性，优于纯隐藏）；
- 单活跃规则 + 多组条件 + 冲突校验 C1/C2/C3；
- `business` 预设一键加入（archive / live / article / pgc）；
- `dirty_count` 增量感知（自上次应用以来新增未套用）。

## 2. 数据源与接入方式选型

### 2.1 2个数据源现状（实测校准，2026-08-24）
| 源 | 位置 | 表结构 | 体量 | 角色 |
|---|---|---|---|---|
| **Analyzer** | `D:\Program Files (x86)\BilibiliHistoryAnalyzer\output\bilibili_history.db` | 按年分表 `bilibili_history_YYYY`，**34 列** | 2813 条（2020–2026） | **主源（read-only 直连）** |
| **Finder 自有** | `D:\Programs\Share\BilibiliHistoryFinder\data\bilibili_history.db` | 单表 `history`，27 列 | 2865 条（近期窗口） | 补充源 |

- 两源互非超集，**合并唯一集 = 3277 条**；Analyzer 含 Finder 永远抓不到的 2020–2025 深历史。
- **canonical `derived` 以 Analyzer 34 列为基准**（最完整 B站 元数据投影）；Finder 多出的仅是分类层与同步簿记，且其 `raw_json` 实测仅 23 键（缺 `business/oid/bvid/cid/page/part/dt/main_category/remark`），**不是真·原始响应权威层**。

### 2.2 接入 Analyzer 的连接方式选型（如何接？有哪些选择？）
均映射进 canonical `derived`（以 Analyzer 34 列为基准，映射量最小）：

| 选项 | 接入方式 | 需起 Fetcher | 数据新鲜度 | 与 Analyzer schema 耦合 | 开发量 | 推荐度 |
|---|---|---|---|---|---|---|
| **① read-only 直连 SQLite（方案 B）** | `file:...?mode=ro` 打开 Analyzer 库，跨年表 `UNION` | 否 | = Analyzer 末次同步 | 强（年表分片 + `_fts`） | 最小 | **已验证·主源（推荐）** |
| **② 调 Fetcher REST API（路径 A）** | `server.py` 瘦适配器，`GET /history/all` + `/history/search`，`X-API-Key` | 是（常驻） | 常新（可触发同步） | 弱（API 契约稳定） | 小 | 常新升级版 |
| **③ 混合（SQLite 读 + API 触发同步）** | 平时读 SQLite 保性能，需刷新时调 API 触发增量再读 | 是（按需） | 常新（按需） | 中 | 中 | 后期优化 |

**选项细节**：
- **① 直连 SQLite**：跨 `bilibili_history_2020…2026` 做 `UNION ALL`，直接拿 34 列原生形状，几乎零映射；跨进程读用只读模式 + 短事务规避写入锁。**最大风险**：Analyzer 改表 / 加年表会断查询——适配器须动态枚举 `bilibili_history_%` 基表（**排除 `_fts` 全文虚拟表**，实测 `SELECT *` 会因 FTS 虚拟表报错）。
- **② 调 Fetcher API**：`GET /history/all?page=&size=&business=&date_range=` 跨年全量分页，返回 `data.records` 含完整字段；可另调同步接口触发增量，拿到比直连 SQLite 更新鲜的全量。CORS 对 `server.py` 服务端调用无影响。
- **③ 混合**：首版不必，待「常新全量」成为刚需再上。

### 2.3 适配为 Fetcher 前端：两条路径设计
> 背景：BilibiliHistoryFetcher（FastAPI `:8899`）是数据后端，官方 BiliHistoryFrontend（Vue3）是其前端。问题：能否把**当前工程的网页前端**改造成 Fetcher 的前端？结论：**能，且两条路径，差异在「规则引擎放哪」**。

#### 2.3.1 Fetcher 接口契约（前端如何与它交互）
- 后端 `:8899`，Swagger `/docs`，CORS 全开，`/health` 免认证，其余需 `X-API-Key`（取自 Fetcher `config.yaml`）。
- `GET /history/all`：跨年全量分页，`available_years` 汇总；参数 `page`/`size`/`sort_order`/`business`/`date_range`/`tag_name`/`main_category`/`use_local_images`；返回 `{status, data:{records, total, size, current, available_years}}`。
- `GET /history/search`：jieba 高级搜索（`search`/`search_type`/`exact_match`/`sort_by`）。
- 单条记录字段（34 列，与 §4.3 Analyzer 同构）：`id`/`title`/`long_title`/`cover`/`covers`/`uri`/`oid`/`epid`/`bvid`/`page`/`cid`/`part`/`business`/`dt`/`videos`/`author_name`/`author_face`/`author_mid`/`view_at`/`progress`/`badge`/`show_title`/`duration`/`current`/`total`/`new_desc`/`is_finish`/`is_fav`/`kid`/`tag_name`/`live_status`。
- 前端配置「服务器地址」→ 扫码登录 →「实时更新」触发后端 `/fetch` 全量 / 增量同步。

#### 2.3.2 两条路径
- **路径 A（server.py 改造为 Fetcher 适配器，最轻，推荐）**：不动前端；只改 `server.py` 数据源——把本地 SQLite 查询换成「请求 Fetcher `/history/all`+`/search`，取全量后套用现有规则引擎（行 191–317 `eval_condition`/`evaluate_rule`/`validate_rule` 零改动）」；分类层（`auto_skip` 等）由适配器补算后注入 `/api/history` 返回结构（前端无感）；`/cover/` 代理仍可用。工作量 ≈ 1 个文件的数据源替换 + 字段整形 + 结果缓存，**规则引擎与前端 100% 复用**。
- **路径 B（去 server.py，前端直连 Fetcher API，最正统但最重）**：浏览器因 CORS 全开可直接 `fetch('http://localhost:8899/history/all', {headers:{'X-API-Key':...}})`；但**规则引擎须移植成 JS**（重写行 191–317），分类状态存 IndexedDB 或后端 `/update-remark` 侧通道——等价于把「方案 D 油猴」搬到独立网页，工作量是重写引擎。**除非要彻底去 Python，否则不如路径 A**。

#### 2.3.3 字段 / 契约映射表（规则引擎需求 ↔ Fetcher 返回）
| 需求（规则引擎 / 前端） | Fetcher 字段 | 适配处理 |
|---|---|---|
| `business`（archive/pgc/live/article） | `business` ✅ | 直用 |
| `progress`（秒，-1=看完） | `progress` ✅ | 直用；`progress_pct` 派生（行 172） |
| `duration` | `duration` ✅ | 直用 |
| `view_at` | `view_at` ✅ | 直用；`view_at_age_days` 派生 |
| `title`/`long_title` | ✅ | 直用 |
| `author_name`/`author_mid` | ✅ | 直用 |
| `bvid`/`uri`/`cover` | ✅ | 直用；封面走 `/cover/` 代理 |
| `kid`（skip 主键） | `kid` ✅ | 直用；无则 `(bvid,view_at)` 合成 |
| `dt`/`live_status` | ✅ | 直用 |
| `archived_only`（私有概念） | ❌ Fetcher 无 | 适配层省略或按「记录是否近期」近似 |
| `auto_skip`/`manual_skip`/`auto_skip_reason`/`skip_state`（分类层） | ❌ Fetcher 不提供 | **适配器用现有规则引擎计算后注入** `/api/history`（路径 A 核心） |

> 映射结论：规则引擎所需字段 Fetcher **全部提供**；唯一需补算的是我们自己的分类层——正是适配器职责，技术上无缺口。

#### 2.3.4 与官方 BiliHistoryFrontend 对比（差异化位置）
| 维度 | 官方 BiliHistoryFrontend | 我们适配后（路径 A） |
|---|---|---|
| 技术栈 | Vue3+Vite+Tailwind+Tauri（重） | 原生 HTML/JS + 1 个 Python 适配器（轻） |
| 覆盖功能 | 历史/年度/评论/收藏/媒体下载/计划任务/设置/视频下载/动态下载（9 大页） | 仅「历史列表 + 续看规则分类」聚焦 |
| 续看三视图 + auto_skip 理由 + 单活跃多组 + 冲突校验 + dirty_count | ❌ 均无 | ✅ 完整（壁垒） |
| 全量历史 | ✅ 后端持续同步 | ✅ 借 Fetcher 后端等同 |

> 定位：官方是「全家桶」分析器；我们适配后是「续看分类器」——互补非竞争。

#### 2.3.5 适配后能力跃迁
1. 从「近期窗口」→「真·全量」：Fetcher 后端持续同步，needs/skipped/stale 才有完整体量。
2. 采集零维护：`collector.py` 可退役，SESSDATA/增量/去重/落库全交 Fetcher。
3. 规则引擎成「跨数据源」资产：同一套 `rules.json`+引擎，既可用于本地库、也可用于 Fetcher 库，为油猴 D 的 JS 移植提供已验证语义基准。

#### 2.3.6 风险与待验证（R1–R5）
- **R1 字段名精确对齐**：Fetcher `/all` 单条确切键名需对 `:8899/docs` 实测（DeepWiki 未逐字段列出）；落地第一步核对 `progress`/`business`/`view_at`/`kid`。
- **R2 分页拉全量**：`/all` 默认 `size=10`，需逐页拉到 `total` 才能套规则算全量三视图；适配层做「全量缓存 + 增量刷新」。
- **R3 `X-API-Key` 配置**：需从 Fetcher `config.yaml` 取 key 注入适配器 / 前端。
- **R4 分类状态归属**：`auto_skip` 等是我们的层，Fetcher 不存；路径 A 下由适配器落 canonical side 小库（`(kid,view_at)→skip`）。
- **R5 与官方前端并存**：同一 Fetcher 后端可同时服务官方前端与我们适配器，互不冲突（只读 + 分类侧存储隔离）。

### 2.4 接入选型结论
- **主源 = ① 直连 Analyzer SQLite（已验证）**：零新增运行时、映射最小（canonical 即以 Analyzer 34 列为基准），直接作全量基。
- Finder 自有采集作**近期窗口补充源**（已走通但为子集，合并进 canonical 即可，后续可退役 `collector.py`）。
- 若需「常新全量」（用户拉取时自动补齐、免去手动跨年合并），再升级到 **② Fetcher API**。
- 三者共用 Phase 0 的 canonical 契约与规则引擎，切换无损。

## 3. 开发路线与阶段编排

### 3.1 总体顺序与理由
**地基（Phase 0）→ 先接 Analyzer 全量（Phase 1）→ 油猴 D（Phase 2）→ 维护（Phase 3）**。
理由：Analyzer 已躺着 2020–2026 深历史（2813 条），是 Finder 近期窗口采集器永远抓不到的；先在全量数据上验证规则引擎，油猴 D 直接复用同一套引擎与 canonical 契约，**避免走两遍**。

### 3.2 Phase 0 — 冻结契约与抽离引擎（前置，不依赖任何存储）
1. 定义并冻结「统一逻辑数据契约」（见 §4.2：raw 权威层 + derived 规范化层，复合主键）。
2. 将 `server.py` 规则引擎（`eval_condition` / `evaluate_rule` / `validate_rule`，行 191–317）抽离为独立可移植模块；`rules.json` schema 定稿（单 active、多分组、字段/操作符集合）。
3. 输出「cursor 响应 / Analyzer 34 列 → canonical derived」字段映射表（一次性工作，供 D / A / B 复用）。

### 3.3 Phase 1 — 接 Analyzer 全量（先于油猴 D，验证规则引擎于全量数据）
1. **直连 SQLite 验证（选项①，已验证主源）**：`server.py` 改为 read-only attach Analyzer 库，跨年表 `UNION` 查询；把 34 列映射进 canonical `derived`（基准即 Analyzer 34 列，映射最小）；规则引擎 / 三视图 / 冲突校验 / `dirty_count` 零改动复用，直接套全量 2813+ 条。
2. **Fetcher API 适配器（选项②，按需升级）**：`server.py` 瘦适配器调 `/history/all` + `/history/search`，分类层（`auto_skip` 等）补算后注入 `/api/history`；拿到常新全量。需 Fetcher 常驻 + `X-API-Key`。
3. **分类状态侧存储**：`auto_skip` / `manual_skip` 等分类层落 canonical side 小库（`(kid,view_at)→skip 状态`），与 Analyzer 源库解耦、互不污染。
4. **验收**：全量记录可在当前网页前端完整筛选 / 三视图分类；验证 Analyzer 深历史（2020–2025）与 Finder 近期窗口合并可行。

### 3.4 Phase 2 — 油猴 D 落地（最终产品形态，复用 Phase 0/1 资产）
1. **油猴骨架**：`@match https://www.bilibili.com/history*`、`@run-at document-start` 的 `fetch` hook；Tampermonkey / Violentmonkey 元数据块；`MutationObserver` 跟随 SPA 重渲染。
2. **双存储（IndexedDB）**：`raw` 仓库（完整 `cursor` JSON 原样，复合 key）+ `derived` 仓库（规范化字段）；**必须抓完整 cursor 响应**（实测 Finder 现版 `raw_json` 缺 `business`/`oid`/`bvid` 等，不能作为权威层）。
3. **规则引擎 JS 移植**：条件组 / 冲突校验 / 三视图 / `dirty_count`，输入为 canonical `derived`（与 Phase 1 同一语义基准）。
4. **原生历史页 overlay**：顶部筛选栏、每条分类角标、命中项隐藏 / 置顶。
5. **浮动规则抽屉**：规则管理（单活跃切换、新增空白 / 预设、二次调整、冲突提示）。
6. **混合形态收口**：原生 overlay 为主 + 浮动面板 / 独立视图为辅（管理规则 + 翻「本地独有」记录）。
7. **被挤掉记录处理**：本地独有（服务端已无）分组；「仍存于 B站 / 仅本地」标注；不回写服务端。
8. **可选增强**：①「加载全部（本页时间窗）」半自动加速按钮；② 轻量导出 JSON/CSV。

### 3.5 Phase 3 — 长期维护
- 跟进 B站历史页（Vue SPA）DOM / 接口变动；Analyzer / Fetcher schema 变动时仅更新 adapter，引擎不变。
- 规则引擎作为「跨数据源资产」持续打磨（同一套语义基准服务 D / A / B）。

## 4. 统一数据契约（canonical schema）

### 4.1 问题
各路线物理存储不同：D 在浏览器 IndexedDB；A / B 在本地 SQLite（Fetcher / Analyzer 已各自落库）。是否要「统一 DB」？统一到什么程度？

### 4.2 结论：统一「逻辑数据契约」，不强求「物理数据库引擎」
- **不统一物理引擎**：浏览器 IndexedDB 与本地 SQLite 各擅其场，且 Fetcher / Analyzer 已各自落库；强行单一物理库会引入 IPC / 跨进程依赖，得不偿失，也破坏「D 零后端」的部署优势。
- **统一逻辑契约（canonical schema）**，所有路线必须遵守：
  - **权威层 `raw`**：完整 `cursor` 响应 JSON 原样存储，`key = (bvid|oid)@view_at`，永不丢字段、永不 FIFO 淘汰。
  - **派生层 `derived`**：规则引擎所需的规范化字段集——`business` / `progress` / `duration` / `view_at` / `title` / `author_name` / `author_mid` / `bvid` / `uri` / `cover` / `kid` / `dt` / `live_status`，加派生字段 `progress_pct` / `view_at_age_days` / `skip_state`（我们的分类层）。
- 规则引擎与 UI **只面向 canonical `derived` 开发一次**；各路线通过 storage adapter 把自身存储映射进 canonical 形式。

### 4.3 实测校准与路线适配
- **canonical `derived` 以 Analyzer 34 列为基准**（最完整 B站 元数据投影）；Finder 多出的仅是分类层 `auto_skip`/`manual_skip`/`auto_skip_reason` 与同步簿记 `created_at`/`updated_at`/`last_seen_sync`/`archived_only`，且**Finder 的 `raw_json` 仅 23 键**（缺 `business`/`oid`/`bvid`/`cid`/`epid`/`page`/`part`/`dt`/`main_category`/`remark`），**不是真·原始响应权威层**——故 Finder 侧 `page`/`part`/`dt`/`main_category`/`remark` 合并进 canonical 时会为空（需重新全量抓取补齐）。
- **路线适配**：
  - **D**：直接在 IndexedDB 建 `raw/derived` 两仓库（双存储设计）。
  - **A（Fetcher）**：其 `/history/all` 返回即 `derived`，字段与 canonical `derived` 几乎一致，仅需整形；`raw` 由 Fetcher 的 `api_responses/`、`history_by_date/*.json` 保留，适配器可读取以保迁移零缺失。
  - **B（Analyzer）**：read-only attach 其 SQLite，映射 `raw/derived` 视图到 canonical。
- 由此，**R1（字段名精确对齐）从「每路线重写引擎」降为「canonical ↔ 各源的一次性映射」**；**R4（分类状态归属）** 统一落 canonical 侧的小 side 存储（`(kid,view_at)→skip 状态`），与源库解耦、互不污染。

### 4.4 统一 DB 的取舍
- **收益**：① 路线间无损切换、零缺失迁移（`raw` 权威层保证）；② 规则引擎 / UI 单一代码库，跨形态复用；③ 迁移工具只需读 `raw`；④ 将来若新增第四种数据源（如 Import JSON），只要映射进 canonical 即可复用全部能力。
- **代价**：① 前期须定义并冻结 canonical schema（设计成本，但一次性的）；② D 路线须自行实现双存储，且**必须抓取「完整 cursor 响应」作 raw 权威层**（实测 Finder 现版 `raw_json` 是裁剪子集，缺 `business`/`oid`/`bvid` 等关键字段，不能作为权威层）；③ 合并两源时，Finder 侧缺的 `page`/`part`/`dt`/`main_category`/`remark` 会留空，属可接受的可选元数据缺失。
- **裁定：是——应基于统一的逻辑 DB 契约开发（非统一物理引擎）。** 这是降低总开发量、保证数据主权（本地超集、不回写服务端）的关键架构决策。

## 5. 各路线评估对比

| 维度 | D 主路线（油猴） | A 接 Fetcher | B 接 Analyzer |
|---|---|---|---|
| 数据全量性 | 3（仅近期窗口） | 5（全量） | 5（全量） |
| 规则引擎保真 | 5（JS 移植） | 5（零改动复用） | 5（零改动复用） |
| 开发量（越大越省） | 4（单文件 JS） | 5（仅改 server.py 数据源） | 5（仅换数据源） |
| 部署便捷 | 5（装插件即用） | 3（跑 Fetcher + server） | 3（跑 Analyzer） |
| 原生体验 | 5（站内 overlay） | 3（独立页） | 3（独立页） |
| 安全(SESSDATA) | 5（浏览器内） | 5（server.py 持有 key） | 5 |
| 对统一 DB 的契合 | 直接实现 canonical | adapter 映射 | adapter 映射 |

> 结论：D 是最终轻量形态（部署最省、原生体验最佳）；A / B 是先行落地的全量验证版与常新升级版（复用同一套规则引擎与 canonical 契约，切换无损）。
