## 2. 重点展开：O3（P2 迁移）—— 唯一"从没设计过"的环节

### 2.1 实测数据（**只读**，未写任何文件、未改任何配置）

按年表统计，并把每条与本地库按 `(bvid, view_at)` 比对：

| 年表                      | 行数       | 唯一 kid  | 其中 `kid=0` | 本地已有     | **需迁入**    |
| ----------------------- | -------- | ------- | ---------- | -------- | ---------- |
| `bilibili_history_2020` | 19       | 19      | 0          | 0        | **19**     |
| `bilibili_history_2021` | 132      | 132     | 0          | 0        | **132**    |
| `bilibili_history_2022` | 46       | 46      | 0          | 0        | **46**     |
| `bilibili_history_2023` | 39       | 39      | 0          | 0        | **39**     |
| `bilibili_history_2024` | 63       | 63      | 0          | 0        | **63**     |
| `bilibili_history_2025` | 64       | 64      | 0          | 0        | **64**     |
| `bilibili_history_2026` | 3685     | **27**  | **3659**   | 2389     | **1296**   |
| **合计**                  | **4048** | 390     | 3659       | 2389     | **1659**   |

**三条结论**

1. **本地库的 2865 条全部是 2026 年**（B站只保留近三个月）→ **2020–2025 那 363 条，本地一条都没有**。
   所以 P2 的真实价值**不是"4048 条"，而是 363 条长尾 ＋ 1296 条 2026 年缺口 = 1659 条**。这也解释了为什么 P2 被称作"唯一有时限的动作"：丢掉就再也拿不回来。
2. **迁移后本地库应为 ≈4524 条**（2865 ＋ 1659），**不是文档写的 ≈4048**；而且**不能整表覆盖** —— 本地有 **476 条 2026 年独有**（Analyzer 没有它）的记录，覆盖即丢。
3. **`kid` 不能用作迁移键**：Analyzer 2026 表 **3659/3685 行的 `kid = 0`**，全库只有 **390** 个唯一 kid（389 个非零 ＋ 1 个 0）。
   代码里 `store.py::_rec_key()` 的注释**早已确认**此事（"`kid` 列 Analyzer 恒为 0、Finder 为 oid"），读取层也**强制覆盖** kid 列 —— 所以迁移**写入时必须自己做键**，不能沿用。

### 2.2 三个必须先定的设计点（O3 的子项）

| 子项      | 要决定什么                            | 建议                                                                    | 不这么做会怎样                                     |
| ------- | -------------------------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| **O3a** | 合并口径：**整表覆盖** 还是 **按 `(bvid, view_at)` upsert** | **upsert**                                                            | 覆盖 → **丢 476 条** 2026 年本地独有记录（Finder 自己抓到的）  |
| **O3b** | 本地表 `kid` **主键**填什么（`kid TEXT PRIMARY KEY`） | 用 `f"{bvid}_{view_at}"`，与 `_rec_key()` 一致                            | 直接用 Analyzer 的 kid → **3659 个 `0` 主键冲突**（或只剩 1 条） |
| **O3c** | 本地表是否**加 `remark` / `remark_time` 列** | **加**                                                                | **389 条带备注的行里，363 条正是 2020–2025 长尾** —— 不加列 = 迁进来的长尾没有备注 |

> **O3c 的注**：备注覆盖与长尾分布高度重合（2020–2025 共 363 条带备注，2026 表另有 26 条，合计 389 条）。也就是说 —— **P2 想保住的那批东西，恰好就是带备注的那批东西**。这条不是可选项。

### 2.3 一个被夸大的担心（澄清，可不处理）

`raw_json` 缺失：1659 条新记录没有 `raw_json`（本地表的 `raw_json` 由直抓写入）。一度担心影响 `dt` / `live_status`。
**实测澄清：影响很低** —— `raw_json` 的唯一消费点是 `store.py::_read_local()` 里取 `dt` / `live_status`，而 `dt` 在整仓**唯一的消费点**是 `app.js:967` 从 DOM dataset 读取（`state.dt = el.dataset.dt`），**不是从记录读**。→ 迁移后这批记录 `dt` 为空，**无人消费**。记一笔即可。

### 2.4 一处口径细节（自洽性校验）

按 `(bvid, view_at)` 算并集时会**略高估** —— 本地 2865 条里有 **11 条 `bvid` 为空**，`_rec_key()` 会回退到 `(oid, view_at)` 键。
所以 **4524 是上界**，实际合并数 ≈ **4513**（4524 − 11），**与 `待办-当前阶段.md` §零 记录的"合并 4513"完全一致** → 口径自洽，交叉验证通过。

### 8.4 ⭐ 实测核出的 4 处设计问题（都在实现中被修正）

这 4 处**都不是笔误**，而是"纸面设计 vs 真实数据 / 真实契约"的差距：

| # | 问题 | 怎么发现的 | 修正 |
| --- | --- | --- | --- |
| **1** | **R3 判据本身是错的** —— 原设计"缺口 = 主源 − 本地" | 冒烟实测 `analyzer_days=2452` / `local_days=134` → R3 **立刻命中 `full`**。但这是 B站接口"只保留近三个月"造成的**结构性差异**，不是缺口 → 会**每 7 天白跑一次全量**（而全量同样补不回 2020–2024） | 判据改为 **本地跨度 vs 历史峰值**（`span_peak_days`；阶段 1 恒为 None → **保守不触发**）；结构差异降级为 `advisory`，**文案直接指向 P2 迁移** |
| **2** | **`merged` / `effective` 会谎报** —— `probe` 读的 `_LAST_SOURCE` 是"上一轮 reload 的结论"，首次调用时是初始值 | 冒烟实测 `merged=0` / `effective=null`（真实值 **4513** / `analyzer`） | `probe_connection()` 先调 `store.get_raw()`（只读 ＋ 走模块缓存）确保数据已加载 |
| **3** | **`connection.finder` 键名漂移** —— 产出用 `state`、能力层读 `sessdata` | `--live` 的"用**真实响应**再喂一次纯函数"断言。**7 个单测段全绿**（样本是我自己写的，两个名字都填了）→ 只有真实产出能抓到 | `_finder_sessdata_status()` 统一返回 **`sessdata`**；并**新增断言**用真实 finder 段驱动能力层，防再次漂移 |
| **4** | **能力层与策略层会自相矛盾** —— `unknown` 凭证下，能力说"不能抓"、策略说"可以增量" | 写单测时发现的语义缺口 | 两侧**共用同一判据**：只有 `present` 放行，`missing` / `unknown` 一律保守 → 新增"一致性地板"断言（5 组组合） |

> **教训（已写进 `dev/README.md` 第三条经验）**：单测里自造的样本只能证明"算法对"。**凡是有"两侧约定"的结构（probe ↔ 能力层、请求 ↔ 响应），必须有一条断言拿真实产出驱动消费方。**
