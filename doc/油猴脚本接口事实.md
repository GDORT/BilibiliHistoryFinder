## 二、请求

```
//api.bilibili.com/x/web-interface/history/cursor
```

**首屏请求**（无游标）：

```
?ps=20&type=archive&web_location=333.1391&x-bili-locale-json={...}
```

**后续分页**（带游标）：

```
?max=117314867432857&view_at=1791536669&business=archive&ps=20&type=all&web_location=333.1391&...
```

| 参数 | 含义 | 备注 |
| --- | --- | --- |
| `ps` | 每页条数 | **实测 20**（不是 30） |
| `max` | 游标 = **上一页最后一条的 `kid`** | ⭐ 见「关键发现 3」 |
| `view_at` | 游标 = 上一页最后一条的观看时间 | 与 `max` 配对 |
| `business` | 内容类型（实测出现 `archive`） | ⭐ 见「限制 1」 |
| `type` | 首次 `archive`，后续 `all` | 页面按 tab 变 |
| `web_location` / `x-bili-locale-json` | 页面埋点参数 | 与我们无关 |

## 三、响应

```jsonc
{
  "code": 0, "message": "0", "ttl": 1,
  "data": {
    "cursor": { "max": 117314867432857, "view_at": 1791536669,
                "business": "archive", "ps": 20 },
    "list": [ { /* 每条 = 下面这些字段 */ } ]
  }
}
```

### 顶层字段（**23 个**，实测全量）

| 字段 | 说明 |
| --- | --- |
| `kid` | ⭐ **B站自己的历史记录唯一 ID**（15 位数字） |
| `title` / `show_title` / `long_title` | 标题三种形态 |
| `cover` / `covers` | 封面（单图 / 多图） |
| `uri` | 跳转链接 |
| `author_mid` / `author_name` / `author_face` | UP主 ID / 名 / 头像 |
| `duration` | 时长（秒） |
| `progress` | 观看进度 |
| `is_finish` | 是否看完 |
| `is_fav` | 是否收藏 |
| `view_at` | 观看时间（Unix 秒） |
| `history` | ⭐ **子对象**（见下） |
| `videos` / `total` / `current` | 分 P 信息（总集数 / 当前集） |
| `badge` / `tag_name` / `new_desc` / `live_status` | 角标 / 标签 / 描述 / 直播状态 |

### `history` 子对象（**8 个**）

| 字段 | 说明 |
| --- | --- |
| `bvid` | BV 号 |

| `epid` | 剧集 ID（影视） |

## 四、关键发现（**直接影响后续设计**）

### 1. 页面用的是 `fetch`，不是 XHR

8 条 **全部** `via=fetch`，XHR 一条都没有。

⇒ 后续可以**只保留 fetch hook**（XHR 那套作为保险先留着，等 M3 稳定后再决定去留）。
这对性能与复杂度都是好消息。

### 2. 顶层**没有** `bvid` / `oid` / `cid`

它们全在 `history` 子对象里（与我 mock 的结构一致，原设计判断**被实测证实**）。

⇒ `raw` 层必须**整条原样存**，不能只挑顶层字段 —— 否则永远拿不到 bvid。

### 3. ⭐ `cursor.max` 就是 `kid`

游标 `max` 是 15 位数字，与 `kid` 同构；下一页请求直接把上一页的 `max` 传回去。

⇒ **主键用 `kid`，不要用 `bvid@view_at`**。
   Finder 那边的 `bvid_view_at` 只是「`kid` 缺失时的兜底」（`collector.py:241`），
   而真实响应**直接给了 `kid`**，两者不必一致 —— 油猴版应直接用 `kid`。

### 4. 每页 20 条，靠滚动加载

时间线显示请求间隔很大（193ms → 12.4s → 40.8s → 65s…），是用户**滚动触发**的，不是一次拉完。

⇒ 旁听模式下**数据量的多少取决于用户滚多少**，见「限制 1」。

### 5. `is_finish` 可直接判定"看完"

顶层就有 `is_finish`，比 Finder 用 `progress == -1` 判断更直白。
M1 移植引擎时要注意这个差异（derived 层可以先归一化）。

### 6. `videos` / `total` / `current` 是分 P 信息

同一 `bvid` 可能有多个分 P（`videos` 总数、`current` 当前集）。
⇒ 去重键若只用 `bvid` 会**丢分 P**；用 `kid` 则天然区分（每次观看一条记录）。

## 五、已知限制

### 限制 1：旁听只能拿到「用户实际浏览过的类型」

实测请求里 `business=archive`、`type=archive/all` 混着出现。
若用户没点某个分类 tab，那部分历史**就不会发请求、也就抓不到**。

- 这不影响 M0–M4（基于拿到的记录做分类/排序）
- **M5（收口）时必须处理**：要么明示"只覆盖已浏览分类"，要么主动补请求
  （主动 GET 不违反「不回写」红线，但**会消耗风控额度**，需单独拍板）

### 限制 2：数据窗口天花板（≈3 个月）

`history/cursor` 本身只返回近期数据（与 Finder 侧认知一致，`store.py:134`）。
这是**服务端限制，结构性无解** —— 长期留存仍要靠定期导出回灌 Finder。

### 限制 3：单次会话抓不全

滚动才加载 ⇒ 想抓全需要用户从头滚到尾，否则只有部分。
（同上，M5 时权衡是否主动分页抓取。）

## 七、真实历史页 DOM 结构（2026-10-09 由 `inspect-dom.js` 实测）

> 这一节是**页面结构事实**，与上面的接口结构同源，改 overlay 前先看这里。

### 容器与卡片

| 项 | 实测值 |
| --- | --- |
| 列表容器 | `div.history-list`（392 个视频链接）／外层 `main.history-record`（同 392） |
| 卡片 | `.bili-video-card`（由子元素 `.bili-video-card__cover` 的 BEM 块名推得） |
| 卡片里的链接 | `<a href=".../video/BVxxxx?spm_id_from=...">` |

### ⭐ 关键发现 7：**卡片不带 `kid` 属性** → 必须靠链接反查

实测卡片属性只有 `class`（及 Vue 的 `data-v-*`），**没有任何 15 位数字的 `kid` 属性**。
⇒ DOM→记录不能靠属性，改为按链接 **`uri` → 路径 → `bvid`** 三级反查（`Overlay.buildResolver`）。

### ⭐ 关键发现 8：`kid` 并非都是 15 位；直播记录**没有 `bvid`**（修正发现 3 的适用范围）

实测库中样本：`kid` 有 `5050`（直播）、`22230707`（直播）、`324911870`（视频）等，**并非都是 15 位**。
且**直播记录只有 `uri`（`https://live.bilibili.com/5050`）、没有 `bvid`**。
⇒ 仅按 `bvid` 匹配会**漏掉全部直播**。因此匹配**必须 `uri` 优先、`bvid` 仅兜底**。

### 同一 uri 多条记录

同一视频看多次 ⇒ 多个 `kid`、**同一个 `uri`**。`buildResolver` 用「桶 + 按 `view_at` 倒序消费」，
让这些记录按卡片在 document 中的先后依次对应（跨多个 `.history-list` 容器也保持顺序，见 `bootstrapAll`）。
