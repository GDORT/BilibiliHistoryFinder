## 1. 目标运行状态与架构

### 1.1 三方并存模型
```
┌─────────────────────────────────────────────────────────┐
│  用户本机                                                 │
│  ┌──────────────────┐   read-only 直读 + 转发触发         │
│  │  BilibiliHistory │   ┌──────────────────────────────┐ │
│  │  Analyzer 后台   │   │  我们的服务 (server.py)      │ │
│  │  (Fetcher 打包)  │──▶│  - 读 Analyzer SQLite(ro)    │ │
│  │  - 拉取/分析B站  │   │  - 规则引擎 + 三视图         │ │
│  │  - 写 bilibili_  │   │  - 转发 /fetch/* 到 8899     │ │
│  │    history.db    │   │  - 侧库 canonical_state.db   │ │
│  │  - 暴露 :8899    │   └───────────┬──────────────────┘ │
│  └──────────────────┘              │ 网页 (app.js)        │
│  ┌──────────────────┐              │ 展示/筛选/触发按钮   │
│  │  Finder 后台     │──▶ read-only  │                     │
│  │  (collector.py)  │   备份源并入  └─────────────────────┘ │
│  │  自有采集兜底    │                                          │
│  └──────────────────┘                                          │
└─────────────────────────────────────────────────────────┘
```
- **Analyzer 后台**：唯一权威数据 + 控制源；常驻时 `:8899` 提供 `/history/*` + `/fetch/*`。
- **Finder 后台（collector.py）**：仅作近期窗口兜底备份源，**按需经「同步数据」按钮调用**（非自启）；Phase 1 合并已自动包含，无额外开发。其 SESSDATA 已失效（`-101`），**计划 A 待停用**（见 §7.4）。
- **我们的服务+网页**：消费 Analyzer（只读）+ 触发其控制端点（转发），不重复造拉取层。

### 1.2 需求本质与差异化壁垒（跨形态复用）
- 需求本质：**续看/历史筛选分类的规则引擎**，非"再做一个历史抓取器"。
- 壁垒（须抽离为与语言无关的算法规格，供后端 Python / 前端 JS / 油猴 D 复用）：
  - `needs`/`skipped`/`stale` 三视图（基于 `progress`）；
  - `auto_skip` + 理由绑定（可解释性）；
  - 单活跃规则 + 多组条件 + 冲突校验 C1/C2/C3；
  - `business` 预设一键加入；`dirty_count` 增量感知。

| **Finder 自有** | `D:\Programs\Share\BilibiliHistoryFinder\data\bilibili_history.db` | 单表 `history`，27 列 | 2865 条（近期窗口） | 补充源（按需调用） |

### 2.2 接入 Analyzer 的连接方式选型
| 选项 | 接入方式 | 需起 Fetcher | 推荐度 |
|---|---|---|---|
| **① read-only 直连 SQLite（已验证·主源）** | `file:...?mode=ro` 跨年表 `UNION`，排除 `_fts` 虚拟表 | 否 | **主源（推荐）** |
| **② 调 Fetcher REST API（常新升级版）** | `server.py` 瘦适配器 `GET /history/all`+`/search` | 是（常驻） | 常新升级 |
| **③ 混合（SQLite 读 + API 触发同步）** | 平时读 SQLite，需刷新时调 API 触发增量再读 | 是（按需） | 后期优化 |

- **① 直连 SQLite**：跨 `bilibili_history_2020…2026` 做 `UNION ALL`；最大风险是 Analyzer 改表/加年表会断查询——适配器须动态枚举 `bilibili_history_%` 基表（排除 `_fts`）。
- **② 调 Fetcher API**：可拿比直连更新鲜的全量；CORS 对服务端调用无影响。

### 2.3 能否替代官方 BiliHistoryFrontend（源码评估结论整合）
> 评估依据：已置本地的真实源码副本 `doc/BiliHistoryFrontend-master/`（前端）与 `doc/BilibiliHistoryFetcher-master/`（后端），**仅读源码**。
> 详细评估原稿 `doc/BiliHistoryFrontend替代评估.md` 与 `doc/Fetcher后端源码评估.md` 已归档至 `doc/archive/`，本节为其结论浓缩。

#### 2.3.0 主结论（一句话）
**能完整替代，且是「功能子集」级别的替代。** 官方前端没有任何独占能力——它是 Fetcher/Analyzer 产物的「显示器 + 遥控面板」，不掌握数据、不掌握控制逻辑、不掌握凭证。我们工程已具备它的全部展示能力（且筛选更强），唯一缺的「触发分析」只是 Fetcher 后端接口，加一层转发即可；Analyzer 是否在运行只影响「能否触发新分析」，不影响「能否替代前端」。

#### 2.3.1 官方前端的真实架构（源码实证）
- 纯前端壳，零后端逻辑（`src-tauri/tauri.conf.json` 仅窗口/打包配置，无内嵌 HTTP server）。
- 「控制 Analyzer 更新」= 前端调 Fetcher 后端 `/fetch/*`（`src/api/api.js`）：实时增量 `GET /fetch/bili-history-realtime`、全量 `GET /fetch/bili-history` → `POST /importSqlite/import_data_sqlite`。**前端只是触发者与展示者，执行者在 Fetcher 后端。**
- 渲染契约（`HistoryContent.vue`）：`bvid/oid/aid/avid/epid/ssid/cid/cover/covers/author_face/author_mid/author_name/tag_name/business/dt/view_at/progress/duration/remark`——与 Analyzer 34 列同构。

#### 2.3.2 Fetcher 后端 = Analyzer 的控制大脑（源码实证）
- **Analyzer 无独立源码**：它是 Fetcher 的 PyInstaller 打包产物（`dist/BilibiliHistoryAnalyzer/BilibiliHistoryAnalyzer.exe`），能力全部来自 Fetcher 后端。
- **控制端点无头可触发**（`routers/fetch_bili_history.py`）：`GET /fetch/bili-history`（全量，:94）、`GET /fetch/bili-history-realtime`（增量，:131）；**无需请求体，SESSDATA 从服务端 `config.yaml` 读取**——外部只要能访问 `localhost:8899` 即可触发。
- 写库链路完整：拉取 → 落 JSON 快照 → `import_all_history_files()` 更新 Analyzer 读的那个 `bilibili_history.db` → 顺带补互动。
- `/mcp` 是**只读 MCP 服务**（只暴露读、不暴露写），印证我们 read-only 路线正确。

#### 2.3.3 替代可行性矩阵（前端功能逐项）
| 官方前端功能 | 我们能否替代 | 说明 |
|---|---|---|
| 展示历史记录（列表/卡片/封面/UP主头像） | ✅ 完全能 | 已 read-only 消费 Analyzer 产物，字段契约同构 |
| 搜索 / 筛选（FTS5 + 基础筛选） | ✅ 完全能，且更强 | 我们高级筛选器是其超集 |
| 触发分析 / 导入（点按钮让 Analyzer 重跑） | ✅ 能，但需转发到 8899 | 原非前端自身能力，是借 Fetcher 的；server 加转发 + 前端按钮即可 |
| 年度分析 20+ 页 / 收藏 / 评论 / 动态 / 下载 | ❌ 不直接替代 | 来自 Fetcher 后端 API 面，前端只是消费；按需对接共存 |
| 二维码登录 / 计划任务 | ❌ 不直接替代 | 同样来自 Fetcher 后端，前端仅按钮 |

#### 2.3.4 与官方前端对比（差异化位置）
| 维度 | 官方 BiliHistoryFrontend | 我们（替代后） |
|---|---|---|
| 技术栈 | Vue3+Vite+Tailwind+Tauri（重，桌面 exe） | 原生 HTML/JS + 1 个 Python 服务（轻，浏览器即用） |
| 覆盖功能 | 全家桶（历史/年度/收藏/评论/媒体下载/计划任务/动态…） | 聚焦「历史列表 + 续看规则分类」 |
| 续看三视图 + auto_skip 理由 + 单活跃多组 + 冲突校验 + dirty_count | ❌ 均无 | ✅ 完整（我们的壁垒） |
| 高级筛选 | 基础（类型/日期/分区） | ✅ 超集级（已实现） |
| 全量历史 | ✅ 后端持续同步 | ✅ 借 Fetcher 后端或直读 Analyzer 等同 |

#### 2.3.5 两条对接路径（替代后的控制层如何接）
- **路径 A（server.py 加 Fetcher 转发层，最轻，推荐）**：`server.py` 加薄代理——`POST /api/trigger-realtime` → `GET http://localhost:8899/fetch/bili-history-realtime`；前端加「实时更新」按钮；分类层仍由我们引擎补算注入 `/api/history`。**规则引擎与前端 100% 复用，零重写拉取逻辑。** 前提：用户本机 Fetcher 后端（Analyzer 后台）在运行。
- **路径 B（去 server.py，前端直连 Fetcher API）**：浏览器因 CORS 全开可直 `fetch('http://localhost:8899/history/all')`；但规则引擎须移植成 JS（重写），工作量等同重写引擎。**除非要彻底去 Python，否则不如路径 A。**

#### 2.3.6 字段 / 契约映射（规则引擎需求 ↔ Fetcher/Analyzer 返回）
| 需求 | Fetcher/Analyzer 字段 | 处理 |
|---|---|---|
| `business` | `business` ✅ | 直用 |
| `progress`/`duration`/`view_at` | ✅ | 直用；`progress_pct`/`view_at_age_days` 派生 |
| `title`/`author_*`/`bvid`/`uri`/`cover` | ✅ | 直用；封面走 `/cover/` 代理 |
| `kid`（skip 主键） | `kid` ✅ | 直用；无则 `(bvid,view_at)` 合成 |
| `aid/avid/epid/ssid/cid/covers/author_face` | ✅ 但 `ANALYZER_COLS` 未全纳入 | 若直连 Fetcher `/history/all` 需补齐 |
| `auto_skip`/`skip_state`（分类层） | ❌ 不提供 | **我们的引擎计算后注入** |

### 2.4 接入选型结论
- 主源 = ① 直连 Analyzer SQLite（已验证）；Finder 自有采集作近期窗口补充源。
- 若需「常新全量」或「替代官方前端 + 获得触发分析能力」（见 §2.3），走 ② **中继 Fetcher API**（路径 A 转发，**当前实现**）。
- **术语澄清（2026-09-25，原 #10 / §0.1 已改名）**：本文件里的「**直连**」专指
  **Finder 自己持凭证、自己向 B站发抓取请求**（即 `collector.py` 那条路），
  与「调用 Fetcher 的 HTTP API」是两回事——后者执行者仍是 Analyzer，属**中继**。
  → **`/api/fetcher-trigger`(②③)、`/api/fetcher-check`(④) 都是中继**；
  **只有 `POST /api/sync` 走 `collector.py` 才算直连**（其凭证已失效 -101）。
- **「直连抓取」的定位 = 轻量 Finder 的规划项**：它不被当作"更强的抓取"，而是
  **Analyzer 缺席时的降级自持能力**（模式 B）。落地形态见 `doc/archive/说明-主备架构与数据模式.md` §3：
  由数据源主开关 `data_source.mode` 显式选择，**不自动回退**。
- 三者共用统一 canonical 契约与规则引擎，切换无损（`kid=(bvid,view_at)` 跨模式一致）。

### 3.6 工程架构现状（Phase 1 实测，吸收自 `架构分析.md`）
> 原 `doc/架构分析.md` 已归档至 `doc/archive/`，其核心内容吸收于此节。

**分层与数据流**（数据源只读 → 读层/合并 → 规则引擎 → 分类/查询 → HTTP 编排 → 前端）：
```
B站服务端(仅collector备用)   Analyzer SQLite(主源,RO,34列/年表)   Finder SQLite(备份源,RO,27列)
        │                            │                              │
        ▼                            └── store.py 合并 ─────────────┘ (统一复合键 (bvid,view_at) 去重)
   data/bilibili_history.db ◄───────────────────────────────────────┘
        │
   store.py — 读多源 → canonical records（RAW_CACHE 模块级缓存）
        │  _read_analyzer() file:?mode=ro 跨年表 UNION（排除 _fts 虚拟表）
        │  _read_local()    file:?mode=ro 读 history 表
   engine.py — 纯逻辑规则引擎（无 I/O）：eval_condition / eval_group / evaluate_rule / validate_rule / classify
        │
   store.py — classify_record() 计算分类 + 侧状态库 canonical_state.db（唯一可写）
        │
   server.py — ThreadingHTTPServer + 后台线程；GET/POST /api/* · /cover/ 代理 · 静态资源
        │
   web/ — 原生 SPA（index.html / app.js / style.css）
```

### 3.8 规则引擎核心（吸收自 `记录筛选规则分析.md` §2–§10）
> 原 `doc/记录筛选规则分析.md` 已归档，规则引擎核心（三视图/优先级/冲突/dirty_count）吸收于此；其 §11「高级筛选器超集」归前端轴（见 `方案-前端.md` §3）。

**数据模型与进度语义**：输入 canonical derived；`progress==-1` 表示已看完 → `progress_pct=1.0`；`view_at_age_days=(now-view_at)/86400` 派生。

**`rules.json` 结构**：单 `active` 规则（同一时刻仅一条，`server.POST /api/rules` 强制校验 C6）+ 多 `groups`（`match:"any"`=OR 语义，命中任一分组即按该分组 `action` 处理）。

**求值算法**：`eval_condition`（单条件）→ `eval_group`（分组内 AND）→ `evaluate_rule`（返回 `(action,label)` 或 `None`；`progress==-1` 短路返回 `None`；首命中优先）。

**三视图模型**（不变式 `finished+auto_skip+stale+needs==total`）：
- `finished`：已看完（progress=-1）
- `auto_skip`：命中 auto_skip 分组
- `stale`：命中 stale 分组（久未观看）
- `needs`：未完成且未被跳过（待观看）
- 实测（default 规则，**2026-09-25 折叠后 4450 条**）：**2153 / 1510 / 0 / 787**（2026-08-24 快照为 1473 / 1226 / 0 / 579；口径随数据增长变化）。

**跳过状态与优先级**：`manual_skip`（人工）> `auto_exempt`（取消自动跳）> `auto_skip`（引擎）；`needs` 视图有隐含 95% 门（progress_pct≥0.95 归入 auto_skip 而非 needs）。

**冲突校验 `validate_rule`**：返回 `{hard, soft, info}`（C1 重复条件 / C2 互斥 action / C3 无效字段；C6 多 active 由 server 强制）。

**增量感知 `dirty_count`**：`rules_hash` 比对「已应用哈希」与当前规则，统计上次应用以来新增未套用条数；`rules_status()` 返回 pending + dirty_count。

**默认规则行为复盘**：5 分组（接近看完/误触/短视频碎片/直播回放/陈旧），default 下 auto_skip 多为短视频碎片（duration<60）、needs 多为低进度长视频——符合预期。

## 4. 统一数据契约（canonical schema）

### 4.1 结论：统一「逻辑数据契约」，不强求「物理数据库引擎」
- **不统一物理引擎**：浏览器 IndexedDB 与本地 SQLite 各擅其场；强行单一物理库会引入 IPC/跨进程依赖，破坏「D 零后端」优势。
- **统一逻辑契约（canonical schema）**，所有路线必须遵守：
  - **权威层 `raw`**：完整 `cursor` 响应 JSON 原样存储，`key = (bvid|oid)@view_at`，永不丢字段。
  - **派生层 `derived`**：规则引擎所需规范化字段集——`business`/`progress`/`duration`/`view_at`/`title`/`author_name`/`author_mid`/`bvid`/`uri`/`cover`/`kid`/`dt`/`live_status` + 派生 `progress_pct`/`view_at_age_days`/`skip_state`。
- 规则引擎与 UI **只面向 canonical `derived` 开发一次**；各路线通过 storage adapter 映射进 canonical 形式。

### 4.2 实测校准与路线适配
- canonical `derived` 以 Analyzer 34 列为基准；Finder 的 `raw_json` 仅 23 键，不是真·权威层。
- 路线适配：D 在 IndexedDB 建 raw/derived 双仓库；A（Fetcher）其 `/history/all` 返回即 derived；B（Analyzer）read-only attach 映射。
- 由此 R1（字段对齐）降为「canonical ↔ 各源一次性映射」；R4（分类状态）统一落 canonical side 小库。

### 4.3 统一 DB 的取舍
- **收益**：路线间无损切换、零缺失迁移；规则引擎/UI 单一代码库跨形态复用；新增第四种数据源只需映射进 canonical。
- **代价**：前期须冻结 canonical schema（一次性）；D 须实现双存储且抓完整 cursor；合并时 Finder 侧缺字段留空（可接受）。
- **裁定：基于统一逻辑 DB 契约开发（非统一物理引擎）。**

### 7.8 最新记录出现"重复视频"的根因分析（2026-09-25）
> ⚠️ **后续修订（2026-09-25 第二轮）**：本节采纳的「**方案 A**：只保留 `view_at` 最大一条」
> 经实测发现**功能性缺陷**——会丢掉「已看完」状态，使 **7 条**视频被误判为「需要观看」。
> 已改为 **§7.11.1 的 Plan B「折叠显示 + 状态聚合」**（`progress` 取 `-1` 优先、新增 `kids` 多键命中）。
> 本节保留作为**根因证据链**（B站按观看会话记录、三方都不折叠的实证），但**折叠规则以 §7.11.1 为准**。
> 详细论证见 `doc/archive/说明-同bvid多会话策略.md`。
>
> 用户反馈：网页最新历史里同一视频出现多条。经数据库实证，结论为**非数据 bug，是 B站原生行为 + 未做"按视频合并"显示**。

**实证过程**：
1. Analyzer 7 张年表实有 **4025** 行（注：早年误报 8383 是把 `_fts` 全文虚表行数也累加进去了，已排除；`bilibili_history_2026` 单表 3662 行）。本地库 `history` 2865 行。
2. 两库各自按 `(bvid, view_at)` 查重：**重复组均为 0**（Analyzer 0、本地 0）。
3. 复现 `store.py` 合并（`merged=dict(analyzer)` + 本地独有并入，键 = `_rec_key=(bvid,view_at)`）→ 合并后 **4490** 条。
4. 按 bvid 聚合：出现 >1 次的 bvid 共 **37** 个，**全部是"同 bvid、不同 view_at"，0 个真·(bvid,view_at) 重复**。
5. 样例（均 `source=analyzer`，今天产生）：
   - `BV1STaM6pEUx`《【舍长】¥328的〈控制2〉》→ 3 条 `view_at` = 1790326865 / 1790325146 / 1790316134（跨度约 2.5h）
   - `BV1N7ag6WEzv`《网红长蛋挞》→ 2 条 `view_at` = 1790318639 / 1790316185
   - `BV1ZpbK6XEtX`《房贷延期至40年》→ 2 条

**根因**：
- B站历史接口**每次"观看会话"记一条独立记录**（带各自 `view_at`），同一视频当天多次打开 → 多条；这是 B站官网历史页的固有行为。
- 我们的合并键 `_rec_key=(bvid,view_at)` 把不同 `view_at` 正确视为不同条目，**去重逻辑本身无误**。
- 显示层**未像 B站官网那样"按视频（bvid）合并、只留 view_at 最大的一条"**，故同一视频的多条会话记录全部铺开。
- 今日跑 Step ②/③（增量/全量拉取）把当天新产生的多条会话记录拉进了 Analyzer，浮到列表顶部 → 用户直观感觉"重复"。

**关键澄清：Analyzer 与开源 Frontend 怎么处理（经源码核对）**：
- **Analyzer（8899）**：年表建表即 `UNIQUE(bvid, view_at)`（`config/sql_statements_sqlite.py:47`）——**每次观看会话是一条独立行，设计上就保留全部会话，不按 bvid 合并**。入库防重有两道：① 同一批抓取内用 `(bvid,view_at)` 集合去重，跳过已存在的精确组合（`scripts/bilibili_history.py:101-129`）；② 翻页依据 `view_at` 倒序游标，遇到 `new_view_at >= last_view_at` 立即停止请求（`bilibili_history.py:1126-1167`），避免把已存旧会话重复拉回。即：**Analyzer 保留全部会话、但永不插入真重复**。
- **开源 Frontend（直连 8899）**：`utils/historyRecordStore.js` 会话缓存 key = `bvid_viewAt`（按会话）；`HistoryContent.vue` 卡片 `:key="grid-${record.id}-${record.view_at}"`、选中态 `bvid_view_at`（`HistoryContent.vue:75,114`）；`page/History.vue` **无任何 groupBy/Map/Set 去重**。即：**Frontend 把 Analyzer 返回的全部行原样铺成卡片，同样不按 bvid 折叠**——开源 Frontend 也会出现"同一视频多条"的观感。
- **结论**：我们的 Finder 合并键 `(bvid,view_at)` + 显示全会话，**与开源 Frontend 行为完全一致**，Analyzer 也保留全部会话。三方都不做"按 bvid 折叠"，这是与 B站官网（只留每视频最新一条）的差异，**不是 Finder 的 bug，也不是与 Frontend 的偏离**。

**裁定与落地（2026-09-25）——采用方案 A（显示层按 `bvid` 折叠），目标对齐「B站官网历史页」而非开源 Frontend**：
> 用户明确定位：**网页就是要与 B站官网行为一致**（同一视频只显示最近一次观看），而非与开源 Frontend 一致。故采用 **A**（Frontend 本身不折叠，属"对齐 Frontend 就选 C、对齐官网就选 A"，此处按官网）。

| 方案 | 做法 | 影响 | 裁定 |
|---|---|---|---|
| **A 显示层折叠** | `store.load_raw_records()` 末尾新增 `_fold_latest_by_bvid()`：同 `bvid` 只保留 `view_at` 最大的一条；无 `bvid` 的直播/专栏不折叠；**保留原始记录 dict（含其 `kid`）**不重算键 | 不动 `kid`/跳过键，`canonical_state.db` 既有 skip 标记**不受影响、无需迁移**；列表与官网一致 | ✅ **已采用·已落地** |
| B 数据层合并 | 改合并键为 `bvid` 取最新落库 | `kid` 变化**作废既有 skip 标记**，需迁移 | 未采用 |

### 7.9 网页可控：⑥ 热重载 / ⑦ 重启服务（2026-09-25 落地，已被 §7.10 合并升级）

**动机**：改代码后每次都要关掉窗口重开 `start.bat` 才能生效。实测显示重启成本本身极低（数据层就绪 0.13 s），做成网页可控很划算。

**实测资源（2026-09-25，本机）**：

| 项 | 实测值 |
|---|---|
| 8765 单实例内存 | WS **38.7–45.1 MB**（私有提交 27.5–30.2 MB） |
| 同解释器裸基线 | 25.8 MB → **服务自身净增 13–19 MB** |
| 对照：Analyzer 进程 | WS **621.5 MB** / 私有 **1543.6 MB**（≈ 8765 的 14–35 倍） |
| 数据层就绪（4450 条） | **0.127 s**（import 0.015 + 读两库折叠 0.058 + import server 0.055） |
| cmd.exe 宿主窗口 | **5.0–5.2 MB**（本来就要开着的那个窗口） |
| 新增常驻进程 | **0**（A + C-lite 均不新增） |

**最终方案 = ⑥ 热重载（A） + ⑦ 重启服务（C-lite：`start.bat` 自当 supervisor）**：

| 能力 | 端点 | 覆盖范围 | 机制 |
|---|---|---|---|
| **⑥ 热重载** | `POST /api/reload` | `engine.py` / `store.py` / `rules.json` / 源库只读重读；静态前端只需浏览器刷新 | `importlib.reload(engine/store)` + `ensure_rules()` + `reload_all()`；**不重启进程、不释放端口**；实测 65–292 ms |
| **⑦ 重启服务** | `POST /api/restart`（`?dry=1` 仅探测托管状态；真重启需请求头 `X-BHF-Confirm: restart`） | **全部**（含 `server.py` 自身路由/Handler） | 回 200 → 0.6 s 后 `httpd.shutdown()` + `server_close()` → `os._exit(42)` → `start.bat` 收到 42 → `timeout /t 2` → `goto RUN` 重新拉起 |

**`start.bat` 改造（supervised 模式，保持纯 ASCII + CRLF）**：主路径包一层循环 `:RUN → 判 errorlevel → :RESTART → goto RUN`，并在启动前 `set "BHF_SUPERVISED=1"`（供网页判断"重启后能否自动拉起"，`⑦ dry` 会回报 `supervised`）。误触发防护：Ctrl+C（退出码 0）、`stop.bat` 的 taskkill（退出码 1）**都不等于 42**，不会被误判为重启请求；**`stop.bat` 无需改动**。

**为什么不选"纯自重启（无 supervisor）"**：风险集中在①新进程起不来时旧进程已退出 → **服务静默失联、无控制台可见错误**；②若改成"先起新再退旧"，会出现**双绑定窗口期**（见下）。业界惯例：长期运行一律外部 supervisor（systemd / nssm / pm2 / supervisor），开发态自动重启用 nodemon / `uvicorn --reload`——架构都是"父进程看子进程"。本机最轻量的等价实现就是让 `start.bat` 自己当 supervisor（额外开销仅那个本来开着的窗口 ~5 MB）。

**⚠️ Windows 特有坑（实测踩到，务必记住）**：`HTTPServer.allow_reuse_address = 1` → Windows 的 `SO_REUSEADDR` 语义**允许两个进程同时 LISTEN 同一端口**（Linux 不允许）。曾实测 8765 上同时存在**两份实例**（17:33 起的 PID 20948 + 17:47 起的 PID 21128），后果是请求可能落到**旧进程**上，表现为"改了没生效 / 行为不一致"。因此：① ⑦ 重启必须**先真正释放端口再拉起新进程**（bat 顺序执行天然满足此约束）；② 排查"改了没生效"时，先 `netstat -ano | findstr :8765` 确认**只有一份**在监听。

**实证（隔离实例实测，未干扰在跑实例）**：
- `POST /api/reload` → `ok=true`、`rules_status` 正常、`records=4450`；`touch store.py` 后再次 reload，返回的 `files["store.py"].mtime` 随之变化 → 证明确实重新读取了模块文件。
- `POST /api/restart?dry=1` → `{supervised:true, restarting:false}`；**不带确认头** → 返回 `refused` 且**服务仍在**（`/api/rules-status` HTTP 200）；**带确认头** → 返回 `restarting:true`，0.6 s 后日志打印"释放端口并以退出码 42 退出"，端口正常释放（仅剩 TIME_WAIT）。
- supervisor 循环以桩程序验证：退出码 `42 → 42 → 0` 时循环执行 **3 次**后正常收敛退出（不会死循环）。

> 附带（**已回退**）：当时给 `get_web_port()` 加过 `BHF_PORT` 环境变量覆盖，用于在不干扰在跑实例的前提下另起隔离测试实例（本节实测即用 8799）。**2026-09-25 深夜已按要求移除**——端口现在只由 `config.json` 的 `web_port` 决定（默认 8765），不再受环境变量影响；要换端口请改配置文件。

**变更文件**：`src/server.py`（`hot_reload()` / `_restart_after_response()` / `request_restart()` + 两个 POST 路由；当时的 `BHF_PORT` 覆盖**已于 2026-09-25 深夜回退移除**）、`src/web/index.html`（⑥⑦ 按钮；**已于 §7.10 合并为单一入口**）、`src/web/app.js`（热重载结果面板 + 重启二次确认/轮询回访/自动刷新）、`start.bat`（supervised 循环）。

### 7.10 ⑥ 单入口「应用变更」：自动判定 + 防重启风暴 + 版本指纹（2026-09-25 落地）

**动机**：§7.9 的 ⑥/⑦ 要求用户自己判断"改了哪些文件"（改 `server.py` 才需重启）。这个判断其实完全可由程序完成——进程启动时对受监视文件取一次 `(mtime_ns, size)` 基线，之后与磁盘 diff 即可分类。故合二为一：**网页只留一个入口，由服务自动选择生效方式**。

#### 7.10.1 判定矩阵

| 变更类别 | 命中文件（目录扫描，共 12 个） | 自动动作 | 停机 |
|---|---|---|---|
| `restart` | `src/server.py`、`start.bat`、`stop.bat`；以及**任何新增/被删文件**（保守归类） | 重启进程（退出码 42 → supervisor 拉起） | ≈3.4 s |
| `reload` | `src/engine.py`、`src/store.py`、`src/collector.py`、`src/adapter_analyzer.py`、`data/rules.json`、`data/fetcher_config.json`、`src/*.py` 其它 | `importlib.reload` + 重读源库 | 0（实测 63–122 ms） |
| `static` | `src/web/*.js / .html / .css / .svg / .ico` | 服务端不动，仅提示刷新浏览器 | 0 |
| 无变更 | — | `action: none` | 0 |
| 未托管 + 需重启 | — | `action: manual`：**不自杀**，尽力热重载可覆盖部分 | 0 |
| 护栏拦截 | — | `action: blocked`（见 7.10.4） | 0 |

**清单来源 = 目录扫描**（`_watch_files()`：`src/*.py` + `src/web/*` + 两个 json），不硬编码文件名 → 以后新增模块自动纳入，不会漏判。

#### 7.10.2 端点

| 端点 | 作用 |
|---|---|
| `GET /api/code-status`（只读） | `{boot_id, pid, port, supervised, version, current_version, changes{restart,reload,static}, pending, next_action, restart_guard}` |

#### 7.10.3 基线推进语义（关键设计，避免徽章永久计数）

`CODE_BASELINE` = 最近一次**已生效**的文件指纹（启动时=磁盘快照）。热重载成功 / 静态文件变更被处理后，`reload`+`static` 类条目会**推进到当前磁盘状态**（`_rebaseline()`）→ 徽章清零；`restart` 类**不推进**（只有重启进程才能真正刷新）。实测：touch `store.py` → `pending=1` → apply → `pending=0`；touch `server.py` → apply 后仍 `pending=1, next_action=restart`。

#### 7.10.4 ② 防重启风暴

`data/run/restarts.json` 记账；**120 s 窗口内 ≥3 次**则拒绝重启并回 `blocked`（带 `retry_after_s`）。
事实核对：`server.py` 语法错时 python 退出码是 **1 而非 42** → `start.bat` 走 `pause` 分支停住，天然不会死循环；护栏防的是"能起来但被反复点重启"的场景。检查顺序为**先护栏、后托管检查**（实测未托管实例在护栏触发时同样回 `blocked`）。

#### 7.10.5 ③ 版本指纹

`version` = 12 个受监视文件 `(mtime_ns, size)` 的稳定短摘要（**手写 FNV-1a 64**）。不用内置 `hash()`（字符串哈希每进程随机，跨进程不可比）；不用 `hashlib`（本进程早已由 `collector → urllib → http.client → ssl` 链加载，改 FNV 不构成节省，但让该逻辑零依赖）。实测两次独立进程 `version` 完全一致、`boot_id` 不同。前端把它与 `pid` 一起放进按钮 tooltip，用于确认"跑的是不是我刚改的代码"，以及发现"两份实例同监听 8765"（Windows `SO_REUSEADDR` 坑，§7.9）。

#### 7.11.1 `#5/#22` 折叠修复：Plan A → **Plan B「折叠显示 + 状态聚合」**

**Plan A 的缺陷（实测）**：只取 `view_at` 最大一条 → **丢掉「已看完」状态**。本机实测 **7 条**视频
「历史某次 `progress == -1`（已看完）、最近一次只点开没看完」被误判为「需要观看」。这是**判断输入错误**，非显示瑕疵。

**Plan B 实现**（`src/store.py` `_fold_latest_by_bvid`，与 `classify_record` **同批**改动）：

| 字段 | 聚合规则 | 目的 |
|---|---|---|
| 展示字段（标题/封面/作者/uri…） | 取 `view_at` 最大的一条 | 「最近一次观看」，与官网一致 |
| `progress` | **任一会话 `== -1` → `-1`**；否则 `max` | **修 P0 误判** |
| `duration` | `max`（防御性；实测无差异） | — |
| `session_count` / `first_view_at` / `kids`（新增） | 会话数 / 最早观看 / 全部会话 kid | 支撑重看分析 + **修 P2 skip 漂移** |
| 无 `bvid` 记录（live/article/pgc） | 不折叠，原样保留 | 实测 22 条本就唯一 |
| 记录自身 `kid` | 仍为「最近一次」的 kid | 展示与既有接口**零改动** |

`classify_record` 新增 **`kids` 多键命中**：`manual_skip / auto_exempt / archived` **命中任一会话即生效**，
故「同一视频再看一次 → 新 `view_at` → 新 kid」不再让既有跳过状态静默失效。

### 7.12 第三轮：「⑥ 应用变更」重启链路被控制台冻结卡死 → 已修（2026-09-25）

> 对应待办 **#33**（派生），触发场景来自你反馈的「⑥ 没生效，只能手动重开 bat」。

#### 7.12.1 根因：关键路径上的一次控制台写入

Windows 控制台处于 QuickEdit（快速编辑）**选中**状态时，任何进程向该控制台写
`stdout/stderr` 都会**阻塞**，直到用户按 Esc / 回车取消选中。
而原 `_restart_after_response()` 的顺序是：

```
time.sleep(delay)          # 先让 HTTP 响应发完
print("…收到网页重启请求…")   # ← 这一句就可能永久阻塞
httpd.shutdown(); server_close()
os._exit(42)               # ← 永远走不到
```

→ 进程退不出去 → 退出码 42 发不出 → `start.bat` supervisor 等不到 → 网页表现即「点了 ⑥ 没反应」。

**本机证据（可复算）**：`data/run/restarts.json` 最后一次记账 **22:46:48**，
而重启后的新进程 `booted_at` 为 **22:47:44** —— **相隔 56 秒**，正常重启链只需约 3 秒
（0.6 s 响应 + 2 s supervisor + 启动），说明中间确实卡住、最后由人工重开 bat 完成。

同一坑还有第二处：`start.bat` 的 `:RESTART` 段是若干 `echo` + `timeout /t 2`，
cmd 自己的 echo 同样会被冻结，会卡住"接力"那一步。

#### 7.12.2 修复（三层防护，均不要求"用户小心别点控制台"）

| 层 | 位置 | 做法 |
|---|---|---|
| ① 输出非阻塞 | `server.py` 新增 `_safe_print()` | 所有服务端输出改到**守护线程**里写：即使被冻结，卡住的只是一次性线程，主流程照常。启动横幅、错误分支、重启提示全部改用它 |
| ② 关键路径零控制台写 | `_restart_after_response()` | 只调 `_log_restart_file()` 写 `data/run/restart.log`（文件写入不受控制台状态影响），再 `shutdown → server_close → os._exit(42)` |
| ③ 退出看门狗 | `_forced_exit()` + `threading.Timer(3.0)` | `shutdown/server_close` 无论出什么问题，**3 秒内必按 42 退出**（最坏 3 秒，而不是永远卡住） |
| ④ supervisor 段静默 | `start.bat` `:RESTART` | 删掉该段的 `echo`，延时改用 `ping -n 3 -w 500 127.0.0.1 >nul`（ping 不碰控制台），再 `goto RUN`——接力链上再无控制台 I/O |

**明确不做**：不修改控制台属性 / 不关 QuickEdit / 不写注册表 —— 你仍可用鼠标选中复制控制台文字，
代价仅是「窗口被选中时输出会延迟到解冻后显示」（服务本身不受影响）。

#### 7.12.3 新增可观测项（便于下次一眼定位）

| 前端 ⑥ 超时弹窗 | — | 直接给出「控制台自检结果 + 按 Esc 解冻」这一首要排查项，并指向 `data/run/restart.log` |

### 7.13 第四轮：「退出码被吞成 0」→ 重启链改成「主线程决定退出码 + 文件握手」（2026-09-25 23:2x）

> 对应待办 **#34**（派生）。触发场景：点 ⑥ 后控制台打出
> `[Status] Server process ended. Exit code = 0`，然后停在「Press any key to continue」——**服务停住、窗口不退出**。

#### 7.13.1 根因：`os._exit` 跑在**守护线程**里，被解释器收尾抢走

旧实现的顺序：

```
工作线程(daemon=True)： sleep(delay) → print → httpd.shutdown() → server_close() → os._exit(42)
主线程              ： serve_forever()  ← 被 shutdown() 打断，返回 → main() 走完 → 解释器收尾
```

`httpd.shutdown()` **会等 `serve_forever()` 真正退出后才返回**。所以它一返回，主线程已经在往「脚本结束」走了；
而工作线程还要做 `server_close()`、写日志（**会释放 GIL**）才能走到 `os._exit(42)`。
等到解释器开始收尾，**守护线程被直接回收** → `os._exit(42)` 永远没机会执行 → 进程以 **0** 退出
→ `start.bat` 的 `if "%RC%"=="42"` 不成立 → 落到 `pause` 分支。

**回归对照（`dev/regression_restart.py` ⑦ 项）**：新旧两种拓扑各跑 3 次 ——
旧设计 **`[0, 0, 0]`**（100% 复现），新设计 **`[42, 42, 42]`**。这不是概率问题，是结构问题。

> **方法论教训**：上一轮（§7.12）的回归脚本是**直接在主线程**调用 `_restart_after_response()`；
> 那种拓扑下调用方自己就是主线程、天然拿得到 42，**把真 bug 完全放过去了**。
> 现已补 `serve` 模式：**真实 `ThreadingHTTPServer` + 主线程 `serve_forever` + 工作线程发起重启**，
> 走与生产同一个 `_serve_forever_and_exit()`。
> 教训：*回归测试必须复现生产的线程/调用拓扑，否则等于没测。*

#### 7.13.2 修复（在 §7.12 四层之上再加两层）

| 层 | 做法 | 位置 |
|---|---|---|
| ④ **退出码由主线程决定** | 新增 `RESTART_PENDING` 挂起标记；`_restart_after_response()` **只关监听、绝不 `os._exit`**；主线程在 `serve_forever()` 返回后检查标记 → `os._exit(42)`。新增 `_serve_forever_and_exit(server)` 承载这段逻辑，`main()` 改调它 | `server.py` |
| ⑤ **文件握手（不看退出码）** | 退出前落 `data/run/relaunch.flag`；`start.bat` 在 python 返回后**先看文件在不在**（`if exist ... goto RESTART`），再看 `%RC%==42` 作为遗留信号。启动时 `_clear_relaunch_flag()` 清陈旧标记，避免「异常退出 → 白拉一轮」 | `server.py` + `start.bat` |
| 看门狗改非守护 | `threading.Timer(3.0, _forced_exit)` 显式 `daemon=False` —— 主线程若真被卡住，计时器必须活着把 42 顶出去 | `server.py` |

其他配套：

- `_begin_restart(httpd, reason, delay)` 统一入口 —— **同步**置挂起标记（必须先于工作线程，否则主线程可能抢先退出）；两处调用点（`/api/restart`、`/api/apply` 的 restart 分支）都改用它。
- Ctrl+C 语义修正：`serve_forever` 因 `KeyboardInterrupt` 退出时**清掉挂起标记**，不当作重启请求（用户意图是停）。
- `GET /api/code-status` 新增 `restart_pending`（挂起标记）与 `relaunch_flag`（握手文件是否存在），只读可查。
- 看门狗触发时也会落握手标记 → supervisor 一定能重新拉起。

### 7.14 第五轮：手动备份补上「保留 N 份」清理（2026-09-26）

**问题**（由 `doc/待办-当前阶段.md` §6.4 第 1 条发现）：`_prune_backups()`（保留最近 N 份）**只挂在自动路径**（`_maybe_auto_backup` ← `_after_data_pull`）；**手动 ⑤ 本地备份走 `/api/backup` → `_create_backup()`，没有挂清理** → 手动连点 6 次以上会看到 6 份、7 份一直堆着，与「最多留 5 份」的策略声明不一致。**这不是操作错误，是清理漏挂了一条路径。**

**修复**：`/api/backup` 端点在 `_create_backup()` 之后补一次 `_prune_backups(_load_backup_policy().get("keep"))`，并把 `pruned` 一并回传（调用方可看到本次清了哪几份）。

```python
manifest = _create_backup()
removed = _prune_backups(_load_backup_policy().get("keep"))   # #35
self._send(200, {"ok": True, "manifest": manifest, "pruned": removed})
```

**实测（隔离验证，真实 `data/backup/` 未受影响）**：把 `server.BACKUP_ROOT` 指向临时目录 → 预置 6 份旧备份 + 新建 1 份 → **7 份收敛为 5 份**，被删 `['20260902-000000','20260901-000000']`（最旧两份），保留到 `20260926-093007`；仓库 `data/backup/` 前后均为 `['20260925-170045']`，**未变**。

**策略口径（不变）**：`data/backup_policy.json` 的 `{auto: true, delta_threshold: 200, keep: 5}` —— 新增 ≥ 200 条才**自动**留一份（首次无基线不触发，需手点 ⑤ 建基线）；**手动备份不受阈值限制，但同样受 `keep` 约束**。

**变更文件**：`src/server.py`（`/api/backup` 分支 + 注释）。
