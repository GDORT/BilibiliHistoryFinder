## 1. 目标运行状态与架构

### 1.1 三方并存模型
```
┌─────────────────────────────────────────────────────────┐
│  用户本机                                                 │
│  ┌──────────────────┐   read-only 直读 + 转发触发         │
│  │  BilibiliHistory │   ┌──────────────────────────────┐ │
│  │  Analyzer 后台   │   │  我们的服务 (server.py)      │ │
│  │  (Fetcher 打包)  │──▶│  - 读 Analyzer SQLite(ro)    │ │
│  │  - 拉取/分析B站  │   │  - 规则引擎 + 三视图         │ │
│  │  - 写 bilibili_  │   │  - 转发 /fetch/* 到 8899     │ │
│  │    history.db    │   │  - 侧库 canonical_state.db   │ │
│  │  - 暴露 :8899    │   └───────────┬──────────────────┘ │
│  └──────────────────┘              │ 网页 (app.js)        │
│  ┌──────────────────┐              │ 展示/筛选/触发按钮   │
│  │  Finder 后台     │──▶ read-only  │                     │
│  │  (collector.py)  │   备份源并入  └─────────────────────┘ │
│  │  自有采集兜底    │                                          │
│  └──────────────────┘                                          │
└─────────────────────────────────────────────────────────┘
```
- **Analyzer 后台**：唯一权威数据 + 控制源；常驻时 `:8899` 提供 `/history/*` + `/fetch/*`。
- **Finder 后台（collector.py）**：默认不运行，仅作近期窗口兜底备份源；Phase 1 合并已自动包含，无额外开发。
- **我们的服务+网页**：消费 Analyzer（只读）+ 触发其控制端点（转发），不重复造拉取层。

### 1.2 需求本质与差异化壁垒（跨形态复用）
- 需求本质：**续看/历史筛选分类的规则引擎**，非"再做一个历史抓取器"。
- 壁垒（须抽离为与语言无关的算法规格，供后端 Python / 前端 JS / 油猴 D 复用）：
  - `needs`/`skipped`/`stale` 三视图（基于 `progress`）；
  - `auto_skip` + 理由绑定（可解释性）；
  - 单活跃规则 + 多组条件 + 冲突校验 C1/C2/C3；
  - `business` 预设一键加入；`dirty_count` 增量感知。

### 2.2 接入 Analyzer 的连接方式选型
| 选项 | 接入方式 | 需起 Fetcher | 推荐度 |
|---|---|---|---|
| **① read-only 直连 SQLite（已验证·主源）** | `file:...?mode=ro` 跨年表 `UNION`，排除 `_fts` 虚拟表 | 否 | **主源（推荐）** |
| **② 调 Fetcher REST API（常新升级版）** | `server.py` 瘦适配器 `GET /history/all`+`/search` | 是（常驻） | 常新升级 |

- **① 直连 SQLite**：跨 `bilibili_history_2020…2026` 做 `UNION ALL`；最大风险是 Analyzer 改表/加年表会断查询——适配器须动态枚举 `bilibili_history_%` 基表（排除 `_fts`）。
- **② 调 Fetcher API**：可拿比直连更新鲜的全量；CORS 对服务端调用无影响。

### 2.3 能否替代官方 BiliHistoryFrontend（源码评估结论整合）
> 评估依据：已置本地的真实源码副本 `doc/BiliHistoryFrontend-master/`（前端）与 `doc/BilibiliHistoryFetcher-master/`（后端），**仅读源码**。
> 详细评估原稿 `doc/BiliHistoryFrontend替代评估.md` 与 `doc/Fetcher后端源码评估.md` 已归档至 `doc/archive/`，本节为其结论浓缩。

#### 2.3.0 主结论（一句话）
**能完整替代，且是「功能子集」级别的替代。** 官方前端没有任何独占能力——它是 Fetcher/Analyzer 产物的「显示器 + 遥控面板」，不掌握数据、不掌握控制逻辑、不掌握凭证。我们工程已具备它的全部展示能力（且筛选更强），唯一缺的「触发分析」只是 Fetcher 后端接口，加一层转发即可；Analyzer 是否在运行只影响「能否触发新分析」，不影响「能否替代前端」。

#### 2.3.1 官方前端的真实架构（源码实证）
- 纯前端壳，零后端逻辑（`src-tauri/tauri.conf.json` 仅窗口/打包配置，无内嵌 HTTP server）。
- 「控制 Analyzer 更新」= 前端调 Fetcher 后端 `/fetch/*`（`src/api/api.js`）：实时增量 `GET /fetch/bili-history-realtime`、全量 `GET /fetch/bili-history` → `POST /importSqlite/import_data_sqlite`。**前端只是触发者与展示者，执行者在 Fetcher 后端。**
- 渲染契约（`HistoryContent.vue`）：`bvid/oid/aid/avid/epid/ssid/cid/cover/covers/author_face/author_mid/author_name/tag_name/business/dt/view_at/progress/duration/remark`——与 Analyzer 34 列同构。

#### 2.3.2 Fetcher 后端 = Analyzer 的控制大脑（源码实证）
- **Analyzer 无独立源码**：它是 Fetcher 的 PyInstaller 打包产物（`dist/BilibiliHistoryAnalyzer/BilibiliHistoryAnalyzer.exe`），能力全部来自 Fetcher 后端。
- **控制端点无头可触发**（`routers/fetch_bili_history.py`）：`GET /fetch/bili-history`（全量，:94）、`GET /fetch/bili-history-realtime`（增量，:131）；**无需请求体，SESSDATA 从服务端 `config.yaml` 读取**——外部只要能访问 `localhost:8899` 即可触发。
- 写库链路完整：拉取 → 落 JSON 快照 → `import_all_history_files()` 更新 Analyzer 读的那个 `bilibili_history.db` → 顺带补互动。
- `/mcp` 是**只读 MCP 服务**（只暴露读、不暴露写），印证我们 read-only 路线正确。

#### 2.3.3 替代可行性矩阵（前端功能逐项）
| 官方前端功能 | 我们能否替代 | 说明 |
|---|---|---|
| 展示历史记录（列表/卡片/封面/UP主头像） | ✅ 完全能 | 已 read-only 消费 Analyzer 产物，字段契约同构 |
| 搜索 / 筛选（FTS5 + 基础筛选） | ✅ 完全能，且更强 | 我们高级筛选器是其超集 |
| 触发分析 / 导入（点按钮让 Analyzer 重跑） | ✅ 能，但需转发到 8899 | 原非前端自身能力，是借 Fetcher 的；server 加转发 + 前端按钮即可 |
| 年度分析 20+ 页 / 收藏 / 评论 / 动态 / 下载 | ❌ 不直接替代 | 来自 Fetcher 后端 API 面，前端只是消费；按需对接共存 |
| 二维码登录 / 计划任务 | ❌ 不直接替代 | 同样来自 Fetcher 后端，前端仅按钮 |

#### 2.3.4 与官方前端对比（差异化位置）
| 维度 | 官方 BiliHistoryFrontend | 我们（替代后） |
|---|---|---|
| 技术栈 | Vue3+Vite+Tailwind+Tauri（重，桌面 exe） | 原生 HTML/JS + 1 个 Python 服务（轻，浏览器即用） |
| 覆盖功能 | 全家桶（历史/年度/收藏/评论/媒体下载/计划任务/动态…） | 聚焦「历史列表 + 续看规则分类」 |
| 续看三视图 + auto_skip 理由 + 单活跃多组 + 冲突校验 + dirty_count | ❌ 均无 | ✅ 完整（我们的壁垒） |
| 高级筛选 | 基础（类型/日期/分区） | ✅ 超集级（已实现） |
| 全量历史 | ✅ 后端持续同步 | ✅ 借 Fetcher 后端或直读 Analyzer 等同 |

#### 2.3.5 两条对接路径（替代后的控制层如何接）
- **路径 A（server.py 加 Fetcher 转发层，最轻，推荐）**：`server.py` 加薄代理——`POST /api/trigger-realtime` → `GET http://localhost:8899/fetch/bili-history-realtime`；前端加「实时更新」按钮；分类层仍由我们引擎补算注入 `/api/history`。**规则引擎与前端 100% 复用，零重写拉取逻辑。** 前提：用户本机 Fetcher 后端（Analyzer 后台）在运行。
- **路径 B（去 server.py，前端直连 Fetcher API）**：浏览器因 CORS 全开可直 `fetch('http://localhost:8899/history/all')`；但规则引擎须移植成 JS（重写），工作量等同重写引擎。**除非要彻底去 Python，否则不如路径 A。**

#### 2.3.6 字段 / 契约映射（规则引擎需求 ↔ Fetcher/Analyzer 返回）
| 需求 | Fetcher/Analyzer 字段 | 处理 |
|---|---|---|
| `business` | `business` ✅ | 直用 |
| `progress`/`duration`/`view_at` | ✅ | 直用；`progress_pct`/`view_at_age_days` 派生 |
| `title`/`author_*`/`bvid`/`uri`/`cover` | ✅ | 直用；封面走 `/cover/` 代理 |
| `kid`（skip 主键） | `kid` ✅ | 直用；无则 `(bvid,view_at)` 合成 |
| `aid/avid/epid/ssid/cid/covers/author_face` | ✅ 但 `ANALYZER_COLS` 未全纳入 | 若直连 Fetcher `/history/all` 需补齐 |
| `auto_skip`/`skip_state`（分类层） | ❌ 不提供 | **我们的引擎计算后注入** |

### 2.4 接入选型结论
- 主源 = ① 直连 Analyzer SQLite（已验证）；Finder 自有采集作近期窗口补充源。
- 若需「常新全量」或「替代官方前端 + 获得触发分析能力」（见 §2.3），升级到 ② Fetcher API（路径 A 转发）。
- 三者共用统一 canonical 契约与规则引擎，切换无损。

### 3.6 工程架构现状（Phase 1 实测，吸收自 `架构分析.md`）
> 原 `doc/架构分析.md` 已归档至 `doc/archive/`，其核心内容吸收于此节。

**分层与数据流**（数据源只读 → 读层/合并 → 规则引擎 → 分类/查询 → HTTP 编排 → 前端）：
```
B站服务端(仅collector备用)   Analyzer SQLite(主源,RO,34列/年表)   Finder SQLite(备份源,RO,27列)
        │                            │                              │
        ▼                            └── store.py 合并 ─────────────┘ (统一复合键 (bvid,view_at) 去重)
   data/bilibili_history.db ◄───────────────────────────────────────┘
        │
   store.py — 读多源 → canonical records（RAW_CACHE 模块级缓存）
        │  _read_analyzer() file:?mode=ro 跨年表 UNION（排除 _fts 虚拟表）
        │  _read_local()    file:?mode=ro 读 history 表
   engine.py — 纯逻辑规则引擎（无 I/O）：eval_condition / eval_group / evaluate_rule / validate_rule / classify
        │
   store.py — classify_record() 计算分类 + 侧状态库 canonical_state.db（唯一可写）
        │
   server.py — ThreadingHTTPServer + 后台线程；GET/POST /api/* · /cover/ 代理 · 静态资源
        │
   web/ — 原生 SPA（index.html / app.js / style.css）
```
**模块清单**（Phase 1 落地）：`engine.py`(498,纯逻辑) / `store.py`(609,数据层) / `server.py`(656,服务编排) / `collector.py`(548,备份采集默认不运行) / `adapter_analyzer.py`(121,验证脚本) / `web/`(2250,前端)。

**只读原则落地**：`store._read_analyzer()/_read_local()` 均 `file:?mode=ro`；分类状态只落 `canonical_state.db`，与两源库物理隔离；唯一可能写源的是 `collector.py`（写自有 Finder 库，默认不运行）。

**关键架构决策与风险**（务必记取）：
- **合并键必须对齐**：初版按 `kid` 合并 → Analyzer `kid` 恒 0、Finder `kid`=oid → 零重叠 → 合并成 5678 重复；修正为 `(bvid,view_at)` 后正确 3278。**任何新增备份源必须先对齐主键**。
- **Analyzer 表结构耦合**：Analyzer 改表/加年表/取消 `_fts` 会使 `GLOB 'bilibili_history_[0-9][0-9][0-9][0-9]'` 漏表；字段名变动需同步 `ANALYZER_COLS`（代码已支持 `ANALYZER_DB` 环境变量覆盖路径便于迁移）。
- **后台任务靠轮询 JSON**：长任务进度依赖前端轮询进度文件，无 WebSocket/SSE。
- **collector 双链路维护成本**：两套采集并存，SESSDATA 过期需手动更新（`server` 暂无重填 UI）。

### 3.7 Phase 1 验证证据（吸收自 `adapter-验证报告.md`）

- **接入**：`GLOB 'bilibili_history_[0-9][0-9][0-9][0-9]'` 枚举 7 张年表（2020–2026，2813 条），**排除 `_fts*`**；`archived_only` 无列补 0。
- **canonical 映射**：Analyzer 34 列 = `derived` 基准完全成立（`business/duration/author_*/title/progress/view_at` 直映；`progress_pct`/`view_at_age_days` 派生）。
- **验证结果（只读，未写库）**：
  ```
  total: 2813 | finished: 1239 | auto_skip: 1085 | stale: 0 | needs: 489
  校验和 1239+1085+0+489 = 2813 ✓
  ```
  `stale=0` 是默认规则「首命中优先」+ 陈旧分组排最后导致（老视频先被短视频碎片命中），非缺陷，可调 `rules.json` 顺序让 stale 生效。
- **结论**：方案①可行、引擎已抽离为可移植纯逻辑、只读原则成立。

### 3.8 规则引擎核心（吸收自 `记录筛选规则分析.md` §2–§10）
> 原 `doc/记录筛选规则分析.md` 已归档，规则引擎核心（三视图/优先级/冲突/dirty_count）吸收于此；其 §11「高级筛选器超集」归前端轴（见 `方案-前端.md` §3）。

**数据模型与进度语义**：输入 canonical derived；`progress==-1` 表示已看完 → `progress_pct=1.0`；`view_at_age_days=(now-view_at)/86400` 派生。

**`rules.json` 结构**：单 `active` 规则（同一时刻仅一条，`server.POST /api/rules` 强制校验 C6）+ 多 `groups`（`match:"any"`=OR 语义，命中任一分组即按该分组 `action` 处理）。

**求值算法**：`eval_condition`（单条件）→ `eval_group`（分组内 AND）→ `evaluate_rule`（返回 `(action,label)` 或 `None`；`progress==-1` 短路返回 `None`；首命中优先）。

**三视图模型**（不变式 `finished+auto_skip+stale+needs==total`）：
- `finished`：已看完（progress=-1）
- `auto_skip`：命中 auto_skip 分组
- `stale`：命中 stale 分组（久未观看）
- `needs`：未完成且未被跳过（待观看）
- 实测（default 规则，3278 条合并集）：1473 / 1226 / 0 / 579。

**跳过状态与优先级**：`manual_skip`（人工）> `auto_exempt`（取消自动跳）> `auto_skip`（引擎）；`needs` 视图有隐含 95% 门（progress_pct≥0.95 归入 auto_skip 而非 needs）。

**冲突校验 `validate_rule`**：返回 `{hard, soft, info}`（C1 重复条件 / C2 互斥 action / C3 无效字段；C6 多 active 由 server 强制）。

**增量感知 `dirty_count`**：`rules_hash` 比对「已应用哈希」与当前规则，统计上次应用以来新增未套用条数；`rules_status()` 返回 pending + dirty_count。

**默认规则行为复盘**：5 分组（接近看完/误触/短视频碎片/直播回放/陈旧），default 下 auto_skip 多为短视频碎片（duration<60）、needs 多为低进度长视频——符合预期。

## 4. 统一数据契约（canonical schema）

### 4.1 结论：统一「逻辑数据契约」，不强求「物理数据库引擎」
- **不统一物理引擎**：浏览器 IndexedDB 与本地 SQLite 各擅其场；强行单一物理库会引入 IPC/跨进程依赖，破坏「D 零后端」优势。
- **统一逻辑契约（canonical schema）**，所有路线必须遵守：
  - **权威层 `raw`**：完整 `cursor` 响应 JSON 原样存储，`key = (bvid|oid)@view_at`，永不丢字段。
  - **派生层 `derived`**：规则引擎所需规范化字段集——`business`/`progress`/`duration`/`view_at`/`title`/`author_name`/`author_mid`/`bvid`/`uri`/`cover`/`kid`/`dt`/`live_status` + 派生 `progress_pct`/`view_at_age_days`/`skip_state`。
- 规则引擎与 UI **只面向 canonical `derived` 开发一次**；各路线通过 storage adapter 映射进 canonical 形式。

### 4.2 实测校准与路线适配
- canonical `derived` 以 Analyzer 34 列为基准；Finder 的 `raw_json` 仅 23 键，不是真·权威层。
- 路线适配：D 在 IndexedDB 建 raw/derived 双仓库；A（Fetcher）其 `/history/all` 返回即 derived；B（Analyzer）read-only attach 映射。
- 由此 R1（字段对齐）降为「canonical ↔ 各源一次性映射」；R4（分类状态）统一落 canonical side 小库。

### 4.3 统一 DB 的取舍
- **收益**：路线间无损切换、零缺失迁移；规则引擎/UI 单一代码库跨形态复用；新增第四种数据源只需映射进 canonical。
- **代价**：前期须冻结 canonical schema（一次性）；D 须实现双存储且抓完整 cursor；合并时 Finder 侧缺字段留空（可接受）。
- **裁定：基于统一逻辑 DB 契约开发（非统一物理引擎）。**
