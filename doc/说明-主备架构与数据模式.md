## 2. #1 落地：三层处理（凭证单一化 → 回退链 → 主动提醒）

### L1 凭证只留一处（消除冲突源）

- 删除 / 停用 `config.json` 的 `SESSDATA`，Finder 不再直连 B站抓取。
- 这一步就是原「**计划 A**」（后端 §7.4 / §7.6）的落点；落地后 `collector.py` 从主链路退场。
- 「同步数据」按钮（`POST /api/sync`）随之改写为**触发 Analyzer 全量**（见 #2 模式 A 的抓取列），或直接移除。

### L2 回退链（auto 优先级）

```
启动 / 每次 reload
  ├─ Analyzer 可达 且 主库可读        → 【模式 A】Analyzer 主力（默认，正常路径）
  ├─ Analyzer 不可达 但 本地库有数据   → 【模式 B-降级】本地只读，顶部黄色横幅提示
  └─ 两者都不可用                      → 空态 + 引导（启动 Analyzer / 检查路径）
```

**明确取舍：不自动启用「自身抓取」。** 理由：

1. 自身抓取需要**有效 SESSDATA**，而凭证按 L1 已单一化到 Analyzer——自动回退会立刻撞上 -101；
2. 与「凭证只留一处」的治理目标直接冲突。  
   → 因此**自身抓取必须由用户在设置里显式启用**（即「模式 B-独立」，见 §3），而不是悄悄回退。

### L3 凭证失效「主动提醒」（Finder 侧补齐）

Analyzer 已有邮件告警，**不重复实现**。Finder 只做**网页可见性**：

| 动作               | 实现点                                                                             |
| ---------------- | ------------------------------------------------------------------------------- |
| 读 Analyzer 登录态   | 转发 `GET /login/check`（已有转发器 `_forward_fetcher`，复用即可）                            |
| 读自身凭证态（仅模式 B 需要） | 探测 `config.json` 的 SESSDATA 是否有效（调一次只读接口看是否 -101）                               |
| 展示               | 顶部横幅：🟢 正常 ｜ 🟡 Analyzer 不可达（已降级本地）｜ 🔴 凭证失效（-101）→ 文案指向 Analyzer `config.yaml` |
| 扩展点              | `GET /api/fetcher-health` 已存在（`server.py:967`），在此基础上加 `sessdata` 字段即可，**无需新端点** |

## 3. #2 落地：主开关 + 两模式数据规则

### 3.1 主开关（一个键，一处判定）

```jsonc
// config.json 新增
"data_source": {
  "mode": "auto",          // auto | analyzer | local
  "local_first_if_analyzer_down": true
}
```

- 端点：`GET /api/data-source`（读，含「当前实际生效模式」）/ `POST /api/data-source`（写）。
- UI：设置齿轮弹窗内加一个三选一（与现有 `/api/fetcher-config` 同款形态，不新增常驻进程）。
- 切换后**立即** `store.reload_raw()`，无需重启。

### 3.2 两模式数据规则（对照表）

| 维度          | **模式 A · Analyzer 主力**（默认）                                             | **模式 B · Finder 自身**（独立 / 降级）              |
| ----------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| 触发场景        | 正常路径                                                                   | Analyzer 未装 / 未启动 / 用户显式切换                 |
| **主源**      | `Analyzer/output/bilibili_history.db`（年表分区，2020–2026 深历史）              | `Finder/data/bilibili_history.db`          |
| 补齐源         | 本地库，仅补 Analyzer 缺失的 kid                                                | 无（Analyzer 不参与）                            |
| **凭证**      | Analyzer `config/config.yaml`                                          | Finder `config.json`（**须用户自备有效 SESSDATA**） |
| **抓取执行**    | 转发 Analyzer：② `/fetch/bili-history-realtime` ｜ ③ `/fetch/bili-history` | 本机跑 `collector.py`（原 `/api/sync` 语义）       |
| **写入方向**    | 不写任何源库；本地库只被 `POST /api/backup` 快照                                     | collector 写本地库（唯一写入者）                      |
| **冲突解决**    | kid 相同 → **Analyzer 优先**（`store.py:164` 现有行为）                          | 无跨源冲突（单源）                                  |
| **折叠规则**    | 按 `bvid` 折叠（Plan A，`_fold_latest_by_bvid`）                             | **同左**（保持一致，避免模式间视图跳变）                     |
| **skip 键**  | `kid = (bvid, view_at)`                                                | **同左**（`_rec_key` 已统一）                     |
| **UI 提示**   | 无                                                                      | 顶部横幅常驻：`自身模式` + 凭证状态点                      |
| **完整性自检 ④** | 中继 Analyzer `/data_sync/check`                                         | 不适用（无 JSON↔DB 双份），改做「本地库自检」或禁用             |

> **跨模式一致性（最要紧的一点）**：`store._rec_key()` 在两源都用 `(bvid, view_at)` 作 kid，  
> 所以 **切模式不会丢 skip / views / lists**（这些存在侧库 `canonical_state.db`，与源库解耦）。  
> 这是当前架构已经具备的红利，主开关可以放心做，不需要状态迁移。

### 3.3 「保证冲突问题」具体指哪三类冲突

| 冲突                                          | 现状              | 模式开关后的处置                                                                       |
| ------------------------------------------- | --------------- | ------------------------------------------------------------------------------ |
| **双写冲突**（Finder collector 与 Analyzer 各写各的库） | 存在（两份凭证、两条同步路径） | 模式 A 下 collector 退场 → **冲突消失**；模式 B 下 Analyzer 不参与 → **仍无冲突**。**同一时刻只有一个写入者**。 |
| **同 kid 内容不一致**（两源都有该记录但字段不同）               | 已按 Analyzer 优先  | 保持不变；模式 B 下无此问题                                                                |
| **抓取时间窗不一致**（本地近期窗口 vs Analyzer 深历史）        | 本地仅补齐           | 模式 A：Analyzer 全量为准；模式 B：本地窗口为准 + 横幅说明「历史深度有限」                                  |

## 4. #10 澄清：「Fetcher API 直连」目前**不算**

### 文档定义

`方案-后端与数据源.md` §0.1 / §2.3 里的「**Fetcher API 直连（常新全量）**」指：

> **Finder 绕开 Analyzer，自己直连 B站 Fetcher 的抓取接口**，从而拿到比「读 Analyzer 的 DB」更新的全量数据。

### 现状判定：**是中继（relay），不是直连**

| 路径                                                               | Finder 做了什么    | 谁执行抓取        | 谁持凭证            | 判定                     |
| ---------------------------------------------------------------- | -------------- | ------------ | --------------- | ---------------------- |
| `POST /api/fetcher-trigger` → 转发 Analyzer `/fetch/bili-history*` | 调用了 8899 的 API | **Analyzer** | **Analyzer**    | ❌ 直连（=**中继**）          |
| `GET /api/fetcher-check` → 转发 `/data_sync/check`+`/report`       | 调用了 8899 的 API | Analyzer     | Analyzer        | ❌ 直连（=中继）              |
| `POST /api/sync` → 本机 `collector.py` 直连 B站                       | 自己发 HTTP 到 B站  | **Finder**   | **Finder**（已失效） | ✅ **这才是直连**，但**当前不可用** |

**判据只有两条**：①谁的进程向 B站发请求；②谁的配置持 SESSDATA。

所以：

- 「Finder 调用了 Fetcher 的 HTTP API」**成立**；
- 「Fetcher API 直连」**不成立** —— 因为执行者是 Analyzer。

### 什么时候会变成"直连"

只有走 **模式 B**（Finder 自持有效 SESSDATA + 跑 `collector.py`）时才叫直连。  
但按你的定位（**Analyzer 主力、Finder 轻量备份**），**不建议**为此恢复 Finder 的直连抓取；  
该行在文档里的定位保持「🔲 未规划（可选升级）」是准确的。

> 建议：文档里把这一行**改名为「直连 B站抓取（collector 自持凭证）」**，避免与「调用 Fetcher 的 API（中继）」混淆——这正是你这次会问出来的根因。
